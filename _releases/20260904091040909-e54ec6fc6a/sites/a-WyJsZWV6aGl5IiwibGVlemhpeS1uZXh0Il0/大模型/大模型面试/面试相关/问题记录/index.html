基础概念

大模型智能体，LLM Agent，是以大语言模型为核心决策器，结合工具调用、状态管理、任务规划、记忆、反馈评估和安全控制的任务执行系统。

  • 核心：LLM，
  • 工具调用
  • 状态管理
  • 任务规划
  • 记忆

普通调用、Agent、Workflow、RAG 的区别

类型 核心特征 适合场景 主要风险
普通 LLM 单轮或多轮文本生成 问答、摘要、写作 容易幻觉，不能执行动作
Workflow 固定流程编排 审批流、ETL、规则明确任务 灵活性不足
RAG 检索后生成 知识库问答、文档查询 检索质量决定上限
Agent 动态规划、工具调用、反馈修正 复杂任务、自动化执行 不可控、成本高、调试难

ReAct模式

Re=Resoning
Act=Action

即“推理 + 行动 (+观察)”。模型在思考、调用工具、观察结果之间循环。

优点：

  • 可解释性：因为是推理+行动+观察的循环，所以便于跟踪、调试。
  • 纠错能力：模型会根据工具的返回不断调整策略。
  • 工具协同：能适应需要多次与外部交互的复杂场景。
  • 幻觉相对较少：因为在不断的获取外部工具的返回。
    缺点：
  • 延迟和成本高：慢、烧Token。
  • 循环风险：需要控制循环次数，不然没完没了
  • 依赖工具返回的质量
  • 增加状态管理成本：长下文变多了
  • 不适合简单任务：杀鸡用牛刀
  • 在长任务重容易偏离最初的计划，越走越远。

实战中需要混合使用：比如用 Plan-and-Execute 先规划大框架，再在每一步里用 ReAct 细执行，兼顾全局观和灵活性。纯 ReAct 在长任务上容易越走越散。

适用场景："边想边查、边查边调"的场景

  • 需要调用多个工具的复合任务：比如一系列的工具调用，先查天气、再规划行程、再定闹钟之类的。
  • 信息检索 + 推理问答（RAG 增强）：比价、产品比较
  • 代码调式、排错
  • 交互式决策：客服、导购、技术支持，"信息逐步到位"的这种

不适用的场景：

  • 简单问答、翻译、摘要
  • 确定性强的：比如格式转换
  • 实时性要求高的
  • 不允许试错的

Plan-and-Execute模式

Plan-and-Execute 把智能体拆成两个角色：先规划，再执行。

复杂任务如果直接用 ReAct，模型容易走一步看一步。Plan-and-Execute 先生成全局计划，再逐步执行，可以提升长任务稳定性。

优点：

  • 结构清晰、可控性强
  • 避免跑偏（ReAct可能会逐渐偏离主题）
  • 适合长链路复杂任务
  • 支持并行执行

缺点：

  • 计划质量是瓶颈，计划错了可能在一些没预料到的地方出问题
  • 重规划成本高，也就是灵活性低
  • 不适合强探索任务：也就是一开始不搜索和查询很难列出靠谱的计划的情况
  • 计划可能过于死板，一开始列的计划不一定是最优的

适用于：

  • 更确定性的
  • 多阶段、长链路任务
  • 需要人类审核的
  • 并行可拆解的任务
  • 已有人工流程的

不太适合：

  • 开放式探索：没法做计划
  • 强实时反馈：计划赶不上变化
  • 步骤极简的任务：没必要做计划，反而是负担

Self-Ask模式

关键是向自己提问。 其实是ReAct的简化版。

Self-Ask 让模型先把复杂问题拆成多个子问题，再逐个求解。

把一个大问题拆成可回答的小问题，降低单次推理难度。

是 2022 年 Google 提出来的一个相对"轻"的模式，专门用来解决复杂多跳问答（multi-hop QA）——就是那种答案不能一次搜出来、必须拆成多个子问题逐步推理的问题。

让模型对问题进行显式的子问题分解，每一步决定："我能不能直接答？如果不能，那我需要先知道什么？" 然后用搜索引擎查那个子问题，拿到答案再继续推理，直到能回答原问题为止。

优点：

  • 适合知识密集型多跳推理
  • 幻觉少
  • 实现简单
  • 有利于减少遗漏
  • 能显式暴露问题结构

缺点：

  • 不适合非问答任务
  • 推理粒度有限
  • 不太适合做复杂 Agent 的底座，更像是QA的增强
  • 子问题拆错会导致最终答案偏离。
  • 不适合简单问题

适用于：

  • 知识库问答、企业知识检索增强
  • 事实核查（社交媒体常见：推特、B站）
  • 学术/研究助手

实战中，更多是作为一个技术模式被吸收进更大的系统，而不是单独用。

思维链模式

是让模型进行逐步推理。实际产品中通常不暴露完整内部推理，而是输出关键理由。

严格来说它不算 Agent 范式，而是一种提示/推理技术，但因为影响太深远，所有 Agent 模式基本都建立在它之上。

不直接问模型"答案是什么"，而是让它显式写出中间的推理步骤，再给出最终答案。

优点：

  • 大幅提升推理能力。数学、逻辑、常识推理上效果立竿见影，复杂问题准确率能涨 30%+。
  • 可解释性强。推理过程透明，方便调试和审查。
  • 实现简单
  • 和其他模式天然兼容。CoT 是"底层能力"。
  • 零成本启动。不用工具、不用额外 LLM 调用，只是 prompt 技巧。

缺点：

  • 不调用外部工具
  • 幻觉问题没解决
  • 推理过程可能是"事后合理化"，模型不一定真的在"思考"，可能只是生成了看起来合理的推理文本，结论是别的方式得到的。
  • 长 CoT 成本高
  • 对简单问题反而是浪费
  • 不擅长开放/主观问题。创造性写作、情感对话这种，强制 CoT 反而别扭。

适用于

  • 数学/逻辑推理题：
  • 多步推理问答
  • 复杂决策解释
  • 作为其他 Agent 模式的"引擎

不太适合：

  • 需要真实世界信息的任务
  • 需要操作外部系统的任务
  • 创意/开放对话（推理链反而限制发散）

思维树模式

把推理从“一条链”扩展为“多条候选路径”，再进行搜索和评估。

ToT（Tree of Thoughts，树状思维）是 CoT 的"超进化版"，2023 年 Princeton 和 Google 提出来的。核心思路是把推理从一条线扩成一棵树，让模型能同时探索多条路径、评估、回溯——这才是更接近"人类思考"的方式。

思维分解-->思维生成-->状态评估-->搜索算法

变种：

  • top-K
  • 回溯
  • 评分

优点：

  • 可解释性强
  • 能回溯、能剪枝
  • 显著提升需要探索的任务：数学证明、组合优化、策略游戏这些场景效果炸裂
  • 评估机制让选择更可靠
  • 解决CoT单链脆弱问题

缺点：

  • 慢、贵
  • 评估器设计是关键也是难点
  • 不适合简单问题
  • 实现复杂度高：树状态、剪枝、控制深度
  • 效果不稳定

适用于：

  • 需要探索和试错的复杂推理：数学证明、逻辑谜题、24 点、数独
  • 策略类任务：下棋、博弈、规划路径（虽然实际游戏 AI 更专用算法）
  • 创意写作需要反复尝试
  • 复杂决策分析

不适用于：

  • 实时性强的
  • 成本敏感的
  • 简单问答的
  • 开放性的，没有客观评估标准的

反思模式

Reflexion 是“执行后反思”。它让智能体根据失败结果总结原因并调整策略。

不要把失败简单重试，而是从失败中提取可执行的修正策略。

优点：

  • 对代码修复、测试失败、工具调用失败很有效。
  • 能把失败信息转化为下一步行动。
  • 可与长期记忆结合，积累经验。
  • 提升长任务鲁棒性。

缺点：

  • 反思质量依赖错误信息质量。
  • 可能反思错方向。
  • 会增加循环次数和成本。
  • 如果没有客观评估，容易自我安慰式修正。

适用于：

  • 自动修复测试失败。
  • 代码生成迭代。
  • 运维故障排查。
  • 文档质量改进。
  • 浏览器自动化失败恢复。

多智能体

Pattern 工作原理
Subagents  子代理商 主代理协调各个子代理作为工具。所有路由都通过主代理，由主代理决定何时以及如何调用每个子代理。
Handoffs  交接 行为会根据状态动态变化。工具调用会更新状态变量，从而触发路由或配置更改、切换代理或调整当前代理的工具和提示。
Skills  技能 按需加载专业提示和知识。单个代理始终保持控制，并根据需要从技能中加载上下文。
Router  路由 路由步骤对输入进行分类，并将其定向到一个或多个专门的代理。最终结果被综合成一个组合响应。
Custom workflow  自定义工作流程 使用 LangGraph 构建定制化的执行流程，融合确定性逻辑和智能体行为。将其他模式作为节点嵌入到工作流中。

多智能体的优点：

  • 上下文隔离：每个 Agent 只看自己关心的上下文，能绕开上下文窗口限制
  • 权限与工具隔离：天然支持最小权限原则。
  • 可观测性更好：出问题时能精确定位是哪个 Agent 哪一步挂了，比一坨黑盒好排查。
  • 可以并行
  • 专业化：每个 Agent 的 system prompt、可用工具、甚至微调过的模型都可以不同，比单Agent上限更高。
  • 错误隔离——下游 Agent 可以 catch 上游的错误重试或兜底。

缺点：

  • Token 消耗爆炸：贵，Anthropic 的研究里，多智能体系统的 token 消耗是单 Agent 的 15 倍。
  • 延迟叠加：慢，多智能体慢+慢+慢=巨慢
  • 上下文传递损耗——Agent A 把信息结构化传给 B，信息会丢失；B 还得再理解一遍。传得越多越失真。
  • 协调逻辑复杂——谁来决策、分支条件、并发冲突、死锁，写过的人都懂。
  • 评估困难——单 Agent 你能搞 input/output pair，多 Agent 是动态链路，ground truth 都没有，自动化评估几乎做不出来。
  • "流程合规但答案平庸"——这是最隐蔽的。每个 Agent 都按部就班，最后组合出来的结果反而没了灵气，甚至不如一个好的单 Agent 直觉式回答。

适用于：

  • 天然多角色的场景：开发（PM+Dev+QA）
  • 强工作流
  • 需要权限、工具隔离

不适用于：

  • 简单问答、单领域
  • 实时性强的
  • 预算敏感的

OpenClaw架构

OpenClaw 是一个 Local-first、Gateway-first 的开源 AI Agent 框架，通过将 LLM 嵌入本地执行环境，使 AI 能够在 24+ 种消息渠道中自主感知、决策和行动。

1. 设计哲学

Local-first（本地优先） 架构是其最具特色的设计决策之一。与其他将数据存储在云端数据库的 Agent 框架不同，OpenClaw 将所有数据——包括对话历史、记忆、知识库、配置——存储在本地 Markdown 文件中。

好处：数据主权、可移植性、可观测性

Gateway-first（网关优先） 是 OpenClaw 区别于其他框架的核心架构决策。大多数 Agent 框架采用"模型优先"的设计——先加载 LLM，再考虑如何接收输入和输出结果。OpenClaw 反其道而行之：

  • Gateway接收所有渠道消息，消息解析、身份验证和路由分发
  • Agent Runtime 在此基础上运行，不关心消息来自哪个渠道

2. 背后的核心框架

OpenClaw 嵌入了 pi-coding-agent SDK 作为其"大脑"层3^。这是一个专门用于代码生成和工具调用的轻量级 SDK

极简：Pi 最大的特点是「做减法」：系统提示词和工具定义加起来不到 1000 tokens，核心只有 read、write、edit、bash 四个工具，没有内置 plan mode，没有 to-do 系统，没有 MCP 支持，没有权限弹窗，甚至没有绑定任何特定模型

3. 架构概览

  • 渠道适配层：消息渠道的协议差异，将消息标准化为内部格式。
  • 网关：消息路由、身份验证、速率限制、负载均衡。
  • Agent Runtime：协调感知-推理-行动循环，管理 Agent 生命周期。
  • 插件和技能：封装可复用的工具能力（发邮件、查数据库等）
  • 记忆和知识：短期对话上下文 + 长期知识存储（本地 Markdown）
  • 模型提供层：抽象多种 LLM 后端（OpenAI、Claude、本地模型等）
  • 本地执行层：在本地 Docker/沙箱环境中安全执行插件代码

AgentUniverse

agentUniverse 定位于多智能体应用开发的模式工厂（Collaborative Pattern Factory）。与 LangGraph 等通用编排框架不同，它的核心设计目标是为金融、投研等需要领域专家知识的严苛业务场景提供经过验证的协作模式抽象3。

1. 核心架构特征

  • 统一的双文件组件模式：一个YAML配置（component.yaml）声明组件属性，一个Python文件定义行为逻辑。这种分离使得组件配置可以在不修改代码的情况下被修改和复用。
  • 组件化元架构：所有可扩展模块统一继承自 ComponentBase 基类，并通过 ComponentEnum 枚举标识类型。框架内置 30+ 种组件类型，每种类型对应独立的 Manager 类（如 AgentManager、ToolManager），采用注册表模式管理组件实例的生命周期
  • 声明式配置驱动：每个组件的 YAML 配置中包含 metadata 段，通过 module 和 class 两个字段指定绑定的 Python 类路径。框架启动时自动扫描配置路径，完成组件的实例化、注册和依赖注入。

其中 Planner 是框架最具特色的组件。它不仅是单智能体的决策核心，更是多智能体协作模式的核心载体——PeerPlanner 实现 PEER 四阶段协作，RagPlanner 实现检索增强生成，ReActPlanner 实现推理与行动循环。

3. 内置的两种协作模式

3.1. PEER（Plan-Execute-Express-Review）

PEER 模式由四个不同角色的 Agent 组成，通过顺序执行和评审反馈实现复杂任务的迭代优化：

  1. Planning Agent（计划智能体）：将任务分解为可执行的步骤框架
  2. Executing Agent（执行智能体）：按步骤执行并收集中间结果
  3. Expressing Agent（表达智能体）：综合所有结果生成最终表达
  4. Reviewing Agent（评审智能体）：评估结果质量并打分（0-100 分）

评审得分 >= eval_threshold 时返回结果，否则循环重试，最多 retry_count 次。

3.2. DOE模式（Definer-Observer-Evaluator）

DOE 模式（又称 Data-fining/Opinion-inject/Express）由三个 Agent 组成，专门面向数据密集型任务14：

  1. Data-fining Agent（数据精化智能体）：处理数据收集、清洗和计算
  2. Opinion-inject Agent（观点注入智能体）：结合数据结果与预收集的专家意见
  3. Express Agent（表达智能体）：基于文档类型和语言风格生成最终输出

适用场景包括金融数据分析报告、数据密集型研究报告等需要结合领域知识的数据分析任务。

LLM 本质上是无状态的——每次调用都像一次"短暂失忆"。Memory 系统的本质是为语言模型补上状态管理能力，让 Agent 能够记住过去的信息、积累经验、保持上下文连贯。

如果向量检索不准确该怎么排查

漏召（该有的没回来）
排错（回来的但不相关排前面）、
语义漂移（字面不沾边但向量很近）

排查方向：

  • Query侧：
  • 检索参数：
    • k 值太小
    • 阈值太高
    • 纯向量没 BM25 兜底
  • 索引侧：
    • chunk 切太碎
    • overlap 不够
    • metadata 过滤条件写错
    • 重复/近重复文档没去重
  • Embedding 模型侧
    • 领域不适配
    • 维度/池化方式
  • Rerank 侧排查
    • rerank 模型太轻或cross-encoder 输入 truncate 太短

如果大模型返回的结果不符合预期该怎么排查

  • 根据症状先判断，有些问题能一眼看出来
  • 根据日志追踪、Hook去定位哪个点开始跑偏，是提示词问题、工具调用、知识质量，LLM执行中逐渐偏离
  • temperature=0 跑 5 次，看是稳定错还是偶发错

  • 自动化断言
