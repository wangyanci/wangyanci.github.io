1. 一句话本质

训练 = "千卡规模 + 数周时间 + 显存放不下 + 通信为主"      → 优化：并行 + 分片 + 重计算
推理 = "单请求毫秒级 + 显存装得下 + 计算为主"            → 优化：批处理 + KV Cache + Kernel 融合

两套完全不同的工程问题，几乎没有代码复用。

2. 训练 vs 推理：完全不同的两套分布式体系

维度 训练 推理
核心目标 尽快把 Loss 降下来 尽快把 Token 吐出来
规模 千卡 / 万卡（数据 + 模型分片） 几卡到几十卡（模型装得下）
时间尺度 数天 ~ 数周 几十毫秒 ~ 几秒
显存压力 极大（模型 + 优化器 + 梯度 + 激活 + KV） 中等（模型 + KV Cache）
通信模式 AllReduce（梯度聚合）+ All-to-All（MoE） 主要是张量并行 AllReduce
主要瓶颈 通信带宽 + 显存 显存带宽 + Kernel 启动开销
关键优化 并行策略 + ZeRO + 重计算 PagedAttention + Kernel Fusion + 连续批处理
代表框架 DeepSpeed / Megatron / FSDP / Colossal-AI vLLM / TensorRT-LLM / SGLang / LMDeploy
底层通信 NCCL / RCCL / HCCL NCCL / RCCL / HCCL（同）
本章核心问题

大模型"分布式"两个字在训练和推理里指的东西几乎完全不同——训练关心"千卡怎么协同算梯度"，推理关心"显存怎么高效吐 Token"。

本文按"训练生态 / 推理生态 / 通信层 / 编排层 / 完整技术栈"五个层次逐层展开。

4. 训练生态的层次结构

所有 LLM 训练框架都遵循同样的 5 层架构：

Application           ← LLaMA-Factory / Hugging Face Trainer / NeMo
       │
Trainer               ← HuggingFace Trainer / Lightning Trainer / 自研 Trainer
       │
Distributed Framework ← DeepSpeed / Megatron-Core / FSDP / Colossal-AI
       │
Torch Distributed(c10d) ← ProcessGroup / NCCL Backend / DDP / FSDP
       │
CUDA / ROCm / CANN    ← 真正的 GPU 通信原语

类比：

层级 比喻
Application "客户的应用需求"
Trainer "项目管理层"
Distributed Framework "工程团队"
Torch Distributed "通信协议层（TCP/IP）"
NCCL / CUDA "物理网卡 / 光纤"
关键洞察

PyTorch Distributed（c10d）是所有训练框架的"事实根"——DeepSpeed / Megatron / FSDP / Colossal-AI 都在它之上构建。

真正负责 GPU 通信的"硬件驱动"是 NCCL（NVIDIA）/ RCCL（AMD）/ HCCL（昇腾）/ oneCCL（Intel）。

因此"换底层通信后端"几乎是唯一能跨硬件厂商移植大模型训练的方法。

5. PyTorch Distributed——所有训练框架的根

PyTorch Distributed（c10d = Common Distributed Communication）
是 PyTorch 的分布式通信模块，提供：

  ProcessGroup        ← 进程组（哪几个进程要一起工作）
  NCCL Backend        ← NVIDIA GPU 集合通信
  Gloo Backend        ← CPU 集合通信
  MPI Backend         ← HPC 集群
  UCC Backend         ← 统一集合通信（CXL / SHARP）
  RPC Framework       ← 跨机远程过程调用
  DistributedDataParallel (DDP)  ← 数据并行
  FullyShardedDataParallel (FSDP)← 模型分片数据并行
  Pipeline Parallel   ← 流水线并行（PyTorch 内置）
  DeviceMesh          ← 多维设备网格（TP × DP）
  DTensor             ← 带分片元信息的分布式张量
  Elastic             ← 弹性训练 + 故障恢复
本节核心问题

DeepSpeed / Megatron / FSDP 是高楼——PyTorch Distributed（c10d）就是地基。

几乎所有大模型训练框架都在 c10d 之上构建。本节从源码角度深度剖析 c10d 的设计：架构、初始化、ProcessGroup、Store、Reducer、Backend、Elastic、DeviceMesh 等。

5.2. 初始化过程（init_process_group）

最经典的初始化代码：

  dist.init_process_group(
      backend="nccl",         # GPU 用 nccl；CPU 用 gloo
      init_method="env://",   # 用环境变量
      world_size=8,           # 总进程数
      rank=3,                 # 当前进程的全局 rank
  )

初始化内部流程：

  init_process_group()（Python）
       │
       ▼
  _create_process_group()（Python → C++）
       │
       ▼
  ProcessGroupNCCL() 构造（C++）
       │
       ├─→ connect Store（连接主节点的 TCPStore）
       │
       ├─→ exchange Rank（交换 rank / world_size / UUID）
       │
       ├─→ 获取 NCCL Unique ID（从 rank 0 广播）
       │
       └─→ ncclCommInitRank() 建立 NCCL Communicator
       │
       ▼
  完成——所有 rank 可以开始集合通信

启动分布式训练的 3 种方式：

方式 适用 命令
torchrun（推荐） 单节点多卡 / 多节点多卡 torchrun --nproc_per_node=8 train.py
torch.distributed.launch（老） 旧脚本 已弃用
MPI Launcher HPC 集群 mpirun -n 16 python train.py

最小启动示例：

import torch
import torch.distributed as dist

# 初始化进程组（每个进程都要调用一次）
dist.init_process_group(
    backend="nccl",            # GPU 用 nccl；CPU 用 gloo
    init_method="env://",      # 用环境变量 WORLD_SIZE / RANK / MASTER_ADDR
)

# 每个进程知道自己是谁
rank = dist.get_rank()          # 0, 1, 2, ..., world_size-1
world_size = dist.get_world_size()

# 集合通信原语
t = torch.zeros(1).cuda()
dist.all_reduce(t, op=dist.ReduceOp.SUM)   # 全局求和
dist.broadcast(t, src=0)                    # 从 rank 0 广播
dist.barrier()                              # 同步所有进程

dist.destroy_process_group()
通信原语速查
AllReduce       所有 rank 的张量聚合后每个 rank 都得到结果（梯度聚合）
AllGather       每个 rank 收集所有 rank 的张量（参数分片拼回）
ReduceScatter   把张量分片分发到对应 rank（分片释放）
Broadcast       从一个 rank 向所有 rank 广播
All-to-All      每个 rank 都跟其他 rank 交换数据（MoE 路由）
Send/Recv       点对点通信（流水线并行）
Barrier         全局同步点

5.3. Store——节点发现服务

所有 GPU 一开始互相不知道对方在哪台机器、用什么 IP、什么端口。

Store = 分布式协调服务，负责：
  1. 节点发现（谁在哪）
  2. 共享元数据（NCCL Unique ID / rank / world_size）
  3. 分布式 barrier（让所有 rank 知道"大家都准备好了"）

支持的 Store 类型：

Store 类型 用途 持久化
TCPStore 默认选项，rank 0 启动 TCP server 内存
FileStore 通过共享文件系统（NFS）交换 文件
HashStore 单机测试 内存
EtcdStore Elastic 训练场景 外部 etcd 集群

环境变量驱动示例（最常用）：

# rank 0 节点（master）
export MASTER_ADDR=10.0.0.1
export MASTER_PORT=29500
export WORLD_SIZE=16
export RANK=0
export LOCAL_RANK=0
torchrun --nproc_per_node=8 train.py

# rank 8 节点
export MASTER_ADDR=10.0.0.1
export MASTER_PORT=29500
export WORLD_SIZE=16
export RANK=8
export LOCAL_RANK=0
torchrun --nproc_per_node=8 train.py

Store 启动流程：

  rank 0（master）
       │
       ▼
  TCPStore.listen()
       │
       │ 监听 10.0.0.1:29500
       │
       ▼
  等待其他 rank 连接
       │
       │  rank 1, rank 2, ..., rank 15
       │  各自 connect(10.0.0.1:29500)
       │  写入自己的 rank / local_rank
       │
       ▼
  交换 NCCL Unique ID（一个 128 字节的 UUID）
       │
       ▼
  所有 rank 拿到相同的 Unique ID
       │
       ▼
  ncclCommInitRank(uniqueId, rank, worldSize)
       │
       ▼
  完成——可以开始 AllReduce / Broadcast

5.4. ProcessGroup——核心通信抽象

ProcessGroup = 一组协同工作的进程 + 一组通信原语。

抽象类层级：

  ProcessGroup（C++ 抽象基类）
       │
       ├── ProcessGroupNCCL      ← NVIDIA GPU（主用）
       ├── ProcessGroupGloo      ← CPU 跨机
       ├── ProcessGroupMPI       ← HPC
       └── ProcessGroupUCC       ← 统一集合通信（CXL / SHARP）

每个 ProcessGroup 提供：
  - all_reduce()
  - all_gather()
  - reduce_scatter()
  - broadcast()
  - all_to_all()
  - send() / recv()
  - barrier()

不同 Backend 实现不同：
  ProcessGroupNCCL::all_reduce()  →  ncclAllReduce()
  ProcessGroupGloo::all_reduce()  →  TCP Socket
  ProcessGroupMPI::all_reduce()   →  MPI_Allreduce()

# 创建自定义 ProcessGroup
group_a = dist.new_group([0, 1, 2, 3])        # 4 个 rank 一个组
group_b = dist.new_group([4, 5, 6, 7])        # 另 4 个 rank 一个组
world = dist.group.WORLD                        # 全部 rank

# 在特定 group 中做集合通信
dist.all_reduce(tensor, group=group_a)
dist.broadcast(tensor, src=0, group=group_a)

PyTorch Distributed 本身并不理解"TP"、"PP"、"DP"、"EP"——它只提供"创建任意 ProcessGroup"的机制。"这些组代表什么"由上层框架（Megatron / DeepSpeed / FSDP）决定。

5.5. Work 对象与异步通信

PyTorch Distributed 的所有集合通信都是异步的。

调用时：
  work = dist.all_reduce(tensor, async_op=True)

不阻塞，返回 Work 对象。

等需要时：
  work.wait()    # 阻塞直到完成
  # 或者用 work.result() / work.is_completed()

Work 对象内部：

  ProcessGroup::Work（C++ 抽象基类）
       │
       ├── 内部状态
       │     ├── CUDA Event（GPU 完成事件）
       │     ├── CUDA Stream（GPU 流）
       │     └── Future（C++ promise/future）
       │
       ├── 同步原语
       │     ├── wait()        阻塞
       │     ├── is_completed()  非阻塞查询
       │     └── result()      获取结果
       │
       └── 异常处理
             └── exception()  获取异常

异步的好处：

  Forward 计算（GPU）
       │
       ├────► 立刻触发梯度 AllReduce（异步）───► 通信后台进行
       │
       ├────► 立刻启动下一轮 Forward（GPU 不阻塞）
       │
       └────► 通信完成时 GPU 已算完下一轮前向（计算与通信 overlap）

5.6. Reducer——DDP 梯度同步核心

DDP（DistributedDataParallel）的最大核心 = Reducer。

Reducer 负责：
  1. 注册 autograd hook 到每个参数的梯度
  2. 收集梯度到 Bucket（桶）
  3. Bucket 满了自动触发 AllReduce
  4. 支持计算-通信 overlap

Bucket 设计：
  ├─ Bucket1：约 25 MB 梯度
  ├─ Bucket2：约 25 MB 梯度
  └─ Bucket3：约 25 MB 梯度

梯度不是一个一个同步——而是 Bucket 满了就一起 AllReduce。

DDP 反向传播时序：

  loss.backward()
       │
       ▼
  Autograd 反向遍历计算图
       │
       ▼
  某个参数的梯度产生
       │
       ▼
  Autograd Hook 触发（Reducer 注册）
       │
       ▼
  梯度进入对应 Bucket
       │
       │  Bucket 满？
       │   ├─ 否 → 等更多梯度
       │   └─ 是 → 立即触发 AllReduce
       ▼
  ProcessGroupNCCL::allreduce(bucket_gradients)
       │
       ▼
  所有 rank 的 Bucket 梯度一致
       │
       ▼
  Optimizer.step() 在本地更新参数（每 rank 独立）

Reducer 关键优化：

1. 计算-通信 overlap
   Bucket 反向算完 → 立刻 AllReduce（不等所有 Bucket）
   通信与剩余梯度计算同时进行

2. Bucket 大小可调
   DDP 默认 25 MB
   太小：通信次数多，开销大
   太大：通信延迟长
   经验：~10-50 MB

3. Gradient bucketing 按反序
   反向传播最后产生的梯度（靠近 loss）先 AllReduce
   因为这些梯度最慢算完，先发出去

5.7. 通信流程——以 AllReduce 为例

以 8 张 GPU 做 AllReduce 为例（每张卡 100 MB 梯度）：

  GPU0  GPU1  GPU2  GPU3  GPU4  GPU5  GPU6  GPU7
  100M  100M  100M  100M  100M  100M  100M  100M
   │     │     │     │     │     │     │     │
   └─────┴─────┴─────┴─────┴─────┴─────┴─────┘
                          │
                  ProcessGroup::collective()
                          │
                          ▼
                 ProcessGroupNCCL
                          │
                          ▼
                  ncclAllReduce()
                          │
                          ▼
                 NCCL Ring Algorithm
                          │
        ┌─────────────────┴─────────────────┐
        │                                   │
   ReduceScatter                       AllGather
   (按 rank 切分结果)                  (把分片发给所有 rank)
        │                                   │
        └─────────────────┬─────────────────┘
                          │
                          ▼
   GPU0  GPU1  GPU2  GPU3  GPU4  GPU5  GPU6  GPU7
   100M  100M  100M  100M  100M  100M  100M  100M
   ↑     ↑     ↑     ↑     ↑     ↑     ↑     ↑
   每张卡都有完整的 100M 平均梯度

NCCL Ring AllReduce 算法：

把 8 张 GPU 排成一个环：

  GPU0 → GPU1 → GPU2 → GPU3 → GPU4 → GPU5 → GPU6 → GPU7 → GPU0

Phase 1: ReduceScatter（7 步）
  每步：每张卡把 1/8 数据发给下一个邻居，收到上一个邻居的 1/8 数据
  累加后，结束时每张卡持有"全和的 1/8"

Phase 2: AllGather（7 步）
  每张卡把"全和的 1/8"广播给下一个邻居
  最终所有卡都有完整的 8/8 = 全和

总通信量 = 2 × (N-1)/N × S ≈ 2S（N=8, S=100M → 200M 传输）
比朴素"每张卡发给所有其他卡"的 N² 量级节省 N-1 倍

5.8. Backend 对比（NCCL / Gloo / MPI / UCC）

Backend 厂商 支持硬件 适用场景 性能
NCCL NVIDIA NVIDIA GPU 几乎所有 LLM 训练 ★★★★★
Gloo Meta（PyTorch） CPU（x86 / ARM） 调试 / 小规模 CPU 训练 ★★
MPI 开源（OpenMPI / MPICH） HPC 集群 传统 HPC 集成 ★★★★
UCC 开源 UCX / SHARP / ROCm 多后端统一（CXL / 异构） ★★★

各 Backend 详解：

NCCL（NVIDIA Collective Communications Library）：
  - 专为 NVIDIA GPU 优化的集合通信库
  - 支持：NVLink / PCIe / InfiniBand / RoCE / GPUDirect RDMA
  - 优化：Ring AllReduce / Tree AllReduce / NVLink-aware 拓扑调度
  - 限制：只支持 NVIDIA GPU

Gloo：
  - Meta 开发的 CPU 集合通信库
  - 支持：TCP / InfiniBand（verbs）
  - 主要用途：CPU 调试 / 小规模训练 / Elastic 场景
  - GPU 性能远不如 NCCL

MPI（OpenMPI / MPICH / Intel MPI）：
  - HPC 标准接口
  - 通过 mpirun / srun 启动
  - 优点：跨厂商支持（HPE Cray / SGI / 国产超算）
  - 缺点：与 PyTorch 集成较 NCCL 复杂

UCC（Unified Collective Communication）：
  - 新一代统一集合通信
  - 后端：UCX / SHARP / ROCm
  - 特点：CXL 支持（跨服务器内存语义）
  - 未来跨硬件趋势

5.9. Elastic——弹性训练 + torchrun

传统分布式训练：
  启动时 8 卡 → 必须始终 8 卡 → 任何 1 卡挂了就失败

Elastic 训练：
  启动时 8 卡 → 挂 1 卡 → 自动恢复 → 继续训练
  训练规模可动态伸缩（8 → 16 → 8 卡）

torchrun 启动示例：

torchrun \
    --nnodes=2:4 \                       # 最小 2 节点，最大 4 节点
    --nproc_per_node=8 \                 # 每节点 8 进程
    --rdzv_id=123 \                      # 任务 ID
    --rdzv_backend=c10d \                # Rendezvous 后端
    --rdzv_endpoint=master:29500 \       # Rendezvous 端点
    train.py

Elastic 内部组件：

  ┌─────────────┐

5.10. DeviceMesh 与 DTensor（PyTorch 2.x 新能力）

DeviceMesh = 多维设备网格（用于描述复杂并行拓扑）
DTensor = 带分片元信息的分布式张量

这是 PyTorch 2.x 之后的统一分布式张量模型——把"张量如何分布在多卡"作为张量的元信息，而不是由用户手动管理。

DeviceMesh 示例：

from torch.distributed.device_mesh import DeviceMesh

# 创建二维 mesh（2 × 4 = 8 GPU）
mesh = DeviceMesh(
    "cuda",
    [[0, 1, 2, 3],
     [4, 5, 6, 7]]
)

# 第一维（mesh dim 0）= Tensor Parallel（每行 4 卡）
# 第二维（mesh dim 1）= Pipeline Parallel（每列 2 卡）

# 还可以加上第三维 = Data Parallel
mesh_3d = DeviceMesh(
    "cuda",
    [[[0,1,2,3], [4,5,6,7]],     # replica 0
     [[8,9,10,11], [12,13,14,15]]]  # replica 1
)
# 含义：2 DP × 2 PP × 4 TP = 16 GPU

DTensor 示例：

from torch.distributed.tensor import DTensor, Shard, Replicate

# 普通张量：每个 rank 各持一份
t = torch.randn(8, 8)

# 分布式张量：第 0 维切分到 mesh dim 0
dt = DTensor.from_local(
    t,
    mesh,
    placements=[Shard(0)]    # 第 0 维切分到 mesh 的第 0 维（TP）
)

# 编译器 / 运行时自动插入必要的通信（AllGather / AllReduce）
# 用户无需手动管理

DeviceMesh 的设计目的：

传统方式：
  用户手动管理：
    tp_group = dist.new_group([0,1,2,3])
    pp_group = dist.new_group([0,4])
    dp_group = dist.new_group([0,4,8,12])
  → 容易出错、难以扩展

DeviceMesh：
  一次性定义多维拓扑
  每维自动创建对应的 ProcessGroup
  → FSDP2、TorchTitan 等新一代框架的基础

5.13. 多级与多维并行的支持

PyTorch Distributed 支持多种并行模式：

并行模式 支持方式 通信模式
跨多机（Multi-Node） init_process_group() 建立全局 ProcessGroup TCPStore + NCCL + InfiniBand
分层通信（Hierarchical） 多个 ProcessGroup + NCCL 拓扑感知 Local Reduce → Cross-Node → Local Broadcast
数据并行（DP） DDP / FSDP AllReduce / AllGather / ReduceScatter
张量并行（TP） 多个 TP ProcessGroup AllReduce / AllGather（每层结束）
流水线并行（PP） 多个 PP ProcessGroup Send / Recv（点对点）
专家并行（EP） 多个 EP ProcessGroup All-to-All（MoE 路由）
序列并行（SP） SP ProcessGroup AllGather / ReduceScatter（沿序列）

多层通信示例（分层 AllReduce）：

  Node1                              Node2
  GPU0 GPU1 GPU2 GPU3              GPU4 GPU5 GPU6 GPU7
    │    │    │    │                  │    │    │    │
    └────┴────┴────┘                  └────┴────┴────┘
              │                                │
        第一层（节点内 Reduce，NVLink 900 GB/s）│
              │                                │
              └──────── 第二层（跨节点 Reduce，InfiniBand 400 Gb/s） ─┘
                              │
              ┌──────── 第三层（节点内 Broadcast）────────┐
              │                                │
  GPU0 GPU1 GPU2 GPU3              GPU4 GPU5 GPU6 GPU7

优势：
  节点内通信用 NVLink（超快）
  跨节点只用 AllReduce 一次（小数据）
  比"全部卡一起 AllReduce" 节省大量跨节点流量

三维并行（目前 LLM 标配）：

  1024 GPU 训练 GPT：

    DP = 16
    TP = 8
    PP = 8
    16 × 8 × 8 = 1024 GPU

  每种都是一个独立的 ProcessGroup：

    world
    ├── DP Groups（16 组，每组 64 卡）
    │      └─ AllReduce（梯度聚合）
    │
    ├── TP Groups（128 组，每组 8 卡）
    │      └─ AllReduce / AllGather（矩阵切分）
    │
    └── PP Groups（128 组，每组 8 卡）
           └─ Send / Recv（层间通信）

  训练时三种通信同时发生：
    DP: AllReduce
    TP: AllGather / AllReduce
    PP: Send / Recv

MoE 的第四维（专家并行）：

  DeepSeek-V3 / Mixtral / Qwen3 MoE 等：

    DP = 16
    TP = 8
    PP = 4
    EP = 2
    16 × 8 × 4 × 2 = 1024 GPU

  四种 ProcessGroup 同时存在：
    DP 通信：AllReduce（梯度）
    TP 通信：AllGather（矩阵切分）
    PP 通信：Send / Recv（层间）
    EP 通信：All-to-All（Token 路由）

PyTorch Distributed 本身是否理解这些层级？

PyTorch Distributed 本身并不知道什么叫 TP、PP、DP、EP。

它只知道：

  tp_group = dist.new_group(tp_ranks)
  dp_group = dist.new_group(dp_ranks)
  pp_group = dist.new_group(pp_ranks)
  ep_group = dist.new_group(ep_ranks)

至于"这是张量并行？这是流水线？这是数据并行？这是专家并行？"——

都是 Megatron、DeepSpeed、FSDP、TorchTitan 等框架定义的语义。

5.14. 跨机器通信（Multi-Node）

PyTorch Distributed 从设计之初就是为了支持 Multi-Node + Multi-GPU 分布式训练。

例如：

  Machine A（192.168.1.10）
  ┌───────────────────────────┐
  │ GPU0 → rank0              │
  │ GPU1 → rank1              │
  │ GPU2 → rank2              │
  │ GPU3 → rank3              │
  └───────────────────────────┘

  Machine B（192.168.1.11）
  ┌───────────────────────────┐
  │ GPU0 → rank4              │
  │ GPU1 → rank5              │
  │ GPU2 → rank6              │
  │ GPU3 → rank7              │
  └───────────────────────────┘

  world_size = 8
  rank: 0~7

对 PyTorch 来说：它不关心 Rank0 和 Rank7 是否在同一台机器。

跨机器的通信路径：

  Machine A                         Machine B
  -----------                       -----------
  rank0                             rank4

  init_process_group()              init_process_group()

        │                                 │
        └────────────TCPStore─────────────┘
                     │
             MASTER_ADDR = 192.168.1.10
             MASTER_PORT = 29500
                     │
             交换 NCCL Unique ID
                     │
        ncclCommInitRank()
                     │
       建立 GPU Communicator
                     │
       AllReduce / Broadcast

  真正跨机器的是：Store + NCCL 通信

GPU 跨机器的物理路径：

  GPU0 (MachineA)
       │
       ▼
     NCCL
       │
       ▼
  InfiniBand HCA（Host Channel Adapter）
       │
       ▼
  InfiniBand 交换机
       │
       ▼
  InfiniBand HCA
       │
       ▼
     NCCL
       │
       ▼
  GPU0 (MachineB)

如果没有 InfiniBand：
  GPU → PCIe → CPU → TCP Socket → 另一台 CPU → PCIe → GPU
  也能通信（但慢 5~10 倍）

跨机器启动命令：

# Machine A（rank 0~7）
MASTER_ADDR=192.168.1.10
MASTER_PORT=29500
torchrun \
    --nnodes=2 \
    --node_rank=0 \
    --nproc_per_node=8 \
    train.py

# Machine B（rank 8~15）
MASTER_ADDR=192.168.1.10
MASTER_PORT=29500
torchrun \
    --nnodes=2 \
    --node_rank=1 \
    --nproc_per_node=8 \
    train.py

跨机器的支持范围：

理论上 PyTorch Distributed 支持任意数量的机器：

  2 Node × 8 GPU
  8 Node × 8 GPU
  64 Node × 8 GPU
  512 Node × 8 GPU
  1024 Node × 8 GPU

都能工作。

真正限制训练规模的是：
  1. 网络带宽（InfiniBand NDR 400 Gb/s 是底线）
  2. 网络拓扑（胖树 / Dragonfly+）
  3. NCCL 算法效率（节点数越多 collective 越慢）
  4. 集群调度能力（K8s / Slurm / Volcano）

GPT-3、Llama、Qwen、DeepSeek 等超大模型训练都是数百到数千张 GPU
跨多台服务器协同完成，底层通信仍依赖 PyTorch Distributed 与 NCCL。

跨机器通信的代码视角：

从程序角度看：跨机器与单机多卡完全一致。

例如：
  loss.backward()
  optimizer.step()

你的代码完全不用改。

DDP 会自动：
  GPU0 梯度 → AllReduce → GPU15 → 同步完成

开发者甚至不知道：
  GPU15 到底在本机还是在美国另一台服务器？
总结：PyTorch Distributed 的三层能力
1. 跨多机（Multi-Node）✅
   通过 init_process_group() + TCPStore 建立全局 ProcessGroup

2. 分层通信（Hierarchical）✅
   通过多个 ProcessGroup + NCCL 拓扑感知优化

3. 多维并行（DP × TP × PP × EP）✅
   通过 new_group()、DeviceMesh、DTensor 等抽象
   由上层框架（DeepSpeed / Megatron / FSDP）组织语义

因此 PyTorch Distributed 是一个"分布式通信运行时"——提供灵活的进程组管理与通信原语，真正的多级、多维并行策略由 DeepSpeed、Megatron-Core、FSDP、TorchTitan 等框架在其之上构建。

6. DeepSpeed——微软超大模型训练框架

DeepSpeed 由 Microsoft 推出，主打"用更少 GPU 训练更大模型"。
核心创新是 ZeRO（Zero Redundancy Optimizer）三阶段 + 各种 Offload。

6.1. ZeRO 三阶段

传统数据并行（DDP）的显存浪费：

每张 GPU 完整保存：
  参数（Params）        ← 模型权重
  梯度（Gradients）     ← 反向传播算出的
  优化器状态（Optimizer）← Adam 的 m / v 状态

以 Adam 训练 7B 模型为例（FP16 训练）：
  参数：       7B × 2 字节  = 14 GB
  梯度：       7B × 2 字节  = 14 GB
  优化器状态： 7B × 4 × 4    = 112 GB（FP32 m + FP32 v + FP32 master = 4×参数）

  单卡总计： 140 GB ← 根本装不下

ZeRO 的解决思路——把"重复数据"分片到不同卡：

阶段 分片内容 显存节省 通信开销 适用模型
ZeRO-1 仅优化器状态 ~4× 轻微 ≤ 13B
ZeRO-2 优化器状态 + 梯度 ~8× 中等 ≤ 40B
ZeRO-3 优化器状态 + 梯度 + 参数 ~N 倍（N = GPU 数） 较高 100B+
ZeRO-Infinity ZeRO-3 + 卸载到 NVMe 几乎无限 高 1T+

6.2. ZeRO-Offload 与 ZeRO-Infinity

ZeRO-Offload：
  把优化器状态 + 梯度从 GPU 卸载到 CPU 内存

  GPU 0                 CPU
  ┌─────────┐          ┌──────────────┐
  │ 参数    │          │ 优化器状态    │
  │ 激活    │          │ 梯度          │
  └─────────┘          └──────────────┘
       ↑ ↓ CPU↔GPU 数据搬运
  节省 GPU 显存 = CPU 内存通常 1~2 TB

ZeRO-Infinity：
  在 ZeRO-Offload 基础上再卸载到 NVMe SSD

  GPU ← CPU ← NVMe SSD
  总可用"显存"理论 = NVMe 容量（几十 TB）

6.3. DeepSpeed 其他特性

特性 作用
3D Parallelism DP + TP + PP 混合（与 Megatron 集成）
Pipeline Parallel 流水线并行（基于 PipeDream）
Activation Checkpointing 重计算：用时间换显存（前向时丢弃激活，反向时重算）
FP16 / BF16 / FP8 训练 混合精度支持
ZeRO++ ZeRO-3 的通信优化版本（减少跨机通信）
DeepSpeed-MoE MoE 训练支持

启动 DeepSpeed 训练：

    --deepspeed ds_config.json \
    --model_size 7B \
    --batch_size 32

  "gradient_accumulation_steps": 4,

7. Megatron-LM / Megatron-Core——NVIDIA GPT 训练

Megatron-LM 由 NVIDIA 推出，主打 GPT 类大模型的高效训练。
首创了张量并行（Tensor Parallel）+ 流水线并行（Pipeline Parallel）+ 序列并行（Sequence Parallel）。
2023 年起拆分为：
  Megatron-Core（库，核心并行实现）
       ↓
  NeMo（NVIDIA 官方框架，包装 Megatron-Core + 数据集 + Trainer）

7.1. 张量并行（Tensor Parallel）

原理：把单个矩阵乘法按行 / 按列切分到多卡

  原始矩阵 A × B（hidden × hidden）：
    A: [4096, 4096]    B: [4096, 4096]

  按列切 B（A 不切）：
    B = [B1 | B2 | B3 | B4]，每块 [4096, 1024]
    GPU0 算 A × B1
    GPU1 算 A × B2
    GPU2 算 A × B3
    GPU3 算 A × B4

  输出阶段：AllReduce 把 4 块结果拼起来

优点：
  - 每层都是细粒度并行，GPU 利用率高
  - 适合单节点多卡（NVLink 高速互联）

缺点：
  - 每层都要 AllReduce（通信密集）
  - 多节点时通信开销爆炸

7.2. 流水线并行（Pipeline Parallel）

原理：把模型的不同层放到不同卡

  32 层 Transformer：

  GPU0：Layer  0-7
  GPU1：Layer  8-15
  GPU2：Layer 16-23
  GPU3：Layer 24-31

  数据流水线：
    micro-batch 1:  GPU0 → GPU1 → GPU2 → GPU3
    micro-batch 2:          GPU0 → GPU1 → GPU2 → GPU3
    micro-batch 3:                  GPU0 → GPU1 → GPU2 → GPU3

优点：
  - 跨机友好（每层之间只需一次点对点通信）
  - 模型规模可扩展到千亿

缺点：
  - "流水线气泡"（bubble）—— 启动 / 收尾阶段 GPU 闲置
  - 需要复杂的 1F1B / Interleaved 调度

7.3. 序列并行（Sequence Parallel）

原理：在张量并行的基础上，把 LayerNorm / Dropout 这类"无大量矩阵乘"的算子沿序列维度再切

  张量并行只切"线性层"，但 LayerNorm / Dropout 在 TP 下每卡都重复算整序列
  → 浪费

  序列并行：把序列切成多段，每卡只算自己的段
  → 通信量减少 ~50%

7.4. 专家并行（Expert Parallel）

原理：MoE 训练时，把不同 Expert 放到不同卡

  8 个 Expert × 8 张卡：
    GPU0: Expert 0
    GPU1: Expert 1
    ...
    GPU7: Expert 7

  每个 Token 通过 Router 选 Top-K 专家
  → 用 All-to-All 通信把 Token 路由到对应卡

Megatron-Core 把 TP + PP + SP + EP 全部组合：
  1000+ GPU 训练 1T+ MoE 模型是它的强项

7.5. Megatron-Core vs NeMo

组件 职责 类比

8. FSDP——PyTorch 官方分片数据并行

FSDP = Fully Sharded Data Parallel
PyTorch 1.11+ 官方提供，是 DeepSpeed ZeRO-3 的 PyTorch 原生等价物。

8.1. FSDP vs DDP

DDP（普通数据并行）：
  每张卡保存完整模型
  通信：每步一次 AllReduce（聚合梯度）

  显存占用 = 模型大小 × GPU 数（重复）

FSDP：
  每张卡只保存模型分片
  通信：每步 AllGather（拼回参数）+ Forward + ReduceScatter（释放参数）

  显存占用 = 模型大小 / GPU 数（节省 N 倍）

8.2. FSDP 工作流程

以 4 张卡训练 7B 模型为例：

  初始状态：
    GPU0: Layer 0, 4     (1/4 参数)
    GPU1: Layer 1, 5     (1/4 参数)
    GPU2: Layer 2, 6     (1/4 参数)
    GPU3: Layer 3, 7     (1/4 参数)

  前向（Forward）：
    1. AllGather 把需要的参数从其他卡拉到本地（拼完整层）
    2. 正常前向计算
    3. 计算完立即释放（参数回到分片状态）

  反向（Backward）：
    1. AllGather 重新拼参数
    2. 反向计算梯度
    3. ReduceScatter 把梯度分片释放到对应卡（自己持有 1/N 梯度）

  Optimizer.step：
    每张卡只更新自己持有的 1/N 参数

8.3. FSDP 使用示例

import torch
from torch.distributed.fsdp import FullyShardedDataParallel as FSDP
from torch.distributed.fsdp import MixedPrecision, BackwardPrefetch

# 初始化进程组
torch.distributed.init_process_group(backend="nccl")

# FSDP 配置
fsdp_config = {
    "mixed_precision": MixedPrecision(
        param_dtype=torch.bfloat16,
        reduce_dtype=torch.bfloat16,
        buffer_dtype=torch.bfloat16,
    ),
    "backward_prefetch": BackwardPrefetch.BACKWARD_PRE,
    "forward_prefetch": True,
    "limit_all_gathers": True,
    "use_orig_params": True,
}

# 包装模型
model = MyModel()  # 原始 nn.Module
model = FSDP(
    model,
    **fsdp_config,
    cpu_offload=CPUOffload(offload_params=True),  # 可选：参数卸载到 CPU
)

# 训练循环（与 DDP 完全一致）
for batch in dataloader:
    optimizer.zero_grad()
    loss = model(batch)
    loss.backward()
    optimizer.step()

FSDP2（PyTorch 2.4+）：更灵活的 per-parameter 分片：

from torch.distributed.fsdp import fully_shard

model = MyModel()

    fully_shard(layer)              # 逐层分片

11. 推理框架的设计目标

训练关心"算力"，推理关心"显存带宽 + KV Cache 管理"。

推理框架的关键指标：
  1. Throughput（吞吐量）  — 多少 token / 秒
  2. Latency（延迟）        — 单请求 TTFT（首 token 时间）+ TPOT（每 token 时间）
  3. KV Cache 利用率        — 多请求并发时显存不要碎掉
  4. Continuous Batching    — 不必等所有请求完成就能塞新请求
  5. Kernel 启动开销        — 减少 CPU ↔ GPU 调度

11.1. 推理优化的关键技术

技术 解决的问题 代表实现
KV Cache 避免每步重新算 K/V 所有推理框架
PagedAttention KV Cache 显存碎片 vLLM
Continuous Batching 动态 batch vLLM / TGI / TensorRT-LLM
Prefix Cache 共享 prompt 前缀 vLLM / SGLang
Speculative Decoding 小模型预生成大模型验证 vLLM / TensorRT-LLM
Kernel Fusion 多个算子合一 TensorRT-LLM
Quantization（INT8/INT4/FP8） 降低显存 + 加速 TensorRT-LLM / vLLM
Tensor Parallel 单卡装不下时跨卡 所有
Chunked Prefill 长 prompt 不阻塞短请求 SGLang / vLLM
推理与训练的根本差异

训练 = 把 Loss 降下来（计算密集 + 通信密集）
推理 = 把 Token 吐出来（访存密集 + 调度密集）

因此训练用 AllReduce 多，推理用自定义 attention kernel + KV cache 管理多。

12. vLLM——PagedAttention 革新者

vLLM 由 UC Berkeley Sky Computing Lab 推出（2023-2024），目前是工业部署的事实标准。
核心创新：PagedAttention——把操作系统的"虚拟内存分页"思想搬到 KV Cache 管理。

12.1. 传统 KV Cache 的问题

传统实现：
  每个请求预分配一段连续显存
  Prompt 长度不可预测（1 ~ 128K）
  → 必须按最大长度预分配
  → 实际只用 30% 长度 → 70% 浪费
  → 长 prompt 抢光显存，短请求无空间

显存碎片：
  GPU Memory
  ┌────────┬──────┬──────────┐
  │Req A 80│空 5  │Req C 200 │
  │用 80   │碎片   │用 200    │
  └────────┴──────┴──────────┘
  → 碎片无法被利用，浪费 5 + 中间缝隙

12.2. PagedAttention 解决思路

借鉴操作系统虚拟内存分页：

  把 KV Cache 切成固定大小的"Page"（通常 16 个 token 一页）
  每个请求的 KV 不再需要连续显存

  GPU Memory
  ┌──────┬──────┬──────┬──────┐
  │Page 0│Page 1│空    │Page 2│
  └──────┴──────┴──────┴──────┘
       ↑          ↑      ↑
     Req A      闲置  Req A（不连续）

  维护"页表"（Page Table）：逻辑块 → 物理块 的映射

  优势：
    - 显存利用率从 ~30% → ~95%
    - 显存碎片几乎为 0
    - 请求并发数提升 2~4 倍
    - Prefix Cache 复用更高效

特性 说明

13. TensorRT-LLM——NVIDIA Kernel Fusion 极致优化

NVIDIA 官方推理引擎，主打"把每一毫秒都榨干"。
核心思路：把所有算子预先编译 + 融合成一个大 Kernel。

13.1. Kernel Fusion 示例

传统实现（多个 Kernel 串行）：

  Linear → Bias → GELU

  GPU 上：
    Kernel 1: Linear (matmul)
    Kernel 2: Bias add
    Kernel 3: GELU activation

  每个 Kernel 启动 ~5~10 微秒开销
  → 3 个 Kernel = 15~30 微秒浪费

TensorRT-LLM 优化后：

  Linear + Bias + GELU → 单个融合 Kernel

  一次 Kernel 启动 = 5~10 微秒
  → 节省 10~20 微秒 / 层

  32 层模型 × 节省 15 微秒 = 0.5 ms / token
  → 看似微小，但每秒数千 token 时累积可观

13.2. TensorRT-LLM 其他特性

特性 说明

KV Cache 优化 自定义 KV layout
INT8 / FP8 量化 SmoothQuant / FP8 / INT4

22. 学习路径建议

系统学习分布式训练的顺序
1. PyTorch Distributed (c10d)
   └─ 理解 ProcessGroup / NCCL Backend / 集合通信原语

2. DDP（DistributedDataParallel）
   └─ 最简单的数据并行，掌握梯度 AllReduce

3. FSDP（FullyShardedDataParallel）
   └─ 模型分片数据并行，ZeRO-3 等价

4. ZeRO（DeepSpeed）
   └─ ZeRO-1/2/3 + Offload + Infinity

5. Tensor Parallel（Megatron-LM）
   └─ 矩阵切分 + 列并行 + 行并行

6. Pipeline Parallel
   └─ GPipe / PipeDream / 1F1B 调度

7. Sequence Parallel
   └─ LayerNorm / Dropout 沿序列切分

8. Expert Parallel（MoE）
   └─ All-to-All 路由

9. NCCL / RCCL / HCCL 通信机制
   └─ Ring AllReduce / Tree AllReduce / NVLink vs IB

学完训练后再学推理会事半功倍：

10. vLLM
    └─ PagedAttention + Continuous Batching

11. TensorRT-LLM
    └─ Kernel Fusion + In-flight Batching

12. SGLang
    └─ RadixAttention + Structured Generation

13. llama.cpp + Ollama
    └─ 本地部署 / GGUF 格式
