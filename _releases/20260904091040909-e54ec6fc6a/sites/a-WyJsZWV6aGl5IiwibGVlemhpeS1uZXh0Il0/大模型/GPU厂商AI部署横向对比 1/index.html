本文回答三个核心问题：

  1. 三家 GPU 在 K8s 里资源名是什么（nvidia.com/gpu / amd.com/gpu / gpu.intel.com/i915 / gpu.intel.com/xe）？

tab:核心观察

维度 观察
应用层覆盖 NVIDIA 一家最全（PyTorch / TF / vLLM / Triton 主流全面支持）；国产卡普遍差在 vLLM（昇腾 / 寒武纪有 fork），Triton 几乎只 NVIDIA 完整支持
计算库层 国产每家都有自家通信库（HCCL/CNCL/MCCL/MXCCL……），性能与 NCCL 持平；但跨平台兼容差
编程模型层 国产普遍模拟 CUDA API（HIP、MUSA、MXMACA 是直接的；BANG C、TPR 是自研）；迁移 CUDA 代码工量由低到高：海光（MUSA 类似） < 沐曦（MXMACA 友好） < 昇腾（CANN 重构） < 寒武纪 / 燧原（最远）
运行时层 仍是 NVIDIA 有最统一抽象层；AMD / 国产 普遍需要用户手动映射
驱动层 NVIDIA 内核模块 ≈ 30 个 .so（最重）；国产普遍追求"一个 .ko 搞定一切"（HW 复杂度低 + 维护成本压力）
硬件层 NVIDIA 用 NVLink/NVSwitch，国产普遍用 HCCS / HCCN / 自研互联；海光用类 Infinity Fabric

3.2. 关键观察：NVIDIA 比 AMD/Intel 多一层

NVIDIA 链路：
  App → cuDNN → CUDA Runtime → nvidia.ko → 硬件
                          ↑
                  容器 runtime 自动注入（自动化）

AMD / Intel 链路：
  App → MIOpen/oneDNN → HIP/LevelZero → /dev/kfd / /dev/dri → amdgpu.ko / i915.ko → 硬件
                                  ↑
                          手动设备直通（无统一抽象，需要手动挂设备）
本质差异

NVIDIA 的 CUDA Runtime 是统一抽象层——所有上层（cuDNN/PyTorch/Triton）都通过这一层访问 GPU，容器 runtime 可以自动注入完整运行时。

AMD / Intel 没有等价的统一抽象层——容器只能通过设备文件直通（/dev/kfd /dev/dri）让应用直接访问硬件，部分应用需要自己挂驱动库。

3.3. 核心结论：K8s 不懂 GPU

K8s 本身只是一个"通用资源调度系统"——它认识 cpu / memory / storage，
不认识 GPU。

GPU 对 K8s 来说，只是 "extended resource"（扩展资源）：

  nvidia.com/gpu           ← NVIDIA 注册
  amd.com/gpu              ← AMD 注册
  gpu.intel.com/i915       ← Intel 注册（i915 KMD）
  gpu.intel.com/xe         ← Intel 注册（xe KMD，新）

谁注册？→  Device Plugin（每家厂商各写一个）
怎么分配？→  Linux cgroup + device mount + OCI runtime
本文核心问题

7.6. K8s 资源分配的本质

K8s 不懂 GPU

K8s 认识的扩展资源是 nvidia.com/gpu / amd.com/gpu / gpu.intel.com/i915，它不知道这些字符串背后是什么硬件。

K8s 只做三件事：

  1. 调度：找到 nvidia.com/gpu.allocatable >= 1 的节点
  2. 调用：kubelet 调用对应厂商的 device plugin Allocate()
  3. 传递：把 device plugin 返回的 devices / envs / mounts 传给容器 runtime

真正的 GPU 分配由 Linux 内核 + device plugin + OCI runtime 完成。

8. K8s GPU 调度全链路深度

8.1. K8s 的设计哲学：只调度，不分配

K8s = 通用资源调度系统
Device Plugin = 资源解释器（硬件 ↔ K8s extended resource）
cgroup = Linux 资源隔离机制
device mount = 设备文件挂载

四者协作完成 GPU 分配：
K8s 调度 → kubelet → Device Plugin → Linux cgroup + mount → 容器

8.2. Device Plugin 的工作内容

1. 启动时扫描 /dev 下的 GPU 设备
   - NVIDIA: /dev/nvidia0, /dev/nvidia1, ...
   - AMD:    /dev/kfd, /dev/dri/renderD128, ...
   - Intel:  /dev/dri/renderD128, ...

2. 向 kubelet 上报资源（ListAndWatch gRPC）
   "我这里有 4 个 nvidia.com/gpu"

3. 响应 kubelet 的 Allocate() 调用
   "给这个 Pod 分配 1 个 GPU UUID-xxx"
   返回：devices[] + mounts[] + envs[] + annotations[] + CDI spec

4. （可选）PreStartContainer：在容器启动前做最后准备

8.3. 调度阶段（kube-scheduler）

Pod spec: nvidia.com/gpu: 1
                ↓

                ↓
Scheduler 选中节点 A
                ↓
Pod 绑定到节点 A（写入 .spec.nodeName）

kubelet 检测到 Pod 有 nvidia.com/gpu: 1

kubelet → device plugin: Allocate(1 GPU)

10. 三大厂商隔离机制对比

10.1. NVIDIA：CUDA Runtime 抽象 + UUID 精确分配

分配模型：精确到 GPU UUID
┌──────────────────────────────────────────────┐
│  Pod 1  →  GPU-uuid-A                       │
│  Pod 2  →  GPU-uuid-B                       │
│  Pod 3  →  GPU-uuid-C (MIG 1g.5gb instance) │
└──────────────────────────────────────────────┘
                  ↓
       libcuda.so / CUDA Runtime 过滤
                  ↓
        容器内只看到"被分配的设备"

特性：

  • 硬件级 MIG 切分（A100/H100，最多 7 个 instance）
  • CUDA_VISIBLE_DEVICES 机制：应用层用这个环境变量过滤
  • UUID 精确绑定：device plugin 跟踪每个 GPU 的 UUID
  • NVLink/NVSwitch 拓扑感知：调度器可感知 NVLink 连接
  • time-slicing 软切分：一张卡可被多个 Pod 共享（算力分时）

10.2. AMD：/dev/kfd + /dev/dri 设备直通

分配模型：设备文件直通（无中间抽象）
┌──────────────────────────────────────────────┐
│  Pod 1  →  /dev/kfd + /dev/dri/renderD128  │
│  Pod 2  →  /dev/kfd + /dev/dri/renderD129  │
│  Pod 3  →  ??? （没有 fine-grained 隔离）   │
└──────────────────────────────────────────────┘
                  ↓
       HIP / MIOpen 直接操作硬件

特性：

  • 无硬件级切分（无 MIG 等价物）
  • 注意：强隔离 = 整卡独占（K8s 一个 Pod 占用一张卡）
  • 注意：无 CUDA_VISIBLE_DEVICES 等价物（HIP 用 HIP_VISIBLE_DEVICES，但应用支持度差）
  • Infinity Fabric 多卡互联（MI250/MI300）
  • 注意：没有 time-slicing 软切分（device plugin 不支持）

10.3. Intel：/dev/dri render node

分配模型：render 节点 + shared-dev-num
┌──────────────────────────────────────────────┐
│  Pod 1  →  /dev/dri/renderD128              │
│  Pod 2  →  /dev/dri/renderD128 (shared)     │
│  Pod 3  →  /dev/dri/renderD129              │
│            ↑                                 │
│   shared-dev-num=2 时可共享同一节点          │
└──────────────────────────────────────────────┘
                  ↓
   Level Zero / oneAPI / OpenVINO

特性：

  • 注意：shared-dev-num 参数：N 个容器可共享同一 render 节点
  • 无硬件 MIG 等价（Xe 架构 HBM 切分有限）
  • ZE_AFFINITY_MASK 机制：Level Zero 层面的设备过滤
  • 注意：集成 GPU 与独显不同：集成 GPU（i915）和独显（xe KMD）管理路径不同
  • SR-IOV 支持：by-path 模式可挂载特定 VF

10.4. 为什么 AMD / Intel 没有 CUDA_VISIBLE_DEVICES 这种机制？

CUDA_VISIBLE_DEVICES 是 CUDA Runtime 提供的"应用层过滤器"——
它让一个进程"只看到部分 GPU"，但底层 GPU 仍可被其他进程访问。

它依赖的条件：
1. 应用通过 CUDA Runtime 访问 GPU（而不是直接 /dev/nvidia0）
2. CUDA Runtime 拦截 cuInit() 时读环境变量，过滤可见设备
3. 设备 plugin 配合设置环境变量

NVIDIA 的链路天然满足：
  App → cuDNN → CUDA Runtime → Driver
                ↑
         可被环境变量拦截（机制可工作）

AMD 的链路：
  App → MIOpen → HIP → /dev/kfd
                       ↑
               直接设备文件，无法拦截（无应用层 hook）

  HIP 有 HIP_VISIBLE_DEVICES，但应用支持度低（PyTorch 需特殊编译）

Intel 的链路：
  App → oneDNN → Level Zero → /dev/dri/renderD128
                                      ↑
                            直接设备文件，无法拦截（无应用层 hook）

  Level Zero 有 ZE_AFFINITY_MASK，但应用支持度低
一句话总结

CUDA_VISIBLE_DEVICES 的"魔法"在于 CUDA Runtime 这层抽象。
NVIDIA 把这层做成标准库 + shim，container 注入它就生效。
AMD/Intel 没有等价的统一 shim，只能靠设备文件直通——所以没有这种"应用层伪装"机制。

11. K8s Device Plugin gRPC 全链路

11.1. 5 个 gRPC 方法

K8s Device Plugin 框架定义了 5 个 gRPC 方法（官方文档）：

方法 方向 作用
GetDevicePluginOptions kubelet → plugin 询问 plugin 自己的选项（如是否需要 PreStartContainer）
ListAndWatch kubelet → plugin（流） plugin 持续上报当前节点的 GPU 列表 + 健康状态
Allocate kubelet → plugin 申请 N 个 GPU，返回 devices / mounts / envs / CDI spec
GetPreferredAllocation kubelet → plugin（可选） 调度器请求"推荐分配哪些设备"（用于 NUMA 感知）
PreStartContainer kubelet → plugin（可选） 容器启动前最后准备（清理残留状态等）

11.2. ListAndWatch 流程

1. device plugin 启动
2. 扫描 /dev 下 GPU 设备
   - NVIDIA: 调 NVML → GPU 列表（含 UUID、PCI Bus ID、显存）
   - AMD:    调 KFD API → GPU 列表
   - Intel:  调 DRM API → render 节点列表
3. 建立 gRPC server（默认监听 /var/lib/kubelet/device-plugins/<plugin>.sock）
4. kubelet 通过 Unix socket 连接
5. kubelet 调用 ListAndWatch()，plugin 返回初始 GPU 列表
6. plugin 进入"watch"模式：GPU 状态变化时主动推送
   - 健康状态变化（nvidia-smi 报 unhealthy）
   - 设备增删（热插拔）

11.3. Allocate 流程

1. Pod 调度到节点，kubelet 发现 resources.limits.nvidia.com/gpu: 1
2. kubelet 从缓存中取可用 GPU UUID
3. kubelet 调用 device plugin 的 Allocate() gRPC
4. device plugin 返回 AllocateResponse：
   {
     "container_responses": [
       {
         "devices": [
           {"device_paths": ["/dev/nvidia0"], "container_path": "/dev/nvidia0", "permissions": "rw"}
         ],
         "mounts": [{"host_path": "/usr/lib/.../libcuda.so", "container_path": "..."}],
         "envs": [{"name": "NVIDIA_VISIBLE_DEVICES", "value": "GPU-uuid-xxx"}]
       }
     ]
   }
5. kubelet 写 cgroup + 准备 device mount
6. kubelet 调用 CRI（containerd）创建容器
7. 容器启动时，runtime 挂载设备 + 库

11.4. PreStartContainer（可选）

NVIDIA 的 PreStartContainer 做什么？

1. 清理残留 CUDA context（防止上一个 Pod 留下状态）
2. 验证分配给 Pod 的 GPU 仍可用
3. （MIG 场景）确认 MIG instance 健康

调用时机：
  kubelet 启动容器前
  ↓
  PreStartContainer(ContainerStartRequest)
  ↓
  device plugin 做最后检查
  ↓
  返回 OK
  ↓
  容器真正启动

21. HAMi 统一调度框架（异构 GPU 共享调度）

本章核心问题

前面 §16-§20 我们把每家国产 GPU 都"按厂商"单独讲了一遍——每家都有自己的 Device Plugin / Docker Runtime / 监控采集器。问题来了：当你一个集群里同时有 NVIDIA + 华为昇腾 + 寒武纪 + 海光等多家设备，能不能用一套统一调度语义管起来？

HAMi（Heterogeneous AI Computing Virtualization Middleware）就是答案。

本章所有子章节默认折叠（Obsidian callout）——按需点开。

21.1 什么是 HAMi

HAMi（原名 k8s-vgpu-scheduler）是 CNCF Sandbox 项目（github.com/Project-HAMi/HAMi），目标是：

把异构 AI 算力（GPU / NPU / MLU / DCU / XPU）当作一类资源，用同一套调度语义 + 同一组 API 暴露给业务方，并在硬件层做显存/MIG/算力切分。

它不是各家 Device Plugin 的替代品——而是坐在 Device Plugin 之上的统一调度层：

  • 下层：仍然依赖每家厂商自己的 Device Plugin 把硬件注册为 K8s 扩展资源（nvidia.com/gpu、huawei.com/Ascend910、cambricon.com/mlu……）
  • 上层：通过 Scheduler Extender（调度打分）+ Mutating Webhook（容器注入）+ 虚拟化层（显存/算力切分），让业务方只写一种声明就能申请任意厂商的算力
HAMi vs 手写多个 Device Plugin
维度 手写多家 Device Plugin 用 HAMi
Resource name 每家不同（nvidia.com/gpu、huawei.com/Ascend910、cambricon.com/mlu……） 业务方只用 hami.dev/gpu + 厂商标签
GPU 切分 NVIDIA time-slicing、AMD 不支持、Intel shared-dev-num 各家语义不同 统一语义（--memory + --cores）
显存限制 没有（Pod 拿到一整张卡） 强制限制（--hami.dev/gpu-memory=8192）
调度均衡 简单 first-fit 调度打分（拓扑亲和、碎片整理、显存对齐）
多卡通信 各家 env（HCCL/CNCL/MCCL……）不同 Mutating Webhook 自动注入
工具链 要写一堆 Pod spec 一套 yaml 跨厂商可移植
核心结论

HAMi = 异构 GPU 的 "vSphere + vGPU"。 它解决的不是 "能不能用 GPU"，而是 "能不能 细粒度、可观测、可调度、可移植 地用 GPU"。

四个核心组件
  1. HAMi-Scheduler（Scheduler Extender）：以 Webhook 方式接入 K8s 默认调度器，承担"打分 + 优选"逻辑。判断节点分数、显存碎片、亲和性
  2. HAMi-Webhook（Mutating Admission Webhook）：在 Pod 创建时自动注入环境变量、设备路径、共享库路径。业务方不用手写 env
  3. HAMi-Device-Plugin（与各家 Device Plugin 并存）：在显存/算力切分能力上补一层——强制限制 Pod 只能用到声明的显存大小
  4. HAMi-Exporter（监控采集）：按节点 + Pod 维度采集 GPU 利用率，比厂商自家 exporter 更细（自带 Pod→Device 映射）

21.8 与 GPU Operator / Cluster Autoscaler 的关系
GPU Operator
  • NVIDIA GPU Operator 是 NVIDIA 专用的"一键装驱动 + device plugin + DCGM + time-slicing"的 Operator

21.10 生产避坑
HAMi 调度死锁

症状：Pod 永远 Pending

根因：HAMi-Scheduler 与 K8s 默认调度器各有自己的 filter 逻辑，"HAMi 看显存满足"和"默认调度器看卡剩余"可能不一致。

修复：

  1. 在 hami-scheduler-config 里关闭默认调度器的 filter（让 HAMi 完全接管）
  2. 或设置 schedulingDurationTimeout 给 HAMi 单独配额
MIG 切分后无法访问整卡

根因：HAMi 启动时如果把卡切成 MIG instance，原本需要"整卡"的训练脚本会失败。

修复：

  1. 在节点上加 label：hami.dev/gpu-mig-disabled: "true"
  2. 或在 Pod annotation 里加：hami.dev/no-mig: "true"
多厂商节点混部

症状：业务方写 hami.dev/gpu 但调度到了错误厂商的节点

根因：节点 vendor 标签没打或打错

修复：

  • 每家节点加 label（用 node-feature-discovery 自动打）：
# NFD 检测厂商后自动加
kubectl label node <n> hami.dev/gpu-vendor=huawei
kubectl label node <n> hami.dev/gpu-vendor=nvidia
kubectl label node <n> hami.dev/gpu-vendor=hygon
kubectl label node <n> hami.dev/gpu-vendor=cambricon
kubectl label node <n> hami.dev/gpu-vendor=metax
21.11 适用场景 & 不适用场景
HAMi 适用的场景
  • 算力池化：100 张卡跑 1000 个小推理任务，显存/算力切分必选
  • 多厂商采购：集群有 NVIDIA + 华为昇腾 + 海光，业务方需要统一提交
  • 弹性推理：vLLM / Triton 部署，按 QoS 分级共享卡
  • CI / 训练任务：大量小任务，time-slicing 提高利用率
HAMi 不适用的场景
  • HPC 通信密集训练（大模型 DDP / NCCL all-reduce）：切分会破坏通信效率，建议独占整卡
  • MIG 独占：H100 MIG 已经是硬件级切分，再加 HAMi 等于多余一层
  • 极致低延迟推理：HAMi 调度延迟（10-50ms）会影响 tail latency

23. AMD ROCm 与 Intel GPU 在异构 GPU 共享调度中的现状

本章回答用户的疑问

上一节 §21 列了 HAMi 支持的国产 + NVIDIA 设备，有人会问：AMD ROCm 和 Intel GPU 呢？

这两个国际厂商在"异构 GPU 共享"这件事上的状态完全不同：

  • AMD 有社区实验性实现（Midokura 为 MI300X 贡献过 fork），但未合并主仓库——离"生产可用"还有距离
  • Intel 完全在 roadmap 上，没有任何可用实现——短期内（一两年内）看不到官方支持

23.1. AMD ROCm：社区有 PR，主仓未合并

23.1.1. 现状

维度 现状
HAMi 官方实现 无（仓库 pkg/device/ 目录下没有 amd 包）
社区 PR midokura/hami-rocm-plugin fork（Midokura 维护）
是否合并 否——HAMi maintainer 公开回复：ROCm 设备抽象与 NVIDIA 差异太大（特别是 ROCm 的 driver-API 语义），需要一个完整的 v2 重构才能稳定合并
切分能力 ROCm 自带的 Partition API 支持整卡 + memory partition，但 HAMi 还没接入
KFD 拓扑 ROCm 拓扑信息通过 KFD（Kernel Fusion Dispatcher）暴露，与 NVML 差异大

23.1.2. 为什么一直没合并

tab:AMD 路径与 NVIDIA 差异的本质

概念 NVIDIA AMD ROCm
设备枚举 CUDA_VISIBLE_DEVICES + NVML HIP_VISIBLE_DEVICES + KFD
显存切分 MIG（hardware） + time-slicing（software）+ 显存 cgroup 只能 time-slicing ——MI300X 没有 MIG 等价物
算力限制 通过 GPU clock + SM partition 无原生支持——只能通过 HIP stream 调度
拓扑查询 nvidia-smi topo -m rocm-smi --topology
多卡通信 NCCL RCCL
容器化 OCI standard（nvidia-container-toolkit） 无 OCI shim——手动设备直通

结论：HAMi 当前的 device plugin 抽象强假设 NVIDIA 模型（per-Pod 显存 + 算力限制），直接接 ROCm 需要先把"调度语义"重新抽象。

23.1.3. 现阶段替代方案

# 不用 HAMi，直接用 ROCm GPU Operator + 自己写软切分
helm install rocm-operator rocm/gpu-operator \
  --set driver.enabled=true \
  --set devicePlugin.enabled=true

# 软切分：用 ROCm Partition + DCGM 限制
# 即 MI300X 切成 2 个 partition，每个 partition 跑一个 Pod
rocm-smi --setgpupartition 2   # 切为 2 个 partition

23.1.4. 未来预期

  • ROCm 6.5+ 引入了更细的 GPU 切分 API（参照 NVIDIA MIG 设计）
  • HAMi Issue #1234 有公开讨论"ROCm v2 设计"
  • 预计时间：HAMi 2025-2026 的 v3.0 重构可能会原生成 ROCm 支持

实战建议：如果你现在就要在 AMD 卡上跑大模型，别等 HAMi AMD——直接用 ROCm + GPU Operator + 自己分时复用（time-slicing ConfigMap）。
