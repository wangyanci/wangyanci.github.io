问题

如何设计高质量的 JSON Schema 工具定义，让 LLM 准确理解和调用工具？

答案

工具 Schema 的设计质量直接决定了 LLM 调用的准确性。description 是模型判断的唯一依据，Schema 设计不是"能跑就行"，而是需要精心设计的工程问题。

Schema 核心结构

{
    "type": "function",
    "function": {
        "name": "tool_name",
        "description": "清晰、具体的工具功能描述，包含适用场景和不适用场景",
        "parameters": {
            "type": "object",
            "properties": {
                "param1": {
                    "type": "string",
                    "description": "参数含义、格式、示例值",
                    "enum": ["可选的枚举值"]
                }
            },
            "required": ["param1"]
        }
    }
}

设计最佳实践

1. description 必须精准具体

# ❌ 坏示例 - 描述含糊
"description": "获取天气"

# ✅ 好示例 - 精确描述边界
"description": "查询指定中国大陆城市的实时天气，包含气温、天气状况、风向风速。不支持查询历史天气或未来预报。不支持国外城市。"

2. 参数说明要包含约束和示例

"properties": {
    "city": {
        "type": "string",
        "description": "城市中文名称，如'北京''上海'。不要带'市'后缀，不要传省份+城市组合。"
    },
    "date": {
        "type": "string",
        "description": "查询日期，格式YYYY-MM-DD，如'2024-01-15'。仅支持今天和明天。"
    }
}

3. 用 enum 限制参数取值范围

"unit": {
    "type": "string",
    "enum": ["celsius", "fahrenheit"],
    "description": "温度单位，默认celsius"
}

4. 明确标注 required 字段

"required": ["city"],  # 必填参数
# 可选参数不要放在 required 中，让模型知道可以不传

5. 避免工具职责重叠

多个工具功能相近时，模型会根据名字猜测，产生误调用。必须明确区分：

# ❌ 坏示例 - 两个工具职责不清
"name": "search"        # description: "搜索信息"
"name": "query_db"      # description: "查询数据库"

# ✅ 好示例 - 职责明确分离
"name": "web_search"    # description: "在互联网上搜索公开信息，适用于查新闻、百科、实时资讯。不适用于查内部系统数据。"
"name": "query_orders"  # description: "查询内部订单管理系统的订单数据，需要订单号或用户ID作为输入。"

6. 控制工具数量和单次可用数量

  • 总工具数建议不超过 20-30 个
  • 单次请求中给模型看到的工具不超过 8 个（避免上下文过长、选择困难）
  • 按场景动态选择工具子集，而非一次性暴露所有工具

完整的高质量 Schema 示例

tools = [{
    "type": "function",
    "function": {
        "name": "create_bug_ticket",
        "description": "在缺陷管理系统中创建 Bug 工单。适用于用户反馈线上问题、测试发现缺陷等场景。不支持创建需求或任务工单。",
        "parameters": {
            "type": "object",
            "properties": {
                "title": {
                    "type": "string",
                    "description": "Bug 标题，简洁描述问题，如'支付接口返回500错误'",
                    "maxLength": 100
                },
                "severity": {
                    "type": "string",
                    "enum": ["P0-紧急", "P1-严重", "P2-一般", "P3-轻微"],
                    "description": "严重程度。线上故障选P0，核心功能不可用选P1，一般缺陷选P2，UI问题选P3。"
                },
                "reproduce_steps": {
                    "type": "string",
                    "description": "复现步骤，用1.2.3.格式列出。至少包含操作步骤、输入数据、期望结果、实际结果。"
                },
                "reporter": {
                    "type": "string",
                    "description": "报告人工号，格式EMP开头，如'EMP00123'"
                }
            },
            "required": ["title", "severity", "reproduce_steps"]
        }
    }
}]

延伸追问

Q: Schema 写得越详细越好吗？
A: 不是。过长描述会增加上下文噪声，消耗更多 token。关键是"清晰、互斥、可校验"——每个字段要有业务含义，工具之间职责不重叠。

Q: 工具数量很多时怎么办？
A: 采用工具检索机制——先用 TF-IDF/BM25/向量检索筛选出最相关的 K 个工具，再交给 LLM 选择。类似 RAG 的思路做 Tool Selection。

常见误区

  1. 误区：description 随便写，模型能猜出来。
    纠正：description 是模型判断的唯一依据，写得不清楚模型就会"瞎猜"。

  2. 误区：所有工具一次性暴露给模型。
    纠正：工具太多会降低选择准确率，建议按场景动态筛选。

  3. 误区：Schema 只是形式，不影响调用质量。
    纠正：Schema 质量直接决定工具选择准确率和参数正确率，是工程落地的关键。
