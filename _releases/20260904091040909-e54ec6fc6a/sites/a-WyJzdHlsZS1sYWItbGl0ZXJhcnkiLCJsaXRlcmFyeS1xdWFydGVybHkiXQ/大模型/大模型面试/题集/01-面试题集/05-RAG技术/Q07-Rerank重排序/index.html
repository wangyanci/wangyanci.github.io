## 问题
在 RAG 系统中，什么是 Rerank（重排序）？为什么需要在检索后增加这一步？常用的 Rerank 模型有哪些？如何实现？

## 答案

**Rerank 是对初步检索结果的二次精排**。RAG 系统中，初步检索（向量检索或混合检索）速度快但精度有限，Rerank 用更精确的模型对 Top-K 结果重新排序，提升检索质量。

**为什么需要 Rerank：**

┌─────────────────────────────────────────────────────────────┐
│ 向量检索的问题 │
│ 1. Embedding 模型是"双塔"结构——查询和文档分别编码 │
│ 没有交互计算，精度有上限 │
│ 2. ANN 是近似搜索，Top2-Top5 的排名可能不准确 │
│ 3. 相似度 ≠ 相关性——语义相似的文档不一定相关 │
└─────────────────────────────────────────────────────────────┘
│
▼
┌─────────────────────────────────────────────────────────────┐
│ Rerank 的作用 │
│ 使用 Cross-Encoder 让查询和文档"交互"计算匹配分数 │
│ 精确判断文档与查询的相关性 │
│ 同时过滤掉不相关的文档 │
└─────────────────────────────────────────────────────────────┘


**双塔 vs Cross-Encoder：**

| 架构 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **双塔(Bi-Encoder)** | 查询和文档分别编码为向量，然后计算相似度 | 速度快，可预计算 | 没有交互，精度有限 |
| **交叉编码(Cross-Encoder)** | 查询和文档一起输入模型，做交互计算 | 精度高，捕获深层语义关系 | 速度慢，无法预计算 |

**Rerank 在 RAG 流程中的位置：**

用户查询
│
▼
┌──────────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐
│ 多路召回 │───▶ │ 初步排序 │───▶ │ Rerank │───▶ │ LLM 生成 │
│ (BM25+向量) │ │ Top-50 │ │ 精排Top-5 │ │ │
└──────────────┘ └──────────┘ └──────────┘ └──────────┘
↑

**常用 Rerank 模型：**

| 模型 | 类型 | 特点 | 适用场景 |
|------|------|------|---------|
| **BGE-Reranker-v2-m3** | 开源 | 中英文效果优秀，可本地部署 | 中文/多语言场景 |
| **Cohere Rerank** | 商用 API | 效果顶级，支持多语言 | 预算充足的生产环境 |
| **bce-reranker-base_v1** | 开源 | 效果接近 Cohere，免费 | 性价比首选 |

**实现示例：**

```python
from langchain.retrievers import ContextualCompressionRetriever
from langchain_community.document_compressors import CrossEncoderReranker
from langchain_community.cross_encoders import HuggingFaceCrossEncoder

# 初始化 Rerank 模型
model = HuggingFaceCrossEncoder(model_name="BAAI/bge-reranker-v2-m3")
compressor = CrossEncoderReranker(model=model, top_n=5)

# 包装原有检索器
compression_retriever = ContextualCompressionRetriever(
    base_compressor=compressor,
    base_retriever=vectorstore.as_retriever(search_kwargs={"k": 20})
)

# 检索 + Rerank 同时进行
compressed_docs = compression_retriever.invoke("什么是RAG？")
# 返回 Rerank 后的 Top-5 文档

# 独立使用 Rerank
from sentence_transformers import CrossEncoder

reranker = CrossEncoder("BAAI/bge-reranker-v2-m3")

def rerank(query, documents, top_n=5):
    """对文档进行重排序"""
    pairs = [[query, doc.page_content] for doc in documents]
    scores = reranker.predict(pairs)
    
    # 按分数排序
    scored_docs = list(zip(documents, scores))
    scored_docs.sort(key=lambda x: x[1], reverse=True)
    
    return [doc for doc, _ in scored_docs[:top_n]]

reranked_docs = rerank("什么是RAG？", initial_results, top_n=5)

性能数据对比：

方案 NDCG@10 平均延迟 说明
纯向量检索 0.62 10ms 基线
向量 + Rerank 0.78 50ms 显著提升
混合检索 + Rerank 0.85 80ms 最佳效果

生产实践建议：

  1. Rerank 只对 Top-20~50 进行，不要对全量数据做
  2. Rerank 后一般取 Top-3~5 送入 LLM
  3. Rerank 可以和 RRF 融合配合使用
  4. 如果延迟敏感，可用轻量级 Rerank 模型（如 ONNX 加速版）

延伸追问

Q: Rerank 为什么比向量检索更精确？

A: 向量检索的双塔模型分别编码查询和文档，没有交互。Rerank 的 Cross-Encoder 将查询和文档拼接后一起输入模型，注意力机制可以让每个 token 都"看到"对方的信息，从而捕获更深层的关系。

Q: Rerank 的延迟问题怎么解决？

A: 1) 只对 Top-K 做 Rerank（K≤50）；2) 使用 GPU 加速；3) 使用 ONNX/TensorRT 加速推理；4) 使用更轻量的 Rerank 模型；5) 异步执行 Rerank。

常见误区

  1. Rerank 替代初始检索 — Rerank 计算成本高，不能替代初始检索，只能作为精排
  2. 对全部文档做 Rerank — 应该只对初步检索的 Top-K 做，控制计算量
  3. 忽略 Rerank 模型和 Embedding 模型的匹配 — 中文场景用中文 Rerank 模型
  4. 认为 Rerank 一定提升效果 — 如果初始检索质量已经很高，Rerank 提升有限
