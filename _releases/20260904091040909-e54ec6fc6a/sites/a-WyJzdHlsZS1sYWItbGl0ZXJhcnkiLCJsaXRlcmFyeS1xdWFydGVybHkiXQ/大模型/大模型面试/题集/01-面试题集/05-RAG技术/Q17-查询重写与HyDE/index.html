## 问题
在 RAG 系统中，查询重写（Query Rewriting）有哪些常见技术？HyDE（假设文档嵌入）的原理是什么？各自适用于什么场景？

## 答案

查询重写是 RAG 检索前优化的关键技术，目的是**缩小用户查询与文档内容的语义鸿沟**，提高检索召回率。

**常见查询重写技术：**

| 技术 | 原理 | 解决的问题 | 示例 |
|------|------|-----------|------|
| **同义扩展** | 添加同义词、近义词 | 词汇不匹配 | "手机发热" → "手机发烫、过热" |
| **语义重写** | 口语化→规范化 | 表述不规范 | "这玩意儿好用吗？" → "产品用户体验如何？" |
| **对话历史融合** | 结合上文消歧 | 指代不明 | "续航多少？" → "Model Y 续航多少？" |
| **问题分解** | 复杂问题拆分为子问题 | 多跳推理 | "比较A和B的优缺点" → 分别查A和B |
| **HyDE** | 生成假设答案再检索 | 查询-文档语义鸿沟 | 见下方详解 |
| **后退提示** | 具体→抽象→再推理 | 信息不足 | "北京房价多少？" → "一线城市房价趋势" |

**HyDE（Hypothetical Document Embeddings）详解：**

HyDE 的核心思想是：**先让 LLM 生成一个假设性的理想答案，然后用这个假设答案的向量去检索真实文档**。

传统 RAG：
用户查询 ──Embedding──▶ 查询向量 ──▶ 向量检索
问题：用户查询和文档的语义空间可能不一致

HyDE：
用户查询 ──▶ LLM 生成假设答案
"量子计算在药物研发中的应用"
──▶ "量子计算通过模拟分子结构，加速新药研发..."

假设答案 ──Embedding──▶ 假设向量 ──▶ 向量检索真实文档
优势：假设答案的语义更接近文档内容


```python
from langchain.chains import HypotheticalDocumentEmbedder

# 创建 HyDE Embedding
hyde_embeddings = HypotheticalDocumentEmbedder.from_llm(
    llm=ChatOpenAI(),
    base_embeddings=OpenAIEmbeddings(),
    prompt_key="web_search"  # 使用预置 Prompt
)

# 使用 HyDE 进行检索
results = vectorstore.similarity_search(
    "量子计算在药物研发中的应用",
    embedding=hyde_embeddings  # 使用 HyDE Embedding
)

Multi-Query（多查询扩展）：

from langchain.retrievers.multi_query import MultiQueryRetriever

# 让 LLM 生成多个查询变体
multi_query_retriever = MultiQueryRetriever.from_llm(
    retriever=base_retriever,
    llm=ChatOpenAI(temperature=0)
)

# 输入一个查询，内部生成多个变体并行检索
results = multi_query_retriever.invoke("苹果新品")
# 内部可能生成：
# - "Apple 2024 发布会"
# - "iPhone 16 配置参数"
# - "苹果秋季新品"

各种技术的适用场景：

技术 适用场景 不推荐场景
HyDE 查询表述与文档差异大 需要严格事实准确性的场景
Multi-Query 召回率要求高 延迟敏感的场景
问题分解 复杂多跳问题 简单单点问题
对话历史融合 多轮对话 单轮查询

延伸追问

Q: HyDE 生成的假设答案不准确怎么办？

A: 1) 设置相似度阈值，假设答案与文档相似度过低时回退到原始查询；2) 使用更准确的 LLM 生成假设答案；3) 结合 Rerank 层过滤不准确的结果。

Q: 查询重写会增加多少延迟？

A: 取决于技术：同义扩展几乎无延迟；HyDE 需要一次 LLM 调用（~1-2s）；Multi-Query 需要多次检索。生产环境需要权衡效果与延迟。

常见误区

  1. 所有查询都需要重写 — 简单明确的查询不需要重写
  2. HyDE 一定更好 — HyDE 依赖 LLM 生成假设答案的质量，如果生成错误反而影响检索
  3. 查询越多越好 — Multi-Query 的查询数量需要控制，过多会增加延迟和噪声
