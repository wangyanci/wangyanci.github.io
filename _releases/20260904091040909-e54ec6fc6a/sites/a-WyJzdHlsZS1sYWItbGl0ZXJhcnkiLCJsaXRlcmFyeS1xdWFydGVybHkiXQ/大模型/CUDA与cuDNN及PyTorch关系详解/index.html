1. 一句话定位

对刚入门的人×
对搞过训练的人×
对系统管理员×
+
CUDA = 让你用 NVIDIA 显卡做计算的"平台"
cuDNN = CUDA 上专门为深度学习写的"算子库"
PyTorch = 让你写 Python 就能"间接"调用上面两者

CUDA 装好驱动 + Toolkit；
cuDNN 装好后框架自动用；
PyTorch 装 CPU 版 / +cu118 / +cu126 等不同 wheel。

机器学习服务器的"三层依赖"：
NVIDIA 驱动 → CUDA Toolkit → cuDNN / cuBLAS → 框架。
每升级一层都要验证上层兼容。

3. CUDA 是什么

3.1. 一句话定义

CUDA（Compute Unified Device Architecture）是 NVIDIA 推出的 GPU 通用计算平台——让程序可以使用 NVIDIA 显卡做"非图形"计算。

—— developer.nvidia.com/cuda-toolkit

CUDA 主要包括四类组件：

  • CUDA Driver：用户态驱动，被 PyTorch 等程序加载。
  • CUDA Runtime（libcudart）：标准运行时 API（cudaMalloc / cudaMemcpy / cudaLaunchKernel 等）。
  • CUDA Compiler（nvcc）：把 .cu 源码编译为 GPU 可执行指令。
  • 各种 GPU 加速库（cuBLAS、cuFFT、cuDNN、cuRAND 等）。

3.2. CPU 加法 vs CUDA 加法

CPU（C 风格）×
CUDA（GPU）×
对应 PyTorch×
+
// 单核循环
for (int i = 0; i < n; i++) {
    c[i] = a[i] + b[i];
}

// Kernel：每个 thread 处理一个元素
__global__ void add(int n, float *a, float *b, float *c) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) {
        c[i] = a[i] + b[i];
    }
}

// 启动：1024 个 block，每个 256 个 thread
add<<<1024, 256>>>(n, a, b, c);

import torch

# 上面那段 CUDA Kernel 在 PyTorch 里就一行
a = torch.randn(n, device="cuda")
b = torch.randn(n, device="cuda")
c = a + b  # 自动调用 Elementwise Kernel
一个 Kernel 启动几千个线程

现代 GPU 的一张卡就有几万到十几万个 CUDA Core。CUDA Kernel 启动后，线程被调度器分配到这些 Core 上——一个数组加法，CPU 要循环 N 次，CUDA 上 N 个线程并行一次完成。

3.3. CUDA 不是深度学习

CUDA 本身是一个通用 GPU 计算平台——它对深度学习一无所知。CUDA 上的神经网络算子由 cuDNN 提供（见 §4）。

4. cuDNN 是什么

4.1. 一句话定义

cuDNN（CUDA Deep Neural Network library）是 NVIDIA 官方提供的 CUDA 之上的深度学习加速库。

—— docs.nvidia.com/deeplearning/cudnn

cuDNN 把所有深度学习里常见的算子都做了高度优化实现：

算子 说明
Conv 卷积（前向 + 反向 + 多种算法）
Pooling 最大池化 / 平均池化
Softmax 含数值稳定版本
BatchNorm 训练 / 推理两个分支
RNN / LSTM / GRU 循环神经网络单元
Attention 缩放点积注意力（含 Flash Attention）
LayerNorm / GroupNorm 各类归一化
Tensor Core ops FP16 / BF16 / TF32 / INT8 矩阵乘

4.2. 调用链示例

x = torch.randn(8, 3, 224, 224, device="cuda")
conv = torch.nn.Conv2d(3, 64, kernel_size=3, padding=1).cuda()

y = conv(x)

完整调用链：

Python
   ↓
torch.nn.Conv2d.forward
   ↓
ATen（PyTorch C++ 张量库）
   ↓
Dispatch（按 device / dtype 选 backend）
   ↓
cuDNN（NVIDIA 写的最优卷积实现）
   ↓
CUDA Runtime
   ↓
NVIDIA Driver
   ↓
GPU 硬件
"自己写"代价

你可以自己在 CUDA 里实现卷积——Winograd / FFT / Implicit GEMM 怎么选、超参怎么调？NVIDIA 工程师调了几十年的算法，cuDNN 一行接口就比手写快 5~20 倍。

5. PyTorch 是什么

5.1. 一句话定义

PyTorch 是一个 Python 优先的深度学习框架——它本身不直接控制 GPU，而是通过调用 CUDA、cuDNN、cuBLAS 等底层库把 GPU 计算包装成简单 API。

5.2. 矩阵乘法的完整调用链

a = torch.rand(1000, 1000, device="cuda")
b = torch.rand(1000, 1000, device="cuda")
c = a @ b

调用链：

Python
   ↓
torch.matmul()
   ↓
ATen
   ↓
Dispatch
   ↓
CUDA Backend
   ↓
cuBLAS（矩阵乘是它的拿手戏）
   ↓
CUDA Runtime
   ↓
Driver
   ↓
GPU
为什么矩阵乘法走 cuBLAS

a @ b 是通用矩阵乘（GEMM）——这是 cuBLAS 的核心优化对象（几十年持续优化）。cuDNN 主要负责神经网络专用算子（卷积、注意力、RNN）。两者各司其职。

5.3. 不同算子走不同的库

PyTorch 调用 走的库 备注
a + b（elementwise） 自带 Elementwise Kernel 简单加法不需要 cuDNN
a @ b（矩阵乘） cuBLAS 通用 GEMM
nn.Conv2d cuDNN 多种卷积算法自动选优
nn.Linear cuBLAS 内部转成 GEMM
nn.LSTM cuDNN 循环网络优化
F.softmax 自带 + 编译期优化 简单算子
nn.BatchNorm cuDNN 训练推理两套
nn.MultiheadAttention cuDNN（含 Flash Attention） PyTorch 2.x 默认走 SDPA

6. CUDA 与 cuDNN 的关系

                        CUDA
                          │
        ┌────────┬────────┼────────┬────────┬────────┐
        ▼        ▼        ▼        ▼        ▼        ▼
     Runtime  Driver   cuBLAS  cuFFT   cuRAND  cuSPARSE
                                                  │
                                                  ▼

cuDNN 不是独立存在

cuDNN 构建在 CUDA 之上，依赖 CUDA Runtime、Driver、cuBLAS 等基础库。

  • 装 cuDNN 之前必须先装对应版本的 CUDA。
  • CUDA Toolkit 安装包通常不包含 cuDNN（需要单独下载 .tar.gz 或 .deb / .rpm）。
  • 深度学习框架的 pip wheel 通常自带对应版本的 cuDNN（libcudnn.so 静态或动态链接进去）。

8. Torch 为什么依赖 CUDA

8.1. CPU 路径 vs GPU 路径

a + b 这一行代码在两个后端走的链路完全不同：

CPU 后端×
CPU 后端调用栈×
GPU 后端×
GPU 后端调用栈×
+
Python
   ↓
torch.add
   ↓
ATen
   ↓
CPU Backend（C++ 实现，调用 OpenBLAS / MKL / oneDNN）
   ↓
CPU

import torch
a = torch.randn(1000, 1000)   # 默认在 CPU
b = torch.randn(1000, 1000)
c = a + b                       # 走 CPU backend

Python
   ↓
torch.add
   ↓
ATen
   ↓
Dispatch（看到 tensor 是 cuda 类型）
   ↓
CUDA Backend
   ↓
CUDA Runtime
   ↓
NVIDIA Driver
   ↓
GPU

import torch
a = torch.randn(1000, 1000, device="cuda")
b = torch.randn(1000, 1000, device="cuda")
c = a + b                       # 走 CUDA backend
PyTorch 的 Dispatch 机制

PyTorch C++ 端用 Dispatcher 模式管理后端：同一个 torch.add 函数，根据 Tensor 的 device（cpu / cuda / mps / xpu / hpu...）自动派发到对应实现。

这也是 PyTorch 比早期 Torch 优雅的地方——一套 API 多个硬件后端。

8.2. 没有 CUDA 也能跑（CPU 版 PyTorch）

# 装 CPU 版 PyTorch（更小，不需要任何 NVIDIA 依赖）
pip install torch --index-url https://download.pytorch.org/whl/cpu

# 验证
python -c "import torch; print(torch.__version__)"
# 2.8.0+cpu
CPU 版适合
  • 学习 / 调试 / 单元测试
  • 小模型推理（BERT-base、Qwen-0.5B）
  • 部署环境无 GPU

不适合：大模型训练 / 推理（慢 10~100 倍）。

9. Torch 为什么依赖 cuDNN

9.1. 速度差距：一个卷积的对比

┌────────────────────────────────────────────────────┐
│  自己写 CUDA 卷积                                  │
│  - Naive：O(n²) 实现                               │
│  - Shared memory tile：快一些                       │
│  - Tensor Core 优化：再快一些                       │
│  - 但比 cuDNN 仍慢 2~20 倍                          │
└────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────┐
│  cuDNN 卷积                                        │
│  - 算法选择器：根据 input size 选最优算法             │

不要手写卷积

早期有人用 torch.cuda.amp.autocast 加手写 kernel 挑战 cuDNN——结果全部失败。cuDNN 背后是 NVIDIA 几百人工程师几十年的工作，业余玩家无法匹敌。

9.2. cuDNN 的算法选择

import torch
import torch.nn as nn

# 启动 benchmark：让 cuDNN 试遍所有算法、选最快的
torch.backends.cudnn.benchmark = True

# 关闭确定性（小幅提速，代价是 bit-exact 结果不可复现）
torch.backends.cudnn.deterministic = False

# 显存允许时开 TF32
torch.backends.cuda.matmul.allow_tf32 = True
torch.backends.cudnn.allow_tf32 = True

# 跑一个 2D 卷积
conv = nn.Conv2d(3, 64, 3, padding=1).cuda()
x = torch.randn(8, 3, 224, 224, device="cuda")
y = conv(x)  # cuDNN 自动选 GEMM / Winograd / Implicit GEMM
cudnn.benchmark = True 的取舍
  • 开启：第一次跑慢（要试每种算法），之后所有相同 shape 的输入都走最优算法——生产环境推荐。
  • 关闭：每次都走固定算法，适合 shape 经常变化的场景。
  • 第一次跑完会自动选优，结果写进 cuDNN 内部 cache。

11. PyTorch 的各种 CUDA 版本是怎么回事

11.1. wheel 文件命名规则

torch==2.8.0+cpu
torch==2.8.0+cu118
torch==2.8.0+cu126
torch==2.8.0+cu128

后缀 含义 适用硬件
+cpu 纯 CPU 版，无 GPU 支持 服务器无 GPU / 调试
+cu118 内置 CUDA 11.8 兼容运行时 NVIDIA 驱动 >= 525.60
+cu126 内置 CUDA 12.6 兼容运行时 NVIDIA 驱动 >= 560
+cu128 内置 CUDA 12.8 兼容运行时 NVIDIA 驱动 >= 570
+rocm6.2 AMD ROCm 6.2 运行时 AMD GPU（MI250X / RX 7900）
+xpu Intel GPU 运行时 Intel Arc / Data Center GPU
+mps Apple Silicon 装 torch 主包即可（MPS 是 CPU 包内置的）

11.2. 装 pip wheel 需要装 CUDA Toolkit 吗？

容易误解

torch==2.8.0+cu126 不要求系统里装完整的 CUDA Toolkit。

  • 官方 PyTorch wheel 已自带 必需的 CUDA 运行时 + 常用库（cuBLAS、cuDNN 等）。
  • 只需要 装足够新的 NVIDIA 显卡驱动（cu126 wheel 一般要求驱动 >= 560.x）。
  • 必须装 CUDA Toolkit 的场景：
    • 写自己的 CUDA 扩展（C++ extension）。
    • 从源码编译 PyTorch。
    • 用 nvcc 编译 .cu 文件。
    • 用 CUTLASS / Thrust / cuDNN 头文件开发自定义算子。

11.3. 怎么选 wheel

# 1. 看 NVIDIA 驱动支持的最高 CUDA 版本
nvidia-smi
# 输出右上角：CUDA Version: 12.6

# 2. 选 <= 该版本的 cu wheel
pip install torch==2.8.0+cu126

# 3. 验证
python -c "import torch; print(torch.cuda.is_available(), torch.version.cuda)"
# True 12.6
驱动 vs CUDA Toolkit
  • 驱动（nvidia-driver）：装在系统上，决定能跑的最高 CUDA 版本。
  • CUDA Toolkit（含 nvcc）：可选，编译 / 开发时用。
  • PyTorch wheel 内置的 CUDA 运行时：运行 PyTorch 用，跟驱动兼容即可。

装 PyTorch 时不需要 apt install cuda-toolkit-12-6，pip 装 +cu126 wheel 即可。

14.2. cuDNN 还需要单独装吗？

不需要，如果用 pip wheel：

  • torch+cu126 wheel 已经把对应版本的 cuDNN 静态 / 动态链接进去了。
  • 装 cuDNN 的场景是：自己写 CUDA 扩展、从源码编译 PyTorch、用 TensorRT 推理。

14.3. 同一台机器能装多个 CUDA Toolkit 吗？

可以，但要管理好 PATH 和 LD_LIBRARY_PATH：

# 例如同时装 11.8 和 12.6
/usr/local/cuda-11.8
/usr/local/cuda-12.6

# 切换版本
export CUDA_HOME=/usr/local/cuda-12.6
export PATH=$CUDA_HOME/bin:$PATH
export LD_LIBRARY_PATH=$CUDA_HOME/lib64:$LD_LIBRARY_PATH

# 装 PyTorch 扩展时也要让 nvcc 用对应版本

14.4. AMD 显卡能跑 PyTorch 吗？

可以，用 ROCm 后端：

# ROCm 版 PyTorch（仅限 Linux + 部分 AMD GPU）
pip install torch --index-url https://download.pytorch.org/whl/rocm6.2

支持范围（2026 年）：AMD Instinct MI250X/MI300X、RX 7900 XTX、Radeon Pro W7900 等。桌面级 RX 6000 系列不在官方支持列表，需用社区版（如 ZLUDA）。

14.5. Apple Silicon（M1/M2/M3/M4）怎么跑？

import torch

# MPS 后端（PyTorch 1.12+ 内置）
device = torch.device("mps" if torch.backends.mps.is_available() else "cpu")
x = torch.randn(1000, 1000, device=device)
y = x @ x
MPS 不走 CUDA

MPS（Metal Performance Shaders）走 Apple 自家的 Metal API，跟 NVIDIA / CUDA 体系完全独立。

  • cuBLAS / cuDNN 在 macOS 上不工作。
  • 性能约为同价位 NVIDIA GPU 的 50%~70%。
  • 适合开发、调试、小模型；不适合大模型训练。

14.6. 没有 GPU 还想跑模型？

  • CPU 版 PyTorch：pip install torch+cpu，能跑小模型。
  • llama.cpp / Ollama（参考 Python原生运行大模型指南）：CPU 跑量化模型首选。
  • Google Colab 免费版：T4 GPU，每会话 ~12 小时。
  • Kaggle Notebooks：每周 30 小时 GPU。

14.7. cuDNN 报 "Could not initialize" 怎么排查？

1. 驱动版本太老 → 升级驱动
2. PyTorch 内置的 cuDNN 与系统装的 cuDNN 版本冲突 → unset LD_LIBRARY_PATH
3. Docker 容器内没挂载 NVIDIA 设备 → 启动时加 --gpus all
4. 多卡环境 NCCL 通信失败 → 检查 NCCL_SOCKET_IFNAME / NCCL_IB_HCA 环境变量

14.8. cuDNN 怎么升级？

如果用 pip wheel：升级 wheel 即可：

pip install --upgrade torch
# cuDNN 会跟着升级

如果是自己从源码编译的 PyTorch：

# 1. 下载新版 cuDNN tarball
# 2. 替换头文件 + 库
sudo cp cudnn/include/cudnn*.h /usr/local/cuda/include/
sudo cp cudnn/lib/libcudnn* /usr/local/cuda/lib64/
sudo ldconfig

16. 小结

  • CUDA：NVIDIA GPU 的通用计算平台——不是深度学习专用的，是给所有 GPU 程序用的。
  • cuDNN：构建在 CUDA 之上的深度学习算子库——卷积、Attention、RNN、BatchNorm 等的最优实现。
  • PyTorch：深度学习框架——通过 ATen + Dispatcher 自动调 CUDA / cuDNN / cuBLAS，把 GPU 编程包装成 Python 一行调用。
  • 三层依赖关系：硬件 → 驱动 → CUDA → cuDNN / cuBLAS → PyTorch。每升一层要验证上层兼容。
  • 安装原则：
    • 驱动装一次（系统级）。
    • CUDA Toolkit 可选（开发时）。
    • cuDNN 通常不需要单独装（pip wheel 自带）。
    • PyTorch 选对 wheel 后缀（+cu126 等）。
  • 不要试图自己实现卷积——cuDNN 背后是 NVIDIA 工程师几十年的工作。
  • 2026 年实践建议：
    • 新机器先装 NVIDIA 驱动（决定能跑的最高 CUDA 版本）。
    • 装 PyTorch 时选 pip wheel 自带 CUDA 运行时 的版本（不需要装 CUDA Toolkit）。
    • 训练时开 torch.backends.cudnn.benchmark = True 让 cuDNN 自动选最优算法。
    • 部署用 官方 PyTorch Docker 镜像——容器化一次性解决版本冲突。
    • 调试用 nvidia-smi + torch.cuda.memory_summary() 看 GPU 状态。

17.8.2. 顶部条：第一行的三个版本号

| NVIDIA-SMI 570.124.04    Driver Version: 570.124.04    CUDA Version: 12.8   |
字段 含义 常见误解
NVIDIA-SMI 570.124.04 工具版本，通常与驱动版本一致（驱动自带 nvidia-smi） 与驱动版不一致 → 异常
Driver Version: 570.124.04 GPU 驱动版本（决定支持的硬件 / OS / CUDA 范围） 跟系统内核版本是两回事
CUDA Version: 12.8 该驱动支持的最高 CUDA Runtime 版本，不是当前装的 CUDA Toolkit 版本 跟 nvcc --version 不必一致
最常见的误解

nvidia-smi 输出的 CUDA Version: 12.8 不代表你装了 CUDA 12.8 Toolkit。

驱动 570.xx 支持的 Runtime 范围：Cuda 12.x
  ↓
  假设系统装了：CUDA 12.4 Toolkit
    ↓
    nvcc --version     →  CUDA 12.4
    nvidia-smi         →  CUDA Version: 12.8
    PyTorch cu124     →  完全可工作

原因：驱动版本决定了能跑的最高 CUDA 版本，系统 Toolkit 可以低于这个版本。反过来不行——装 CUDA 12.8 Toolkit 但驱动只支持 12.4，会报 cuda runtime error: version mismatch。

查看驱动的另外两种方式：

cat /proc/driver/nvidia/version
# 输出：NVRM version: NVIDIA UNIX x86_64 Kernel Module  570.124.04  ...

modinfo nvidia | head -5
# 输出：filename, version, license, description 等

17.8.5. 显存（Memory-Usage）

| 1024MiB / 24564MiB |
  • 格式：已用 / 总容量
  • 单位：MiB 或 GiB
  • 训练时显存占用接近上限是好事——说明 batch size 充分利用。
显存和 GPU-Util 没关系

显存被占用 ≠ GPU 在计算。模型加载完就常驻显存，后续推理 / 训练才是实际计算。GPU-Util=0 + 显存 100% 几乎都是 DataLoader 瓶颈或同步阻塞。

PXB（多个 PCIe Switch） GPU0 ──Switch1──┬──Switch2── GPU1
PHB（经 CPU） GPU0 ──PCIe── CPU ──PCIe── GPU1
SYS（跨 CPU Socket） GPU0 ──CPU0──UPI──CPU1── GPU1

17.11.4. CPU Affinity 列

GPU0    ...     0-31
GPU1    ...     0-31
GPU2    ...     32-63
GPU3    ...     32-63
  • 数字代表物理核心编号
  • GPU 优先与 CPU Affinity 范围内的核通信
  • NUMA 调优：
# 把进程绑到 GPU0 所在的 NUMA node（CPU0）
numactl --cpunodebind=0 python train.py

# 进一步：绑具体核心
numactl --physcpubind=0-31 python train.py

17.11.5. 8 卡服务器示例（典型双 CPU）

        GPU0 GPU1 GPU2 GPU3 GPU4 GPU5 GPU6 GPU7

GPU0      X   NV4 PHB PHB SYS SYS SYS SYS
GPU1     NV4  X   PHB PHB SYS SYS SYS SYS
GPU2     PHB PHB  X  NV4 SYS SYS SYS SYS
GPU3     PHB PHB NV4  X  SYS SYS SYS SYS
GPU4     SYS SYS SYS SYS  X  NV4 PHB PHB
GPU5     SYS SYS SYS SYS NV4  X  PHB PHB
GPU6     SYS SYS SYS SYS PHB PHB  X  NV4
GPU7     SYS SYS SYS SYS PHB PHB NV4  X

物理含义：

CPU0 (NUMA node 0)              CPU1 (NUMA node 1)
├─ GPU0 ══ NV4 ══ GPU1         ├─ GPU4 ══ NV4 ══ GPU5
├─ GPU2 ══ NV4 ══ GPU3         ├─ GPU6 ══ NV4 ══ GPU7
└────────────────────────────────────────────────────
                  UPI / QPI
              （最慢的跨 CPU 通道）
  • GPU0 与 GPU1（NV4）：同一 CPU、同 NUMA 节点、有 NVLink → 通信最快
  • GPU0 与 GPU2（PHB）：同一 CPU、不同 PCIe 通道 → 中等
  • GPU0 与 GPU4（SYS）：跨 CPU、跨 NUMA → 最慢

17.11.6. 为什么训练时要看 topo -m

8 卡分布式训练：

GPU0 ←→ GPU1   NV4      速度：数百 GB/s  ← 理想
GPU0 ←→ GPU4   SYS      速度：几十 GB/s   ← 瓶颈
                  ↓
AllReduce 通信时间被最慢链路拖累

主流框架会自动读 topo：

  • NCCL：NCCL_IB_HCA、NCCL_P2P_LEVEL 等环境变量
  • PyTorch DDP：torch.distributed.init_process_group(backend='nccl') 会优先 NVLink
  • DeepSpeed / Megatron：自动拓扑感知

17.11.7. 通信性能排序（实际训练经验）

拓扑类型 通信性能 典型场景
NV12 / NV8 ★★★★★ HGX H100 / H200 全互联（顶级 GPU 服务器）
NV4 / NV2 ★★★★☆ 桌面工作站（RTX 4090 NVLink 版）、DGX
PIX ★★★★☆ 同 PCIe Switch 下的消费卡
PXB ★★★☆☆ 经过 PCIe 桥接
PHB ★★☆☆☆ 普通多卡服务器（经 CPU PCIe Host Bridge）
NODE ★★☆☆☆ 同一 NUMA 节点但跨 PCIe
SYS ★☆☆☆☆ 跨 CPU Socket，需 UPI/QPI——大模型训练最大瓶颈
8 卡服务器选购要点
  • 看 topo -m 是否全 NVLink：8 张卡任意两张都 NVLink 是顶级 GPU 服务器（HGX 平台）。
  • 只看单卡算力不看拓扑：8 张 RTX 4090 通过 PCIe + SYS 互联 vs 8 张通过 NV12 互联，大模型训练差距 3~5 倍。
  • CPU 选型：双路 EPYC / Xeon 时，确认 8 卡挂在同一 CPU 还是分两 CPU——后者会引入 SYS 跨 CPU 通信。

21.1. 是什么 + 解决什么问题

NVIDIA Container Toolkit 是一个分层架构的工具集，用于在容器环境中透明地暴露 NVIDIA GPU 设备。它由 libnvidia-container（底层 C 库）、nvidia-container-runtime（OCI 运行时 shim）、nvidia-ctk（CLI 工具）和 nvidia-cdi-hook（运行时钩子）组成。

—— GitHub: NVIDIA/nvidia-container-toolkit

没有它时的问题：

docker run -it ubuntu nvidia-smi
# 报错：command not found

docker run -it ubuntu python -c "import torch; torch.cuda.is_available()"
# 输出：False（容器内看不到 GPU）

# 原因：容器内的进程无法直接访问宿主机的 /dev/nvidia* 设备节点
# 也不应该共享宿主机的整个 CUDA 安装

装上 nvidia-container-toolkit 后：

Legacy 模式验证（docker --gpus）×
CDI 模式验证（docker --device）×
细粒度选择（指定卡号）×

机制 NVML 动态发现设备 读预生成 YAML 静态注入
规范 Docker 专有 --gpus CNCF 标准（OCI 兼容）
启动速度 慢（每次调 NVML） 快（读 YAML 即可）
多厂商统一 ❌ 只支持 NVIDIA ✅ CDI 规范可描述任何设备
K8s 原生 ⚠️ 通过 device plugin ✅ K8s 1.31+ CDI GA
Docker 版本 任意 Docker 25.0+ 支持，28.2+ 默认
推荐场景 老 Docker 单机 新部署、生产、K8s
CDI 是 OCI 标准

CDI（Container Device Interface）由 CNCF 推动，目标是让任意厂商（GPU / FPGA / DPU / TPU）都能用同一套机制描述设备注入。多 GPU 服务器、异构计算集群推荐开启 CDI。

21.11. GPU 显存隔离：5 种真实可行的方案

NVIDIA_MEMORY_LIMIT 不存在

NVIDIA 官方 nvidia-container-toolkit 源码（internal/config/image/envvars.go）只定义 8 个 NVIDIA_ 环境变量（详见 §21 开头表格）。NVIDIA_MEMORY_LIMIT 是伪变量——用 -e NVIDIA_MEMORY_LIMIT=4096 不会有任何效果。

真实可用的显存隔离方案：

+
# 8 卡机器上让容器只看到 GPU 0，物理上独占 80GB 显存
docker run --rm --gpus '"device=0"' nvidia/cuda:12.6-base nvidia-smi
# Memory-Usage: 0MiB / 81559MiB（独占整张 H100）

# 用环境变量等价写法
docker run --rm -e NVIDIA_VISIBLE_DEVICES=0 nvidia/cuda:12.6-base nvidia-smi

# 缺点：颗粒度粗——显存只用到 1GB 也独占整张卡

# 1. 启用 MIG（GPU 0）
sudo nvidia-smi -i 0 -mig 1
sudo reboot

# 2. 把 GPU 0 切成 7 个 1g.10gb 实例（A100 80GB）
sudo nvidia-smi mig -cgi 0 -C 1g.10gb

# 3. 容器只看到一个 MIG instance（10GB 显存，硬件隔离）
docker run --rm --gpus '"device=0"' nvidia/cuda:12.6-base nvidia-smi
# +-----------------------------------------------------------------------------+
# | GPU  Name  |  MIG 1g.10gb    |  Memory-Usage |  1024MiB / 9728MiB             |
# +-----------------------------------------------------------------------------+

# 缺点：只支持 A100/H100；启用 MIG 后整卡被切分（除非用 mixed 模式）

# PyTorch 进程内限制：最多用 4GB 显存
import torch
torch.cuda.set_per_process_memory_fraction(0.5, device=0)  # 用 50% = 40GB
# torch.cuda.set_per_process_memory_fraction(0.05, device=0)  # 用 5% = 4GB

x = torch.randn(1000, 1000, device='cuda')
# 如果超过 4GB → CUDA out of memory（不会拖累其他进程）

# 适合：单个容器内多进程 / 多模型推理服务
# 缺点：进程级限制，超限直接 OOM，不能"借用"空闲显存

# 1. 主机端启动 MPS 控制进程（per-GPU）
export CUDA_MPS_PIPE_DIRECTORY=/tmp/nvidia-mps
export CUDA_MPS_LOG_DIRECTORY=/tmp/nvidia-mps-log
nvidia-cuda-mps-control -d    # 后台启动 daemon

# 2. 容器启动时挂载 MPS 管道
docker run --rm --gpus all \
  -v /tmp/nvidia-mps:/tmp/nvidia-mps \
  -e CUDA_MPS_PIPE_DIRECTORY=/tmp/nvidia-mps \
  nvidia/cuda:12.6-base bash

# 容器内：所有进程共享 GPU，但**显存仍可能争抢**
# 优势：减少 kernel launch overhead（高并发推理场景提升 30%+）
# 缺点：不隔离显存；NVIDIA 官方已不推荐新部署使用（推荐 MIG）

# cgroup v2 + device controller：只能限制容器能访问哪些 GPU 设备
# 不能限制显存大小——Linux 内核无 GPU 显存 cgroup

# 例：限制容器只能访问 /dev/nvidia0
docker run --rm \
  --device=/dev/nvidia0:/dev/nvidia0 \
  --device=/dev/nvidiactl:/dev/nvidiactl \
  --security-opt=no-new-privileges \
  nvidia/cuda:12.6-base nvidia-smi
# 显存仍由 CUDA driver 管理，无 cgroup 限制

方案对比表：

方案 隔离级别 颗粒度 硬件要求 推荐场景
整卡独占 物理级 整张卡（80GB） 任意 GPU 单任务独享、不混部
MIG 硬件级 1g.5gb ~ 7g.40gb A100/H100 多租户推理、生产
应用层 quota 进程级 百分比（5%~100%） 任意 GPU 单容器多进程、推理服务
CUDA MPS 进程级 无显存隔离 任意 GPU 高并发推理（已不推荐新用）
cgroup v2 设备级 不能限制显存 任意 GPU 仅能限制可见设备数
实际推荐
  • 新部署 + A100/H100 → MIG（硬件隔离，最稳）
  • 新部署 + 其他 GPU → 整卡独占（简单粗暴，但浪费）
  • 推理服务多实例 → 应用层 quota（set_per_process_memory_fraction）
  • 训练任务 → 整卡独占或 MIG，不要用 MPS / quota

22.1. 架构：device plugin 解决什么问题

┌─────────────────────── kubelet ───────────────────────┐
│                                                        │
│   厂商硬件（GPU）                                      │

Device Plugin 框架的核心：

  • K8s 在 v1.10+ 提供 DevicePlugin gRPC 接口，让第三方厂商无需改 K8s 核心代码就能把硬件暴露成可调度资源。
  • v1.26 GA，v1.31+ CDI 支持 GA。
  • 5 个 gRPC 方法：GetDevicePluginOptions / ListAndWatch / Allocate / GetPreferredAllocation / PreStartContainer。

22.4. Pod 中请求 GPU

apiVersion: v1
kind: Pod
metadata:
  name: gpu-pod
spec:
  containers:
  - name: train
    image: pytorch/pytorch:2.8.0-cuda12.6-cudnn9-runtime
    command: ["python", "train.py"]
    resources:
      limits:
        nvidia.com/gpu: 1        # ← 关键：只写 limits
必须用 limits，不能用 requests

K8s 的 extended resources（扩展资源）只支持 limits，写 requests 会被忽略或拒绝。

这跟普通 CPU / 内存不同——不要照搬 CPU Pod 的写法。

调度流程：

1. Pod 创建 → scheduler 检查 nvidia.com/gpu: 1
2. 找节点：nvidia.com/gpu.allocatable >= 1
3. kubelet 调用 device plugin Allocate
4. device plugin 返回：
   - 设备节点挂载（/dev/nvidia0 等）
   - 环境变量（NVIDIA_VISIBLE_DEVICES=0）
   - CUDA 库挂载（驱动路径）
   - CDI 规范（CDI 模式）
5. nvidia-container-toolkit 注入 OCI spec
6. 容器启动

apiVersion: v1
kind: Pod

  containers:
  - name: train
    image: pytorch/pytorch:2.8.0-cuda12.6-cudnn9-runtime
    resources:

        nvidia.com/gpu: 4        # 请求 4 张卡

  nodeSelector:
    nvidia.com/gpu.product: NVIDIA-H100-80GB-HBM3

  # 用污点容忍把 Pod 放到专用节点
  tolerations:
  - key: nvidia.com/gpu
    operator: Exists
    effect: NoSchedule

  # 用 affinity 把 Pod 拉到特定节点
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: kubernetes.io/hostname
            operator: In
            values: ["gpu-node-01", "gpu-node-02"]

22.6. Time-Slicing

原理：把一张物理 GPU 通过 CUDA context 切换"复制"成多份，没有硬件隔离——多个 Pod 共享同一张卡的算力。

# ConfigMap：把 GPU 0 切成 16 份
apiVersion: v1
kind: ConfigMap
metadata:
  name: time-slicing-config
  namespace: kube-system
data:
  any: |-
    version: v1
    sharing:
      timeSlicing:
        resources:
        - name: nvidia.com/gpu
          replicas: 16
    flags:
      migStrategy: "none"
Time-Slicing 的代价
  • 16 个 Pod 同时占用 GPU 时，实际性能 ≈ 1/16（视负载特征）。
  • 适合延迟容忍、轻负载场景：dev / test / 推理服务、低优先级 notebook。
  • 不适合训练：显存不隔离，一个 OOM 会拖累所有 Pod。

22.7. MIG（Multi-Instance GPU）

硬件特性（A100 / H100 才有）：把一张 GPU 切成最多 7 个硬件隔离的 instance，每个有独立显存 + 算力。

# 1. 启用 MIG（GPU 0）
sudo nvidia-smi -i 0 -mig 1     # 需要重启
sudo reboot

# 2. 查看 MIG 档位
nvidia-smi mig -lgip            # 列出所有 MIG instance profile

# 3. 创建 MIG instance
nvidia-smi mig -cgi 0 -C        # GPU 0 上创建一个 MIG instance（最大档位）

# 4. 在 K8s 中暴露 MIG（修改 device plugin 配置）

device plugin 中 MIG 三种策略：

策略 含义 适用
none 不暴露 MIG，只用整卡 训练、独占
single 只暴露 MIG 实例，不暴露整卡 完全 MIG 化集群
mixed 同时暴露整卡和 MIG 混合负载（推荐）

A100 / H100 MIG 档位参考表：

GPU 档位名 Compute Slice Memory Slice 适用
A100 40GB 1g.5gb 1/7 5 GB 小推理
A100 40GB 2g.10gb 2/7 10 GB 中推理
A100 40GB 3g.20gb 3/7 20 GB 大推理
A100 40GB 4g.20gb 4/7 20 GB 小训练
A100 40GB 7g.40gb 7/7 40 GB 等于整卡
A100 80GB 1g.10gb ~ 7g.80gb 同比例 显存翻倍 大模型
H100 80GB 1g.10gb ~ 7g.80gb 同比例 显存翻倍 Hopper 架构 
# 列出所有可用 MIG 档位
nvidia-smi mig -lgip

# 创建特定档位的 MIG 实例
nvidia-smi mig -cgi 0,1,2,3,4,5,6 -C   # GPU 0 创建 7 个 1g.5gb instance
nvidia-smi mig -cgi 0 -C 2g.10gb        # GPU 0 创建 1 个 2g.10gb

# 查看已创建的 instance
nvidia-smi mig -lgi

# 删除所有 MIG instance（恢复整卡）
sudo nvidia-smi mig -dci all
sudo nvidia-smi mig -cgi all            # 重新创建（如果需要）

24.2. 关键最佳实践（2026）

24.2.1. 驱动与 CUDA

  • 驱动装一次（系统级），升级前先看 release notes——驱动升级可能影响 cuDNN 兼容性。
  • CUDA Toolkit 选装：纯跑 PyTorch 用 pip wheel 自带运行时即可；写 CUDA 扩展 / 从源码编译 PyTorch 时才装完整 Toolkit。
  • 多版本共存用 CUDA_HOME + update-alternatives 切换，不要乱改 /usr/local/cuda 符号链接。
  • cuDNN 90% 场景不需要手动装——pip wheel 已自带；手动装的场景主要是编译期依赖。

24.2.2. 容器化

  • nvidia-container-toolkit 1.13+ 启用 CDI 模式——更快、更标准、OCI 兼容。
  • 装完 toolkit 一定要 nvidia-ctk cdi generate 生成 /etc/cdi/nvidia.yaml，否则 CDI 不工作。
  • 多卡机器 / 异构硬件用 CDI，单机老 Docker 用 Legacy。
  • 容器内 NVIDIA_VISIBLE_DEVICES=void 可保留库、屏蔽设备——适合构建阶段。

24.2.3. Kubernetes

  • device plugin 用 Helm 安装——YAML manifest 难改镜像 tag / 副本策略。
  • Time-Slicing 只用于轻负载（dev / 推理 / notebook）；训练用整卡或 MIG。
  • MIG 适合多租户推理服务——A100/H100 最多切 7 个隔离 instance。
  • DCGM-Exporter 是 GPU 监控的事实标准，配合 Prometheus + Grafana Dashboard 12239。
  • 分布式训练不要手写 StatefulSet——用 Volcano / KubeRay / LWS。

24.2.4. 监控一体化

  • GPU 监控：DCGM-Exporter（节点级） → Prometheus → Grafana Dashboard 12239
  • CPU / 内存 / 磁盘 / 网络：node_exporter → Prometheus → Grafana Dashboard 1860
  • 框架层：PyTorch 通过 torch.profiler / torch.cuda.memory_summary() 上报到 TensorBoard / W&B
  • 统一面板：Grafana 用变量 + dashboard link 把 CPU / GPU / 应用层 dashboard 串起来
