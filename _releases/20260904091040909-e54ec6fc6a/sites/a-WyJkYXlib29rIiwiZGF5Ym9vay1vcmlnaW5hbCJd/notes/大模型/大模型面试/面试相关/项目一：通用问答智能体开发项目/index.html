项目一：通用问答智能体开发项目

2026-06-246 min
2.4k chars0 views--viewing

• 设计实现 RAG 智能体核心模块：基于 LangGraph 构建多 Agent 工作流（fetch → query → researchteam → finalanswer 五节点 DAG），整合 ReAct 推理、向量召回、Rerank重排与流式回答能力

职责

• 设计实现 RAG 智能体核心模块：基于 LangGraph 构建多 Agent 工作流（fetch → query → research_team → final_answer 五节点 DAG），整合 ReAct 推理、向量召回、Rerank重排与流式回答能力

• 优化知识检索、语义理解与答案生成流程，实现智能切片（粗切 + LLM 并行标注 + 位置还原）、向量化召回 + DashScope Rerank 重排 + FAQ 混合打分

• 提供API接口与集成方案，构建 JWT + ServiceToken 双认证，发布可独立调用的 Service API（含三级流控），支持企业多场景快速集成与部署。

职责解释

1. RAG智能体核心模块

1.1. 基于LangGraph构建多Agent工作流

4个Agent：

  • Chat：聊天
  • Query：信息检索员
  • Researcher：网页分析师（并发5，Semaphore信号量控制）
  • Final_Answer：报告撰写

协作机制：State流转（不直接对话）

面试官可能追问 + 怎么答
Q：所有 Agent 共用一个 LLM 还是不同？
A： 共用 qwen-flash，通过 state["llm"] 注入。生产可换成不同模型（比如 query 用便宜的，researcher 用贵的），目前为了简化统一。

Q：Agent 之间能"对话"吗？
A：不能。它们是单向数据流，不是多轮对话。如果需要对话，得改成 LangGraph 的循环边。

Q：为什么 Final Answer Agent 不给工具？
A：它的工作是"综合已有 research_context"，给它工具反而可能引入新的不确定性（比如它又调一次检索）。纯综合更可控。
Q：Researcher Agent 并发数怎么定的？
A：经验值。DashScope qwen-flash rate limit 大约 60 req/min，并发 5 + 重试 3 次刚好不超。如果换 OpenAI 可以调到 10-20。

Q：如果 URL 有 100 个怎么办？
A：先在 Query Agent 阶段按向量相似度截 top 20（避免 token 浪费），再并发 5 个 Researcher 跑。
Q：怎么调试 Agent？
A： 每个节点有 print_thinking 开关，把 LLM 输入输出写到 crawl_task_logs 表，前端 ThinkingProcessViewer.vue 实时显示。

1.2. 整合ReAct范式

项目中使用ReAct范式的场景：

Agent 触发场景 工具 ReAct链路
Chat 用户提问 DAG KnowledgeBaseRetrievalTool 思考→检索→观察→再思考→回答
Query 爬虫研究 VectorRecallTool 思考→向量召回→观察→挑 URL→输出
Researcher 单 URL 分析 UrlMetadataTool 思考→拿 markdown→观察→提取信息→输出

Q：怎么调试 ReAct？
通过 astream_events(version="v2") 监听事件：

  • on_chat_model_stream → 拿 LLM 输出（Thought + Action）
  • on_tool_start → 工具调用开始
  • on_tool_end → 工具返回（Observation）
    这些事件写到 crawl_task_logs 表，前端 ThinkingProcessViewer.vue 实时显示。

1.3. 向量召回

向量召回 = 把文本转成"向量数字串"，通过相似度计算找到相关文档。

Embedding（向量化）--> 存储到向量库（Qdrant） --> 相似度检索

  • 向量化使用text-embedding-v2模型，1536维度
  • 向量库使用Qdrant（读音quadrant）,默认使用HNSW索引，这是ANN（近似最近邻）算法，牺牲 1% 精度换 100× 速度
  • 相似度检索：top-k传10，相似度阈值传0.5。余弦相似度（向量夹角cosθ）

Q：向量维度怎么选？
A: 经验值：英文 768-1024 维，中文 1024-1536 维。维度越高语义越丰富，但存储和计算成本线性增加。

Q：HNSW 和 IVF 索引怎么选？
A：HNSW 准确率高（95%+），但内存占用大（10GB+ for 1M 向量）；IVF 内存友好，但准确率稍低（90%）。我们数据量小（< 100K），用 HNSW 默认配置。

Q：向量召回失败的 fallback 是什么？
A：降级到关键词搜索（MySQL LIKE %query_text%）。项目里 FAQ 路径就是这么做的——向量召不到就靠关键词打分。

Q：embedding 模型换了一定要重建索引吗？
A：是的。维度变了（1536→1024）或语义空间变了（text-embedding-v2 → text-embedding-v3），都需要重新 embedding 全部文档。

1.4. Rerank重排

Rerank = 对向量召回的候选结果做"精细重排序"，把最相关的 top_n 喂给 LLM。

项目中使用Qwen3-Reranker-8B对向量召回的数据进行精排，相对于向量召回的速度慢但是精度高。

"Rerank 是对向量召回的候选做精细重排序，解决向量召回'召回率高但精度低'的问题。

原理是用 Cross-Encoder 架构，把 query 和 doc 一起输入 Transformer，输出 [0, 1] 的相关性分数。比向量召回用的 Bi-Encoder 精度高，但慢 100 倍，所以只能精排 20-50条候选，不能全库检索。

我们项目里用阿里百炼的 Qwen3-Reranker-8B，召回 20 条 → Rerank 精排 → 最终 top 5 喂给 LLM。
工业界标配是 Bi-Encoder 召回 + Cross-Encoder 精排两阶段（也叫 Two-Stage Retrieval）。"

1.5. 流式回答能力

流式回答 = LLM 每生成一个 token 就立刻推送给前端，用户看到"打字机效果"，而不是等全部生成完才看到完整答案。

维度 体现
协议层 SSE（Server-Sent Events）单向推送，不是 WebSocket 双向
后端层 FastAPI StreamingResponse + yield，不等 LLM 完成
Agent 层 LangGraph astream_events(v2) 监听 token + tool_call + retrieval_results
前端层 fetch + ReadableStream 实时解析（axios 不支持流式）
反代层 Nginx X-Accel-Buffering: no 防缓冲
UX 层 自动滚动、用户上滚检测、引用实时出现、思考过程可视化

1.6. 意图识别

如果面试官问"为什么没做意图识别"

策略 A：承认 + 解释取舍

"我们没有做显式的意图识别模块。因为：

  1. 业务场景聚焦——系统只服务企业内部 RAG 问答，99% 问题都是'查知识库'，闲聊场景可以由其他系统处理
    . Service 层已经做了路由——每个 Service 发布时配置好'走 Agent 还是走纯召回'，不需要运行时判断 2. Agent 自己会判断——ReAct 范式下，Agent 通过 system prompt 自我决定要不要调用工具

分析用户问题

  1. 如果是关于产品/文档/FAQ 的问题 → 调用 KnowledgeBaseRetrievalTool
  2. 如果是闲聊/与业务无关 → 直接礼貌拒绝
  3. 如果信息不够 → 换个关键词再调一次

1.7. 文档处理

基于微软开源的MarkItDown先转Markdown

  • 用户上传文件
  • 临时存储
  • 切片预览
  • 确认
  • Celery 异步切片
  • Embedding
  • 入 Qdrant + MinIO + MySQL

切片策略：

  • 普通切片：按分隔符切
  • LangChain RecursiveCharacterTextSplitter：指定分隔符
  • 智能切片（LLM 标注边界）：先按3000字符粗切，并发调LLM标记边界，相对位置转绝对位置+边界保护

1.8. 爬虫

项目介绍

这是一套企业级 RAG 知识库系统，叫 DocBase。它解决的核心问题是：企业内部知识散落在文档、Wiki、FAQ、外部网站中，传统的全文搜索答不准、LLM又答不了私有数据。

系统支持三种知识来源：用户上传文档（PDF/Word/PPT/HTML）、FAQ 问答对、外部网站自动爬取。所有内容经过智能切片 → Embedding → 入 Qdrant 向量库之后，用户的提问会走多路召回 + Reranker 重排 + LangGraph Agent 流式回答的链路，每个回答都附带原文引用和可下载的原文档。

系统的工程亮点是：多租户权限（组织树 + RBAC）、对外服务化（每个 Service 有独立 API Key 和流控）、可视化爬虫任务编排（CrewAI + Playwright 反爬）、实时思考过程可视化（Redis + SSE）。

技术栈上后端用 FastAPI + SQLAlchemy + Celery + Redis + Qdrant + MinIO + LangGraph + DashScope，前端用 Vue3 + Element Plus。整套系统跑在 7 个 Docker 容器里，有完整的 deploy.sh 一键部署脚本。
