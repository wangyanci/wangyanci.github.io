3. 项目一:数字员工管理智能体开发项目(202604 — 至今)

项目现状

这是简历上的项目,目前只有 4 条核心职责要点,本节需要深度展开。下面所有架构细节、工具设计、生命周期、监控指标等都是基于这 4 条要点合理推演的"实战叙事",便于面试时讲深讲透。真实代码与细节如有出入,请在面试前对照实际实现微调。

3.1. 项目概述

业务背景:宁波银行内部有大量重复性、规则化的咨询与操作工作(账户查询、转账规则、产品咨询、表单填写等),传统做法是外包人工坐席或写死规则机器人,效率低、扩展性差。数字员工管理平台的目标是让业务人员能可视化配置"数字员工"(即 AI Agent),每个员工一个 Agent,可独立完成一类业务,并支持后续运营监控。

项目目标:

  1. 可配置:业务人员无需写代码,通过管理端表单即可创建并发布一个 Agent
  2. 可扩展:Agent 能力由"工具(Tool)"组成,工具可插拔、可复用
  3. 可观测:每个 Agent 的执行链路、工具调用、Token 消耗、错误率都要可追溯
  4. 多租户:不同业务部门/分行数据隔离,各自配置独立

个人职责:核心开发,负责:

  • Agent 编排框架(基于 LangGraph + 自研 Runtime)
  • Agent 生命周期管理(创建/配置/发布/执行/监控)
  • 工具调用与 RAG 增强体系
  • 多租户后端服务架构(鉴权、流控、日志、会话)

3.3. 架构详解

3.3.1. 整体架构

关键设计:

  1. 管理端与运行时分离:Agent 配置(元数据)走 CRUD,执行时由 Runtime 拉取最新配置并构建 LangGraph 实例。配置变更不需要重启 Runtime。
  2. 多租户隔离:每一层都带 tenant_id,数据库行级过滤、向量库独立 collection、Redis key 加前缀。
  3. 工具与 Agent 解耦:工具是独立注册的"能力",Agent 引用工具 ID,运行时动态加载。

3.3.2. Agent 编排框架(基于 LangGraph State)

State 设计(LangGraph TypedDict):

class AgentState(TypedDict):
    # === 基础上下文 ===
    tenant_id: str                  # 租户
    agent_id: str                   # 当前 Agent
    session_id: str                 # 会话
    user_id: str                    # 用户

    # === 对话与记忆 ===
    messages: List[BaseMessage]     # 完整对话历史
    summary: str                    # 长对话摘要(滚动窗口触发)

    # === 任务执行 ===
    task_input: Dict                # 任务原始输入
    plan: List[Step]                # Plan-and-Execute 模式下的步骤列表
    current_step: int               # 当前执行到第几步
    step_results: Dict[str, Any]    # 每步结果

    # === 工具与 RAG ===
    tool_calls: List[ToolCall]      # 工具调用记录
    tool_results: List[ToolResult]  # 工具结果
    retrieved_docs: List[Doc]       # RAG 召回文档

    # === 决策与控制 ===
    next_action: Literal["think", "act", "answer", "end"]
    retry_count: int                # 重试次数(防循环)
    error: Optional[str]            # 错误信息

核心执行流(ReAct 模式):

[用户输入]
   │
   ▼
[Node: think_node]  注入 system_prompt + 历史 + 召回文档,让 LLM 思考下一步
   │
   ▼ (LLM 输出 think + action)
[Node: should_continue]  判断:是 tool_call? 达到重试上限? 还是最终答案?
   │       │       │
   │       │       └─是 end ──▶ [Node: answer_node] ──▶ END
   │       │
   │       └─是 tool_call ──▶ [Node: act_node]
   │                                │
   │                                ▼ 工具执行
   │                                │
   │                                ▼ 回到 think_node(循环)

为什么用 LangGraph 而不是简单链式:

  • 状态显式可持久化(checkpointer 写 Redis),会话中断可恢复
  • 天然支持 human-in-the-loop(interrupt() 在敏感工具前暂停)
  • 条件边(should_continue)让"思考-行动"循环天然适配 ReAct
  • 子图(subgraph)隔离不同 Agent 内部状态,多 Agent 协作不污染

为什么不用 agentUniverse:agentUniverse 的"模式工厂"适合金融业务已经固化的 SOP 场景;而数字员工平台强调"业务人员可配置",Agent 类型多样、流程需要灵活编排,LangGraph 的低层图编排更适合,且生态更广。

  • 所有写操作工具自动审计日志 + 数据脱敏

3.3.4. Agent 生命周期管理

关键状态机(AgentStatus enum):

状态 允许操作 备注
Draft 编辑、测试、删除 业务人员反复调
Testing 自动评测中 跑 Badcase + 业务评测集
Published 监控、下线 业务用户可调用
Suspended 编辑、恢复 自动触发或管理员手动
Archived 仅查看 软删除

自动挂起机制:Runtime 每分钟统计每个 Agent 的:

  • 错误率 > 5%
  • 平均耗时 > 30s
  • Token 消耗异常(对比基线 +200%)

满足任一自动切到 Suspended,触发企微告警。

3.3.5. 多租户后端架构

租户层级:银行 → 分行 → 部门 → 业务组(支持四级,通过 parent_tenant_id 树形结构)。

隔离策略:

资源 隔离方式
元数据 OB 表每行带 tenant_id,SQLAlchemy 查询自动注入过滤
向量库 Qdrant 按 tenant_id 独立 collection,运行时切换
缓存 Redis key 前缀 t:{tenant_id}:...,防跨租户读
LLM 调用 计费维度包含 tenant_id,行内成本核算到部门
知识库 MinIO 路径 /tenants/{tenant_id}/kb/...
API 限流 Redis 滑动窗口,按 tenant_id + user_id 双维度

认证流(JWT + Refresh Token):

[登录] → access_token (2h) + refresh_token (7d)
[调用 API] → Bearer access_token,中间件解析 → 注入 tenant_id 到 request.state
[过期] → 前端 401 → 自动 refresh → 重放原请求

三级流控:

  1. 全局 QPS:Redis 计数器,防突发
  2. 租户级 QPS:滑动窗口,按 tenant_id
  3. 用户级 QPS:按 user_id,防单个用户刷

3.4. 技术亮点(面试深挖点)

  1. 配置驱动的 Agent Runtime:改 Agent 行为不需要发版,管理端改完即生效(Runtime 每 30s 拉取配置 diff)
  2. 工具调用全链路可观测:每次 LLM 调用、Tool 调用都记录到 executions 表,可按 session 回放完整思考过程
  3. 评测自动化:Agent 发布前自动跑 200 条评测集,Badcase 自动归类(意图错误 / 工具错误 / 幻觉),准确率达标才允许发布
  4. 租户级成本看板:每个 Agent 的 Token 消耗按天/周/月聚合,管理员可看到排行,治理"Token 大户"
  5. 灰度发布:新版本 Agent 先对 5% 租户开放,监控无异常再全量
  6. 敏感操作人工介入:interrupt() 在转账/合同等高风险工具前暂停,后台审核后继续

3.5. 知识考察点(高频追问 + 答案要点)

3.5.1. Q1:LangGraph State 是怎么设计的?为什么这样设计?

要点:

  • 用 TypedDict 显式定义字段,字段类型包含对话、计划、工具调用、决策变量
  • 关键设计:区分"短期上下文(messages)"与"长期决策(plan)";messages 用 add_messages reducer,plan 用自定义 reducer 保证不重复追加
  • 可序列化:所有字段必须可 JSON 化,这样 checkpointer 写 Redis 才能恢复
  • 避免把整个对象塞进 state(如直接放 LLM 实例),否则序列化失败

追问:如果会话很长怎么办?

  • 多层:messages 用滑动窗口 + summary 字段做长对话压缩(超过 20 轮触发 LLM 摘要)
  • 摘要与近 N 轮原文一起塞进 prompt

3.5.2. Q2:意图识别是怎么实现的?

要点(对应岗位"外汇金管家项目"的智能填表):

方案对比:

方案 优点 缺点
规则匹配(关键词+正则) 准确率高、可解释 覆盖窄,扩展差
传统 ML(SVM/FastText) 轻量、可离线 维护成本中等
LLM 分类(Prompt) 灵活、零训练 延迟与成本
LLM + 小模型蒸馏 平衡性能 工程复杂

我们的方案:小模型初筛 + LLM 兜底(分层架构)

  1. 第 1 层(快速):FastText/规则匹配,延迟 < 10ms,覆盖 80% 高频意图(账户查询/转账/汇率)
  2. 第 2 层(兜底):置信度 < 0.85 时调 LLM 分类,Prompt 包含意图清单 + Few-shot 示例,延迟 200-500ms
  3. 第 3 层(澄清):都不确定时返回澄清话术:"您是想查询账户余额,还是要转账?"

追问:用户一次表达多个需求怎么办?

  • LLM 分类时 Prompt 要求输出多标签(而非 argmax),如 ["查余额", "顺便问汇率"]
  • Runtime 按列表顺序串行执行多个子任务,中间状态保留
  • 或并行执行后合并答案(简单查询)

3.5.3. Q3:Agent 编排 vs 普通调用 vs Workflow 区别?

要点(可直接背诵):

类型 核心特征 适合场景 主要风险
普通 LLM 单/多轮文本生成 问答、摘要 幻觉、不能执行动作
Workflow 固定流程编排 审批流、ETL 灵活性不足
RAG 检索后生成 知识库问答 检索质量决定上限
Agent 动态规划+工具调用+反馈修正 复杂任务自动化 不可控、成本高、调试难

我们项目多种模式并存:简单问答用 LLM 直接调,知识库问答用 RAG,填表/查询类用 Agent + Workflow 混合。

3.5.4. Q4:RAG 检索流程、回退机制是什么?

要点:

[Query] → Query Rewrite(改写)
       → Embedding(向量化)
       → 向量召回(top_k=20,余弦相似度)
       → BM25 关键词召回(top_k=10,补充)
       → RRF 融合去重
       → Rerank 精排(Qwen3-Reranker-8B,top 5)
       → 阈值过滤(相似度 < 0.5 丢弃)
       → 构造 Prompt + 上下文
       → LLM 生成答案
       → 引用溯源

回退机制(3 级):

  1. 召回回退:向量召不到 → BM25 兜底 → 仍无 → 返回"知识库暂无相关信息,建议人工咨询"
  2. 质量回退:Rerank 后相似度均 < 阈值 → 不强行编,LLM Prompt 加 "请回答'我不确定'"
  3. 生成回退:LLM 输出格式不符(比如意图分类返回非枚举值)→ 重试 1 次 → 还失败 → 走兜底话术 + 记 Badcase

追问:向量检索不准确怎么排查?

按"漏召 / 排错 / 语义漂移"三类分别排查:

4.5.1. Q1:RAG 提升召回准确率有哪些手段?

  • 金融场景必备:产品代码、合同编号、政策文件名,BM25 完胜向量

4.5.3. Q3:Query 改写怎么做的?

4.5.7. Q7:龙虾的三层/五层架构(OpenClaw Architecture)

黑话提醒

"龙虾" = OpenClaw(团队内部对 OpenClaw 的中文昵称,因为 OpenClaw 发音像 "Open Claw" = "开爪",借龙虾的钳子意象)。所以面试官问"龙虾的三层/五层架构",就是问 OpenClaw 的分层架构。

OpenClaw 是什么:Local-first、Gateway-first 的开源 AI Agent 框架,定位与 LangGraph 完全不同(LangGraph 是图编排引擎,OpenClaw 是消息优先 + 本地优先的 Agent 运行时)。

三层架构(高层视角):

  1. Channel Layer(渠道适配层):对接 WhatsApp/Telegram/Discord/Slack/钉钉/企微 等 24+ 消息渠道,做协议适配 → 统一消息格式
  2. Gateway(网关层):消息路由、身份认证、限流、负载均衡
  3. Agent Runtime(Agent 运行时):执行感知-推理-行动循环,管理 Agent 生命周期

五层架构(细分视角):

层 职责
1. Channel System(渠道适配层) 消息渠道协议差异,标准化为内部格式
2. Gateway(网关路由层) 消息路由、身份认证、限流、负载均衡
3. Plugin & Skills(插件与技能系统) 封装可复用工具能力(发邮件、查数据库、调外部 API 等)
4. Agent Runtime(Agent 运行时) 协调感知-推理-行动循环,管理 Agent 生命周期
5. Memory & Knowledge(记忆与知识) 短期对话上下文 + 长期知识存储(本地 Markdown)

加上 LLM Provider(模型提供层) 和 Local Execution(本地执行层),完整是 7 层架构:

渠道适配层 → Gateway → Plugin & Skills → Agent Runtime
           → Memory & Knowledge → LLM Provider → Local Execution

核心设计哲学:

  1. Local-first(本地优先):所有数据(对话历史、记忆、知识库、配置)存本地 Markdown 文件,而非云数据库。
    • 好处:数据主权(隐私合规)/ 可移植性(换设备即恢复)/ 可观测性(Markdown 可读可搜)
  2. Gateway-first(网关优先):先有 Gateway,再有 Agent。
    • 其他框架"模型优先"(先加载 LLM,再考虑消息输入输出);OpenClaw 反过来:Gateway 先统一消息入口,Agent Runtime 不关心消息来自哪个渠道,只负责任务执行
  3. 极简大脑(pi-coding-agent SDK):系统提示词 + 工具定义加起来 < 1000 tokens,核心只有 4 个工具:read、write、edit、bash
    • 没有内置 plan mode、to-do 系统、MCP 支持、权限弹窗,甚至不绑定特定模型

架构图:

为什么龙虾会被问到:面试官可能想考你对非 LangChain 系 Agent 框架的了解,看你是否只熟悉主流框架,还是对Local-first + Gateway-first 这种设计哲学有认知。

对比记忆:LangGraph = 图引擎(开发者画图)、agentUniverse = 模式工厂(填角色进 PEER/DOE)、OpenClaw = 消息优先 + 本地优先(对接多渠道,数据归用户)。

4.5.10. Q10:Planner Agent / ReAct Agent / A2A Agent 范式对比

范式 工作原理 适用 缺点
Planner Agent 先全局规划 → 按步骤执行 多阶段长链路 计划质量是瓶颈
ReAct Agent 思考+行动+观察循环 边想边查任务 慢、长任务易跑偏
A2A(Agent-to-Agent) 多个 Agent 对等通信 强协作任务 通信开销、难调试
Supervisor 主 Agent 调度子 Agent 任务分发 主 Agent 成瓶颈

实战:Plan-and-Execute(Planner)+ReAct 细执行 是金融场景的最佳实践。

6.2. 框架与技术对比

6.2.1. Q6:介绍 ReAct(高频)

完整答案:

ReAct = Reasoning + Action(+Observation)。模型在"思考 → 调用工具 → 观察结果"之间循环。

优点:

  • 可解释(可看每步 thought)
  • 纠错能力(根据工具返回调整策略)
  • 工具协同(适应多次外部交互)
  • 幻觉相对少(持续获取外部信息)

缺点:

  • 慢、烧 Token
  • 循环风险(需 max_iterations 限制)
  • 依赖工具返回质量
  • 长任务易跑偏

适用:边想边查场景(代码调试、客服导购、复合工具调用)。
不适用:简单问答、确定性任务、实时性要求高。

实战技巧:Plan-and-Execute(规划)+ ReAct(执行) 混合;astream_events 调试;handle_parsing_errors=True 防格式崩溃。

6.2.2. Q7:Plan-and-Execute vs ReAct(高频)

完整答案:

维度 Plan-and-Execute ReAct
工作方式 先全局规划 → 逐步执行 边想边执行
结构 清晰、可控 灵活
避免跑偏 是 否
适合长链路 是 否
计划质量 是瓶颈 不存在

6.2.3. Q8:Self-Ask、CoT、ToT、Reflection 模式对比(高频)

Self-Ask:

  • 关键:向自己提问(ReAct 简化版)
  • 把大问题拆成可回答的小问题
  • Google 2022 提,适合多跳问答(multi-hop QA)
  • 优点:幻觉少、显式暴露问题结构;缺点:不适合非问答、推理粒度有限
  • 实战:多作为技术模式被吸收进更大系统

CoT(Chain of Thought):

  • 让模型显式写中间推理步骤
  • 严格说是提示/推理技术,不是 Agent 范式
  • 数学/逻辑推理准确率提升 30%+
  • 缺点:不调外部工具、可能"事后合理化"、长 CoT 贵
  • 适用:数学/逻辑、多步问答、复杂决策解释

ToT(Tree of Thoughts):

  • 推理从"一条链"扩成"多条候选路径"
  • 2023 Princeton & Google
  • 思维分解 → 生成 → 评估 → 搜索(BFS/DFS)
  • 优点:可回溯、可剪枝;缺点:慢、贵、评估器设计难
  • 适用:数学证明、24 点、策略游戏、复杂决策

Reflection:

  • 执行后反思,根据失败结果总结修正策略
  • 不是简单重试,而是从失败提取可执行修正
  • 优点:对代码修复、测试失败、工具调用失败很有效
  • 缺点:反思质量依赖错误信息质量、可能反思错方向、增加循环
  • 适用:自动修复测试、代码生成迭代、运维排查

6.2.4. Q9:OpenClaw 架构(也叫"龙虾")

五层架构(细分):Channel System → Gateway → Plugin & Skills → Agent Runtime → Memory & Knowledge

  2. ORM 模型元数据:SQLAlchemy 的 declarative_base() + 元类管理表名、字段、索引等元数据。

6.3. LLM/RAG 类

6.3.1. Q11:RAG 检索的流程,回退机制是什么?

完整答案(参考 2.5 Q4 + 3.5 多次覆盖):

流程:Query Rewrite → Embedding → 向量召回(top_k=20)→ BM25 召回 → RRF 融合 → Rerank 精排(top 5)→ 阈值过滤 → Prompt 构造 → LLM 生成 → 引用溯源

3 级回退:

  1. 召回回退:向量召不到 → BM25 兜底 → 仍无 → 返回"知识库暂无"
  2. 质量回退:Rerank 后相似度 < 阈值 → Prompt 加"如不知道请回答不清楚"
  3. 生成回退:格式不符 → 重试 1 次 → 还失败 → 兜底话术 + 记 Badcase

6.3.2. Q12:RAG 如何提升召回准确率?

完整答案(参考 3.5 Q1):

  • 索引:chunk 200-500 token、overlap 10-20%、metadata 过滤、Hybrid Search
  • Query:Query Rewrite(同义词扩展/上下文补全)、HyDE、Multi-Query
  • 检索:调 k 值、阈值、过滤条件
  • 后处理:Rerank、去重、相关性反馈
  • 数据:去重、近重复检测、数据质量

6.3.3. Q13:BM25 关键词检索怎么配合向量?

完整答案(参考 3.5 Q2):

互补:向量擅长语义匹配,BM25 擅长精确匹配(专有名词/缩写/型号)。金融场景必备(产品代码、合同编号)。

融合方式:

  • RRF(倒数排名融合,简单稳定)
  • 加权打分(线性组合,需调权重)

实现:Qdrant 自带 BM25;ES/Haystack 也有;或自己用 rank_bm25 库。

6.3.4. Q14:Query 改写思路

完整答案(参考 3.5 Q3):

  • 上下文补全:把对话历史里省略的主语补全("它呢?" → "美元兑人民币汇率呢?")
  • 同义词扩展:"报销" → "费用补偿/票务抵扣"
  • HyDE:先让 LLM 假设答案文档,再 embedding 假设文档检索
  • 实现:Prompt + Few-shot,成本可控

6.3.5. Q15:向量检索 vs 普通检索的区别

完整答案:

  • 普通检索(BM25/全文):基于词频统计(词袋模型),精确匹配好,但语义差("汽车"和"轿车"不匹配)
  • 向量检索:基于 Embedding 语义空间,召回率高,但精度低(可能召出不相关)
  • 底层:BM25 是 Lucene 倒排索引;向量是 ANN(HNSW/IVF)
  • 速度:BM25 快(< 50ms);向量取决于 top_k 和索引(< 200ms)
  • 工业界标配:Two-Stage Retrieval(Bi-Encoder 召回 + Cross-Encoder 精排),向量召 20 → Rerank top 5 → 喂 LLM

6.3.6. Q16:检索结果不准确怎么排查?

完整答案(参考 2.5 Q4):

按"漏召 / 排错 / 语义漂移"三类分别排查:

Query 侧:k 太小、阈值太高、纯向量没 BM25、Query 改写未做

索引侧:

  • chunk 切太碎(语义被割裂)或太大(召回不准)
  • overlap 不够(上下文丢失)
  • metadata 过滤条件写错
  • 重复/近重复文档没去重

Embedding 侧:

  • 领域不适配(金融术语未在训练集)
  • 维度/池化方式不对
  • 模型太老或质量差

Rerank 侧:

  • rerank 模型太轻
  • cross-encoder 输入被 truncate 太短

6.3.7. Q17:LLM 返回不符合预期怎么排查?

完整答案:

  1. 症状先判断:格式错?幻觉?事实错?逻辑错? 一些能一眼看出
  2. 稳定 vs 偶发:temperature=0 跑 5 次。稳定错说明 Prompt/数据有系统问题;偶发错说明模型能力边界或随机性
  3. 日志追踪:用 LangSmith/自研 Hook 定位哪个点开始跑偏 — 是 Prompt 问题、工具调用、知识质量、还是 LLM 执行中逐渐偏离
  4. Prompt 工程:加 CoT、加 Few-shot、加约束、加 System Prompt 角色
  5. 数据/工具:换检索源、调 Rerank 阈值、修工具 bug
  6. 换模型:同 Prompt 换更强模型,验证是不是能力问题
  7. 自动化断言:用 LLM-as-Judge 或规则匹配自动评估,看 Badcase 分布

6.3.8. Q18:RAG 知识库如何处理非结构化数据(财报)

完整答案(参考 3.5 Q7 追问):

双层解析架构:

  1. 优先:外部专业 OCR API(高准确率)
  2. Fallback:pdfplumber 本地解析(免费可靠)

提高准确率手段:

  • 表格分类:关键词匹配 + 内容特征匹配(双重匹配,避免标题被截断时仍能正确分类)
  • 科目标准化:subject_mapping.py 的 57 个映射,统一中英文/不同表达
  • 数据清洗:LLM 辅助(OCR 纠错、字段抽取、嵌套数值)
  • 合计行自动补算:CalcAgent 在计算前自动补算缺失的合计科目(如"流动资产合计"缺失时累加各项)
  • 多页表格拼接:跨页表格提取后按类型归类合并

6.5. 算法 / 训练类(中级岗位考察)

6.5.1. Q28:强化学习训练时的难点有哪些?

完整答案:

  • 奖励函数设计:难以量化"好的回答",稀疏奖励问题严重
  • 奖励 Hacking:模型学会钻空子获取高奖励(如 RLHF 中变长变啰嗦)
  • 样本效率低:需要大量环境交互
  • 训练不稳定:策略崩塌、训练崩溃,超参敏感
  • 分布漂移:训练分布与部署分布不一致
  • 安全性:RL 可能生成有害内容,需对齐约束

6.5.2. Q29:预训练和 SFT 的关系,为什么用 SFT?

完整答案:

关系:SFT(Supervised Fine-Tuning)是预训练的"专业化"。

  • 预训练:海量无标注文本,训练基础语言能力(语言建模目标)
  • SFT:在预训练基础上,用标注的指令-回答对微调,适配特定任务

为什么用 SFT:

  • 预训练模型只会"续写",不会"对话/指令跟随"
  • SFT 让模型学会理解指令、按格式回答
  • 比 RLHF 简单、稳定、便宜
  • 是 RLHF/DPO 的前置步骤(先 SFT 再 RLHF)

6.5.3. Q30:训练大模型时,需要的新的数据量是多少?

完整答案(经验值,具体看模型规模):

  • 预训练:TB 级文本(7B 模型约 1-2T token)
  • SFT:万-百万级对话(常见 10K-100K 条高质量样本)
  • RLHF:万-十万级偏好对(常见 10K-50K)
  • DPO:同 RLHF 量级,无需奖励模型
  • 继续预训练(Continued Pre-training):GB-TB 级领域文本

数据质量 > 数量:1 万条高质量 > 10 万条低质量。

6.5.4. Q31:SFT 有哪些关键过程?

完整答案:

  1. 数据准备:清洗、去重、质量过滤、格式化(ChatML/ShareGPT)
  2. 底座选择:Qwen/LLaMA/ChatGLM,按需选规模
  3. 微调方式:全参数(贵,效果好) / LoRA(省显存) / QLoRA(再省)
  4. 训练配置:学习率(1e-5 ~ 5e-5)、batch size、epoch(2-5)、warmup
  5. 评测:验证集 + 业务 Badcase,人工抽检
  6. 合并/部署:LoRA 合并权重 → 量化(可选)→ vllm/TGI 部署
  7. 监控:训练 loss 曲线 + 业务指标

6.5.5. Q32:微调和预训练有什么关系,需要注意什么?

完整答案:

关系:微调是预训练的继续,基于预训练权重继续训练。

注意事项:

  • 学习率:比预训练低 1-2 个数量级(1e-5 vs 1e-4)
  • 过拟合:小数据集易过拟合,用 early stopping、正则化
  • 灾难性遗忘:混入通用数据(5-10%),保留基础能力
  • 评估:不仅看 loss,看业务指标(答案质量、幻觉率)
  • 超参:epoch 2-5 起步,batch size 越大越好,gradient accumulation 补足
  • 数据平衡:各类任务均匀分布,避免偏向单一模式

6.7.2. Q39:智能问答助手使用哪些行业相关工具,首 Token 耗时?

  • 流式预热(prefill + decode 并行)

实测:qwen-flash 首 token 200-400ms,整句生成 2-5s。

6.7.3. Q40:智能体搭建框架选择

完整答案(参考 5.2 Q2):

根据场景选择:

  • 业务 SOP 固化:agentUniverse(PEER/DOE 模式)
  • 灵活编排 + 多 Agent:LangGraph(图引擎)
  • 快速原型 + 单 Agent:LangChain(上层 API)
  • 可视化拖拽:Dify/Coze(业务人员友好)

我们的项目:数字员工(灵活)+ 通用问答(多 Agent DAG) → 选 LangGraph。

6.7.4. Q41:性能瓶颈如何调优?

完整答案:

定位方法:

  1. APM:SkyWalking/Datadog 看各服务耗时
  2. LangSmith:看 LLM 调用链(每个 LLM 的输入/输出/耗时)
  3. 火焰图:Python cProfile/py-spy 找热点
  4. 数据库慢查询:MySQL slow log

常见瓶颈:

  • LLM 调用慢 → 换小模型/并行/缓存
  • 向量检索慢 → 调 HNSW efConstruction/ef / 减少 top_k / 加缓存
  • 数据库慢 → 加索引/读写分离/分库分表
  • 工具调用慢 → 异步化(并发多个工具)
  • 流式卡顿 → Nginx 缓冲/X-Accel-Buffering

6.8. 其他高频题

6.8.1. Q42:知识库切片召回

完整答案:

切片策略:

  • 按字符数(简单但粗暴)
  • 按分隔符(段落/句子,LangChain RecursiveCharacterTextSplitter)
  • 按语义(LLM 标注边界,慢但准)
  • 按结构(Markdown 标题、HTML 标签,适合结构化文档)

召回优化:

  • chunk 大小:200-500 token(平衡上下文与精度)
  • overlap:10-20%(避免边界信息丢失)
  • 元数据:文档来源/章节/时间(支持过滤)
  • 多级索引:段落级 + 文档级(先粗后细)

6.8.2. Q43:智能问答平台设计

完整答案(综合):

架构层:

  • 前端(Vue3 + 流式渲染)
  • 网关(Nginx + 认证)
  • API(FastAPI)
  • AI 编排(LangGraph)
  • 异步(Celery)
  • 存储(MySQL + Qdrant + MinIO + Redis)
  • 外部 LLM(DashScope)

核心模块:

  • 文档处理(上传/切片/Embedding)
  • 检索(向量召回 + BM25 + Rerank)
  • Agent 工作流
  • 流式回答
  • 多租户管理

运营:

  • 评测自动化
  • Badcase 闭环
  • 监控告警
  • 灰度发布

6.8.3. Q44:表单填写助手的设计要点

完整答案:

  • 字段抽取:从对话/文档抽取字段值
  • 默认值:根据上下文/历史预测默认值
  • 校验:实时校验(格式/范围/必填)
  • 跳过/补齐:已填字段跳过,缺失字段主动询问
  • 敏感字段:密码/验证码走安全通道
  • 多步表单:分步填,支持上一步/下一步
  • 保存草稿:中断后可恢复
  • 提交确认:提交前展示完整表单,确认后提交

6.8.4. Q45:前端同源策略限制了哪些内容

完整答案:

限制:

  • 跨域 AJAX/Fetch 请求默认被拒
  • 跨域读取 Cookie/LocalStorage
  • 跨域 DOM 操作(iframe)

不受限:

  • <img>/<script>/<link> 标签(历史原因)
  • 表单提交(可跨域)

解决方案:

  • CORS(推荐):服务端 Access-Control-Allow-Origin
  • JSONP(旧方案,只支持 GET)
  • 代理:同源服务代理跨域请求
  • postMessage:iframe 跨域通信

AI 应用注意:流式 SSE 也受 CORS 限制,服务端要正确配置 CORS 头。

6.8.5. Q46:智能体对前端的影响

完整答案:

  • 流式渲染:逐 token 渲染,前端需要 ReadableStream 支持
  • 思维可视化:展示 Agent 思考过程(Thought/Action/Observation)
  • 富交互卡片:文本/表格/图表/按钮混合,需要动态组件渲染
  • 不确定状态:Loading/部分结果/重试按钮设计
  • 错误降级:优雅降级 UI,不卡死
  • 多模态:语音/图像输入输出
  • 个性化:基于上下文的 UI 适配

技术栈:Vue 3 + ECharts/Chart.js + Markdown-it + KaTeX。

8.4. 常见雷区

雷区 应对

八股答不上来 诚实说"这块不太熟,我了解的是...",不要硬编
跑题/超时 1 分钟自介 + 5 分钟项目 + 留时间给追问

如果时间不够:

"时间有限,我先讲重点 X、Y、Z,如果有疑问可以追问。"
