title: "Codebase architecture"

Codebase architecture

This page is the source-level architecture map for OpenClaw: directories, ownership boundaries, and the main runtime call paths.

Companion pages:

  • Gateway architecture — WebSocket roles, pairing, canvas URLs, protocol summary.
  • Plugin internals — capability matrix, loader layers, hook ownership, compatibility signals.

1. System context

OpenClaw ships as an npm package (openclaw) with a Node 22+ ESM TypeScript implementation. At a high level:

  • A gateway process owns messaging integrations, exposes a typed WebSocket API plus HTTP surfaces (control UI, optional OpenAI-compatible HTTP, canvas host, plugin routes).
  • The openclaw CLI configures the system, runs doctor checks, talks to the gateway as a client, and can run the gateway in the foreground.
  • Plugins in extensions/* extend channels, model providers, tools, HTTP routes, and hooks. They load through src/plugins/loader.ts and register into a runtime registry.
  • Native apps under apps/* are clients of the gateway protocol (not where channel business logic lives).

2. Repository top level

Path Purpose
src/ All core TypeScript: CLI, gateway, agents, config, routing, plugins, infra, media, tests colocated as *.test.ts.
extensions/* Workspace plugins (one package per id in normal cases). Each has openclaw.plugin.json and its own package.json.
apps/ macOS, iOS, Android, and related native projects; consume the gateway protocol.
docs/ Mintlify documentation. Generated config schema and other artifacts live under docs/.generated/.
dist/ pnpm build output; published package main and exports point here.
skills/ Bundled skill assets used by the agent stack where configured.
scripts/ Repo automation (packaging, i18n, commit helpers, and so on).

User-facing docs and UI say plugin; the internal directory name extensions/* is kept for tooling and history (see repository guidelines).

Files at src/ root worth remembering:

  • src/entry.ts — CLI early argv handling; loads src/cli/run-main.js for full CLI.
  • src/index.ts — Dual behavior: library lazy exports via library.js when imported, CLI when executed as main via runLegacyCliEntry.
  • src/library.ts — Stable programmatic exports (loadConfig, createDefaultDeps, session helpers, and so on).

4. Packaging and build

  • package.json bin.openclaw points at openclaw.mjs, which boots compiled output in dist/.
  • package.json exports exposes . and many openclaw/plugin-sdk/* subpaths for extensions.
  • pnpm build produces dist/; gateway and CLI run against this in production installs.
  • Development uses pnpm openclaw / pnpm dev so contributors rarely run raw dist/ locally.

5. CLI architecture

5.1. Program construction

  • src/cli/program/build-program.ts — builds the root Commander, enables positional options, wires help, pre-action hooks, and calls registerProgramCommands.
  • src/cli/program/command-registry.ts — lazy registration: each top-level command (for example onboard, gateway, doctor) is loaded via dynamic import() when that command is the primary argv target. This keeps cold start fast.
  • src/cli/program/register.subclis.ts — optional sub-CLIs and additional registration paths.
  • src/cli/deps.ts — createDefaultDeps() is the shared dependency bucket injected into gateway context and many commands (filesystem, exec, logging).

5.2. Startup sequence (runCli)

src/cli/run-main.ts:

  1. Normalizes argv (Windows), parses --profile early, applies profile env.
  2. Loads CLI dotenv quietly, normalizes env, optionally ensures openclaw is on PATH.
  3. Asserts supported Node runtime.
  4. May short-circuit to root help or tryRouteCli (special argv routes).
  5. Enables console capture, builds the program, installs unhandled rejection and uncaught exception handlers.
  6. Resolves the primary command from argv; if known, registers only that core command module first, then sub-CLIs.
  7. Unless skipped for fast paths, loads validated config and registerPluginCliCommands from src/plugins/cli.ts so plugins contribute CLI flags.
  8. Parses argv with Commander.

5.3. tryRouteCli

src/cli/route.ts handles argv patterns that should not go through the full Commander tree (for example dedicated utilities). Extend here only when the full program tree is intentionally bypassed.

6. Gateway architecture

6.1. Server bootstrap

  • src/gateway/server.impl.ts — startGatewayServer: resolves config at start, constructs channel manager via createChannelManager in src/gateway/server-channels.ts, builds HTTP and WebSocket stack through createGatewayRuntimeState (src/gateway/server-runtime-state.ts), wires node registry, session subscribers, cron, and reload hooks.
  • src/gateway/server-startup.ts — startGatewaySidecars: session lock cleanup, optional browser control server, Gmail watcher, model prewarm, channel start, internal hooks, plugin services, memory backend, restart sentinel wake.
  • src/gateway/config-reload.ts — config hot reload paths used when operators patch config at runtime.

6.2. WebSocket request routing

All JSON-RPC-style methods flow through handleGatewayRequest in src/gateway/server-methods.ts:

  1. authorizeGatewayMethod — combines role policy (src/gateway/role-policy.ts) and operator scopes (src/gateway/method-scopes.ts). The health method is special-cased.
  2. Control-plane write budget for config.apply, config.patch, update.run (src/gateway/control-plane-rate-limit.ts).
  3. Handler lookup: opts.extraHandlers[method] (plugin-registered gateway methods) first, else coreGatewayHandlers[method].
  4. The handler runs inside withPluginRuntimeGatewayRequestScope so plugin runtime can call back into the gateway (for example subagent dispatch in src/gateway/server-plugins.ts).

6.3. Core gateway methods (merged handler map)

coreGatewayHandlers spreads the following modules from src/gateway/server-methods.ts (each exports a map keyed by method string):

voicewake.ts Voice wake forwarding hooks.
health.ts Health and readiness aggregation.
channels.ts Channel status, start/stop, probes coordinated with ChannelManager.
chat.ts Chat completions style runs, streaming buffers, abort controllers.
cron.ts Cron store and scheduling RPC.
devices.ts Device identity and pairing flows at the gateway.
doctor.ts Doctor checks invoked remotely.
exec-approvals.ts Exec approval queue for gated tools.
web.ts Web channel and related control.
models.ts Model listing and catalog queries.
config.ts Config get, apply, patch with auth gates.
wizard.ts Configure wizard bridging to src/wizard/.
talk.ts Talk or voice-related gateway RPCs.
tools-catalog.ts Tool listing for UIs.
tts.ts TTS requests.
skills.ts Skills discovery and status for sessions.
sessions.ts Session CRUD and usage surfaces.
system.ts System-level operations (presence, shutdown hooks, and similar).
update.ts In-place update triggers.
nodes.ts / nodes-pending.ts Node commands, capabilities, pending approvals.
push.ts Mobile or push bridge hooks.
send.ts Outbound message send with idempotency.
usage.ts Usage stats and billing-related summaries.
agent.ts / agents.ts Primary agent run and multi-agent helpers.
browser.ts Remote browser automation RPCs.

Plugins may add methods by contributing to extraHandlers during gateway setup (see src/gateway/server-plugins.ts and plugin runtime types).

6.4. Channel manager

src/gateway/server-channels.ts implements createChannelManager:

  • Tracks per-account abort controllers, in-flight start promises, and runtime snapshots for status APIs.
  • Uses getChannelPlugin / registry to resolve the implementation for each ChannelId.
  • Applies restart backoff (CHANNEL_RESTART_POLICY) on failures.
  • Passes optional PluginRuntime["channel"] into channel gateway contexts so external channel plugins can call SDK reply and routing helpers without importing src/** directly.

Bundled channel implementations are imported from extensions/* and listed in src/channels/plugins/bundled.ts. Dynamic resolution for a channel id goes through loadChannelPlugin (src/channels/plugins/load.ts), which reads the active plugin registry (getActivePluginRegistry()).

6.5. Protocol and typing

  • src/gateway/protocol/ — TypeBox schemas, error codes, and shared request and event types. JSON Schema generation and Swift model codegen consume this layer.
  • src/gateway/server/ws-connection/ — Frame handling, auth context, message handler pipeline after the socket connects.

6.6. HTTP surfaces

HTTP entry and feature flags are split across:

  • src/gateway/server-http.ts and related helpers for static control UI, OpenAI-compatible endpoints when enabled, sessions history endpoints, plugin HTTP routers (src/gateway/server/plugins-http/), TLS, and security headers.

Exact routes change over time; when adding HTTP APIs, follow existing patterns in src/gateway/ and mirror documentation in docs/gateway/ when user-visible.

7. Agent execution path (detailed)

7.1. Gateway to embedded runner

  1. agent WS method lands in src/gateway/server-methods/agent.ts.
  2. The handler resolves session key, workspace, routing, delivery options, idempotency, and pairing policy, then calls dispatchAgentRunFromGateway.
  3. That calls agentCommandFromIngress with an ingress object describing the originating channel, account, thread, images, thinking level, lane, and optional overrides.
  4. agentCommandFromIngress lives in src/agents/agent-command.ts and is re-exported from src/commands/agent.ts (gateway and OpenAI-compatible HTTP import the commands barrel). It prepares execution via prepareAgentCommandExecution and runAgentAttempt in the same module.
  5. runEmbeddedPiAgent (src/agents/pi-embedded-runner/run.ts) performs the actual model loop, tool calls, streaming callbacks, and transcript writes.

7.2. Invariants for transcript writes

Gateway server method code and tests emphasize: Pi session JSONL must preserve the parentId chain. Use SessionManager.appendMessage (or a wrapper) rather than ad hoc JSONL appends. See src/gateway/server-methods/AGENTS.md in the repo.

7.3. CLI agent command

src/cli/program/register.agent.ts registers openclaw agent. The default path calls src/commands/agent-via-gateway.ts so the CLI acts as a gateway client (same server-side agent method as WebChat and other clients). With --local, the CLI runs the embedded stack in-process via src/agents/agent-command.ts instead of remote WS.

8. Routing and auto-reply

  • src/routing/ — Session key derivation, account normalization, route tables, delivery target resolution. Used by both gateway agent ingress and channels when deciding which agent workspace should answer.
  • src/auto-reply/ — Reply templates, getReplyFromConfig, directive parsing, and the bridge from inbound messages to dispatch paths that ultimately trigger agent runs or quick replies.

9. Plugins and extensions

9.1. Load order (conceptual)

  1. Discovery — src/plugins/discovery.ts enumerates candidates from config, workspace, global roots, and bundled extensions.
  2. Manifests — src/plugins/manifest-registry.ts reads openclaw.plugin.json (native manifest) and supported bundle formats.
  3. Load — src/plugins/loader.ts loadOpenClawPlugins uses jiti with a carefully constructed alias map (src/plugins/sdk-alias.ts) so openclaw/plugin-sdk/* resolves to the in-repo SDK without letting extensions import arbitrary core internals.
  4. Activate — registry entries record providers, channels, tools, gateway methods, HTTP routes, and hooks. setActivePluginRegistry publishes the registry for channel loaders and runtime.

9.2. Extension package rules

Inside extensions/<id>/:

  • Put runtime dependencies in that package dependencies (not the repo root), and avoid workspace:* in dependencies for npm compatibility in plugin installs.
  • Production code should import openclaw/plugin-sdk/* and local barrels (api.ts, runtime-api.ts), not src/ paths from another package.

See Plugin internals for capability shapes, hook-only plugins, and compatibility labels surfaced in openclaw doctor and openclaw plugins inspect.

10. Supporting subsystems

Area Entry concepts
Memory src/memory/ — prompt sections, optional backends started from gateway sidecars.
Context engine src/context-engine/ — prompt context assembly for agents.
Media src/media/ — inbound media normalization; understanding registry under src/media-understanding/.
Browser src/browser/ — Playwright-based automation; CLI and gateway share server context patterns.
Canvas src/canvas-host/ — HTTP host for agent-created canvases and A2UI bundles (pnpm canvas:a2ui:bundle when changing bundled UI).
Cron src/cron/ — scheduled tasks; gateway exposes cron methods and persists store paths.
TTS src/tts/ — provider registry for speech output.
Image generation src/image-generation/ — provider registry for image tools.
ACP src/acp/ — optional ACP bridge behavior when enabled in config.
Daemon src/daemon/ — supervised gateway argv and macOS launch integration helpers.
Pairing src/pairing/ — shared pairing stores feeding gateway device flows.

11. Configuration and on-disk state

  • Config loads from src/config/config.ts with schema validation and merge rules; generated docs live under docs/.generated/ and drift checks run via pnpm config:docs:check when schema changes.
  • Sessions metadata is JSON-backed under src/config/sessions/ helpers; default state dir is under ~/.openclaw/ for installs (see user-facing security notes in docs: never commit real paths or tokens).

12. Install scripts (separate repo)

Install scripts served from https://openclaw.ai/* live in the sibling openclaw.ai repository (public/install.sh, and related). Core repo changes that affect install UX often need a coordinated change there.

13. Tests and quality gates

Command Role
pnpm check Lint and format (oxlint, oxfmt).
pnpm test Vitest across the repo; prefer pnpm test -- <path> -t "name" for scoped runs.
pnpm build TypeScript compile to dist/; required when changes affect exports, bundling, or lazy import boundaries.
pnpm tsgo Typecheck pass used in CI workflows.

Gateway-heavy changes should include or extend tests beside src/gateway/*.test.ts. Channel changes should consider all bundled and extension channels when touching shared routing or pairing.
