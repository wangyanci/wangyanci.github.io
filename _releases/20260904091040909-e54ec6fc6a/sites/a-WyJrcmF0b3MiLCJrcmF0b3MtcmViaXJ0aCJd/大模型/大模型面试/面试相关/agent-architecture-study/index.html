大模型智能体设计架构学习资料

本文面向希望系统学习 LLM Agent 架构、设计模式和工程落地的读者。重点不是罗列概念，而是解释每种模式解决什么问题、什么时候适合用、有哪些风险、如何组合成可上线的智能体系统。

1. 智能体基础概念

大模型智能体，LLM Agent，是以大语言模型为核心决策器，结合工具调用、状态管理、任务规划、记忆、反馈评估和安全控制的任务执行系统。

普通大模型更像“回答问题的模型”，智能体更像“能持续推进任务的系统”。

核心模块说明：

  • LLM Core：负责理解、推理、生成和决策。
  • Planner：把复杂目标拆成步骤。
  • Executor：执行计划中的单个步骤。
  • Tool Router：选择工具并构造调用参数。
  • Memory：保存短期上下文、长期偏好和任务状态。
  • Evaluator：判断结果是否正确、完整、安全。
  • Controller：控制循环、预算、权限、错误恢复和终止条件。

2. Agent、Workflow、RAG 的区别

类型 核心特征 适合场景 主要风险
普通 LLM 单轮或多轮文本生成 问答、摘要、写作 容易幻觉，不能执行动作
Workflow 固定流程编排 审批流、ETL、规则明确任务 灵活性不足
RAG 检索后生成 知识库问答、文档查询 检索质量决定上限
Agent 动态规划、工具调用、反馈修正 复杂任务、自动化执行 不可控、成本高、调试难

工程上不要把所有问题都做成 Agent。规则明确的流程优先用 Workflow，知识问答优先用 RAG，需要动态决策和多步执行时再使用 Agent。

3. ReAct 模式

ReAct 是 Reasoning + Acting，即“推理 + 行动”。模型在思考、调用工具、观察结果之间循环。

3.1. 核心思想

ReAct 让模型不要一次性给出结论，而是在每一步根据环境反馈决定下一步动作。它是多数工具型 Agent 的基础。

3.2. 优点

  • 推理和工具调用过程清晰，便于调试。
  • 适合需要外部信息或多步验证的任务。
  • 工具结果会反过来修正模型判断。
  • 架构简单，容易作为第一个 Agent 原型。

3.3. 缺点

  • 容易陷入重复搜索或无效工具调用。
  • 如果工具返回噪声，模型可能被误导。
  • 循环次数、成本和延迟需要严格控制。
  • Prompt injection 会通过工具结果影响后续决策。

3.4. 适用场景

  • 搜索增强问答。
  • 数据查询。
  • 代码阅读和修改。
  • 浏览器自动化。
  • 运维排障。
  • 需要边做边看的任务。

3.5. 示例代码

def react_agent(goal, llm, tools, max_steps=6):
    trace = []

    for _ in range(max_steps):
        decision = llm({
            "goal": goal,
            "trace": trace,
            "instruction": "Decide the next thought and action.",
        })

        if decision["action"] == "final":
            return decision["answer"]

        tool_name = decision["action"]
        tool_input = decision["action_input"]
        observation = tools[tool_name](tool_input)

        trace.append({
            "thought": decision["thought"],
            "action": tool_name,
            "action_input": tool_input,
            "observation": observation,
        })

    return llm({
        "goal": goal,
        "trace": trace,
        "instruction": "Return the best answer with current evidence.",
    })

3.6. 开发注意事项

  • 设置最大步数、最大工具调用次数和最大 token 预算。
  • 工具返回内容要做清洗，避免把不可信网页内容当成系统指令。
  • 每一步都记录 trace，方便审计和复盘。
  • 让模型在无法确认时停止，而不是继续猜。
  • 高风险工具调用前加入用户确认。

3.7. 是否可以组合使用

可以。ReAct 常和 Tool-Use、RAG、Plan-and-Execute、Evaluator、Reflexion 组合。典型做法是：外层 Planner 负责任务拆解，内层每个步骤用 ReAct 执行。

4. Plan-and-Execute 模式

Plan-and-Execute 把智能体拆成两个角色：先规划，再执行。

4.1. 核心思想

复杂任务如果直接用 ReAct，模型容易走一步看一步。Plan-and-Execute 先生成全局计划，再逐步执行，可以提升长任务稳定性。

4.2. 优点

  • 适合长任务和多阶段任务。
  • 用户能提前看到计划，便于纠偏。
  • 可以把规划和执行使用不同模型或不同 prompt。
  • 容易加入进度展示和任务状态持久化。

4.3. 缺点

  • 初始计划可能错误。
  • 如果执行阶段发现新信息，需要动态重规划。
  • 规划过细会降低灵活性，规划过粗会失去控制。
  • 对任务完成判定要求更高。

4.4. 适用场景

  • 软件开发任务。
  • 数据分析报告。
  • 项目调研。
  • 多文件文档生成。
  • 自动化运维流程。

4.5. 示例代码

def plan_and_execute(goal, planner, executor, evaluator):
    plan = planner.create_plan(goal)
    results = []

    for step in plan["steps"]:
        result = executor.run(step)
        results.append({"step": step, "result": result})

        review = evaluator.check_step(goal, step, result)
        if review["needs_replan"]:
            plan = planner.replan(goal, results, review["reason"])

    return planner.summarize(goal, results)

4.6. 开发注意事项

  • 计划要结构化，例如 id、description、dependencies、expected_output。
  • 支持用户审批计划，尤其是涉及写操作或成本较高的任务。
  • 执行结果要能映射回计划步骤。
  • 重规划不能无限发生，需要设置次数限制。
  • 计划应和实际 trace 一起保存。

4.7. 是否可以组合使用

可以。常见组合是 Plan-and-Execute + ReAct，Planner 生成步骤，Executor 用 ReAct 调工具完成每一步。也可加入 Evaluator 检查步骤质量。

5. Self-Ask 模式

Self-Ask 让模型先把复杂问题拆成多个子问题，再逐个求解。

5.1. 核心思想

把一个大问题拆成可回答的小问题，降低单次推理难度。

5.2. 优点

  • 适合复杂问答和分析。
  • 能显式暴露问题结构。
  • 可结合检索工具分别回答子问题。
  • 有利于减少遗漏。

5.3. 缺点

  • 子问题拆错会导致最终答案偏离。
  • 子答案之间可能互相矛盾。
  • 对简单问题会显得冗余。
  • 需要综合阶段做去重和冲突处理。

5.4. 适用场景

  • 决策分析。
  • 技术方案比较。
  • 研究型问答。
  • 复杂需求澄清。
  • 根因分析。

5.5. 示例代码

def self_ask(question, llm, answer_subquestion):
    subquestions = llm({
        "question": question,
        "instruction": "Break the question into necessary subquestions.",
    })

    answers = []
    for subquestion in subquestions:
        answers.append({
            "question": subquestion,
            "answer": answer_subquestion(subquestion),
        })

    return llm({
        "question": question,
        "subanswers": answers,
        "instruction": "Synthesize a final answer and mention uncertainty.",
    })

5.6. 开发注意事项

  • 限制子问题数量，避免发散。
  • 子问题应互相独立且覆盖主问题。
  • 综合答案时要处理冲突、缺口和不确定性。
  • 对需要证据的问题，每个子答案都应附来源。

5.7. 是否可以组合使用

可以。Self-Ask 经常和 RAG 组合：每个子问题单独检索。也可以和 Evaluator 组合，用评估器检查子问题是否覆盖主问题。

6. Chain-of-Thought 模式

Chain-of-Thought，CoT，是让模型进行逐步推理。实际产品中通常不暴露完整内部推理，而是输出关键理由。

6.1. 核心思想

通过逐步分析提升模型在逻辑、数学、规划问题上的表现。

6.2. 优点

  • 提升复杂推理能力。
  • 有助于模型避免跳步。
  • 对数学、逻辑、规划任务有效。
  • 可作为其他模式的内部推理能力。

6.3. 缺点

  • 完整推理链可能包含错误、隐私或安全信息。
  • 推理越长成本越高。
  • 模型可能生成看似合理但实际错误的推理。
  • 对工具型任务不够，需要结合行动机制。

6.4. 适用场景

  • 数学题。
  • 逻辑推理。
  • 排程规划。
  • 复杂解释。
  • 方案分析。

6.5. 示例代码

def cot_answer(question, llm):
    return llm({
        "question": question,
        "instruction": (
            "Reason internally step by step. "
            "Return only the final answer and a concise explanation."
        ),
    })

6.6. 开发注意事项

  • 不建议把完整思维链直接暴露给终端用户。
  • 输出应强调结论、证据和关键理由。
  • 对事实类问题应结合检索或工具验证。
  • 对高风险结论要要求模型表达不确定性。

6.7. 是否可以组合使用

可以。CoT 更像底层推理能力，可嵌入 ReAct、Planner、Evaluator、Self-Ask 等模式中。

7. Tree of Thoughts 模式

Tree of Thoughts，ToT，把推理从“一条链”扩展为“多条候选路径”，再进行搜索和评估。

7.1. 核心思想

让模型生成多个候选解法，并用评分、剪枝或搜索选择更优路径。

7.2. 优点

  • 适合需要比较多个方案的问题。
  • 能降低单一路径错误带来的风险。
  • 对创意、策略、复杂规划很有帮助。
  • 可以结合评估器做自动筛选。

7.3. 缺点

  • 成本和延迟较高。
  • 评估标准不清时容易选错。
  • 分支过多会失控。
  • 实现复杂度高于 CoT。

7.4. 适用场景

  • 架构设计。
  • 策略选择。
  • 创意生成。
  • 复杂规划。
  • 高风险决策前的方案比较。

7.5. 示例代码

def tree_of_thoughts(problem, llm, evaluator, branch_count=3):
    candidates = llm({
        "problem": problem,
        "instruction": f"Generate {branch_count} different solution paths.",
    })

    scored = []
    for candidate in candidates:
        score = evaluator({
            "problem": problem,
            "candidate": candidate,
            "criteria": ["feasibility", "risk", "completeness"],
        })
        scored.append((candidate, score))

    best = max(scored, key=lambda item: item[1]["total_score"])[0]
    return llm({
        "problem": problem,
        "selected_path": best,
        "instruction": "Produce the final answer.",
    })

7.6. 开发注意事项

  • 明确分支数量和搜索深度。
  • 评估器要有清晰评分标准。
  • 剪枝要早，避免成本爆炸。
  • 对关键任务保留被淘汰方案和理由，便于复盘。

7.7. 是否可以组合使用

可以。常见组合是 ToT + Evaluator + Plan-and-Execute：先生成多个计划，评估后选择一个执行。

8. Reflexion 模式

Reflexion 是“执行后反思”。它让智能体根据失败结果总结原因并调整策略。

8.1. 核心思想

不要把失败简单重试，而是从失败中提取可执行的修正策略。

8.2. 优点

  • 对代码修复、测试失败、工具调用失败很有效。
  • 能把失败信息转化为下一步行动。
  • 可与长期记忆结合，积累经验。
  • 提升长任务鲁棒性。

8.3. 缺点

  • 反思质量依赖错误信息质量。
  • 可能反思错方向。
  • 会增加循环次数和成本。
  • 如果没有客观评估，容易自我安慰式修正。

8.4. 适用场景

  • 自动修复测试失败。
  • 代码生成迭代。
  • 运维故障排查。
  • 文档质量改进。
  • 浏览器自动化失败恢复。

8.5. 示例代码

def reflexion_loop(task, executor, reflector, evaluator, max_attempts=3):
    reflection = None

    for _ in range(max_attempts):
        result = executor.run(task, reflection=reflection)
        review = evaluator.check(task, result)

        if review["passed"]:
            return result

        reflection = reflector({
            "task": task,
            "result": result,
            "issues": review["issues"],
            "instruction": "Explain the root cause and next strategy.",
        })

    return result

8.6. 开发注意事项

  • 反思必须基于真实反馈，例如测试输出、异常日志、评估报告。
  • 反思格式应包含：错误、原因、修正策略、下次避免事项。
  • 设置最大尝试次数。
  • 避免把所有失败都写入长期记忆，只保存可复用经验。

8.7. 是否可以组合使用

可以。Reflexion 适合接在 Evaluator 后，也可嵌入 ReAct 或 Plan-and-Execute 的失败恢复路径。

9. Tool-Use / Function Calling 模式

Tool-Use 让模型通过结构化接口调用真实工具，而不是在文本中假装完成动作。

9.1. 核心思想

把模型的“意图”转成受控的函数调用，由系统执行真实动作。

9.2. 优点

  • 能接入真实系统。
  • 参数结构化，便于校验。
  • 易做权限、日志和审计。
  • 是 Agent 工程化的基础。

9.3. 缺点

  • 工具设计质量直接影响效果。
  • 工具太多会导致选择困难。
  • schema 不清晰会导致参数错误。
  • 写操作存在安全风险。

9.4. 适用场景

  • 数据库查询。
  • 业务 API 调用。
  • 文件读写。
  • 浏览器操作。
  • 代码执行。
  • 工单、CRM、ERP、运维系统集成。

9.5. 示例代码

TOOLS = {
    "search_docs": {
        "description": "Search internal documents.",
        "parameters": {"query": "string"},
    },
    "create_ticket": {
        "description": "Create a support ticket.",
        "parameters": {"title": "string", "body": "string"},
    },
}

def tool_use_agent(message, llm, tool_runtime):
    decision = llm({
        "message": message,
        "tools": TOOLS,
        "instruction": "Return either a tool call or a final answer.",
    })

    if decision["type"] == "tool_call":
        result = tool_runtime.call(
            decision["name"],
            decision["arguments"],
        )
        return llm({
            "message": message,
            "tool_result": result,
            "instruction": "Continue or answer based on the tool result.",
        })

    return decision["answer"]

9.6. 开发注意事项

  • 工具名使用清晰动词，例如 search_docs、send_email。
  • 工具参数尽量简单，避免深层嵌套。
  • 工具返回结构化 JSON，不要返回大段无关文本。
  • 区分只读工具和写操作工具。
  • 对删除、付款、发消息等动作加入人工确认。
  • 给工具设置超时、重试、幂等键和审计日志。

9.7. 是否可以组合使用

可以。Tool-Use 是多数 Agent 模式的基础，通常和 ReAct、Plan-and-Execute、RAG、Memory、Evaluator 一起使用。

10. RAG Agent 模式

RAG Agent 是 Retrieval-Augmented Generation 与 Agent 的结合。它不仅检索一次，而是能根据缺口多轮检索。

10.1. 核心思想

让 Agent 主动决定查什么、是否继续查、如何基于证据回答。

10.2. 优点

  • 降低事实幻觉。
  • 可引用来源。
  • 支持企业私有知识库。
  • 能处理信息不足时的二次检索。

10.3. 缺点

  • 检索质量决定上限。
  • 文档切分不当会丢上下文。
  • 旧文档和冲突文档会误导模型。
  • 多轮检索增加延迟和成本。

10.4. 适用场景

  • 企业知识库问答。
  • 技术文档助手。
  • 法律、金融、医疗文档分析。
  • 客服知识库。
  • 研究助手。
  • 内部制度查询。

10.5. 示例代码

def rag_agent(question, retriever, llm, max_rounds=3):
    evidence = []
    query = question

    for _ in range(max_rounds):
        docs = retriever.search(query)
        evidence.extend(docs)

        decision = llm({
            "question": question,
            "evidence": evidence,
            "instruction": (
                "Decide whether the evidence is enough. "
                "If not, return a better search query."
            ),
        })

        if decision["type"] == "enough":
            break

        query = decision["query"]

    return llm({
        "question": question,
        "evidence": evidence,
        "instruction": "Answer using evidence only and cite sources.",
    })

10.6. 开发注意事项

  • 文档切分要保留标题、层级和语义完整性。
  • 使用 metadata 过滤权限、时间、业务域和文档类型。
  • 回答必须引用来源。
  • 对冲突来源要明确说明。
  • 没有证据时不要编造答案。
  • 建立索引更新、删除和权限同步机制。

10.7. 是否可以组合使用

可以。常见组合包括 RAG + Self-Ask、RAG + ReAct、RAG + Evaluator、RAG + Memory。

11. Memory Agent 模式

Memory Agent 为智能体提供长期状态，包括用户偏好、历史任务、项目上下文和可复用经验。

11.1. 核心思想

让 Agent 在当前上下文之外，记住对长期任务有价值的信息。

11.2. 优点

  • 支持个性化体验。
  • 适合长期项目协作。
  • 可以减少重复解释。
  • 能保存任务进度和偏好。

11.3. 缺点

  • 错误记忆会污染后续结果。
  • 隐私和合规风险高。
  • 旧记忆可能过时。
  • 记忆检索不准会引入噪声。

11.4. 适用场景

  • 个人助手。
  • 编程助手。
  • 长期项目管理。
  • 教育辅导。
  • 客户服务。
  • 需要连续上下文的企业助手。

11.5. 示例代码

class MemoryAgent:
    def __init__(self, llm, memory_store):
        self.llm = llm
        self.memory_store = memory_store

    def run(self, user_id, message):
        memories = self.memory_store.search(
            user_id=user_id,
            query=message,
            limit=5,
        )

        response = self.llm({
            "message": message,
            "memories": memories,
            "instruction": "Respond using relevant memories only.",
        })

        decision = self.llm({
            "message": message,
            "response": response,
            "instruction": "Return whether to save a durable memory.",
        })

        if decision["save"]:
            self.memory_store.save(
                user_id=user_id,
                text=decision["memory"],
                source="conversation",
            )

        return response

11.6. 开发注意事项

  • 明确哪些信息允许保存，哪些禁止保存。
  • 重要记忆最好让用户确认。
  • 支持查看、修改、删除记忆。
  • 每条记忆要有来源、时间戳和置信度。
  • 对旧记忆做衰减或过期处理。
  • 敏感信息默认不保存。

11.7. 是否可以组合使用

可以。Memory 可与 ReAct、RAG、Plan-and-Execute、Reflexion、Multi-Agent 组合。注意不要让所有 Agent 随意写共享记忆。

12. Evaluator / Critic 模式

Evaluator 模式引入评估器检查结果质量。Critic 更偏提出问题，Evaluator 更偏给出通过与否。

12.1. 核心思想

把“生成”和“评估”拆开，让结果经过质量门禁。

12.2. 优点

  • 提升输出质量。
  • 能发现遗漏、矛盾和安全问题。
  • 适合作为自动化验收节点。
  • 可结合测试、规则和静态分析。

12.3. 缺点

  • LLM 自评不总是可靠。
  • 评估标准不清会导致空泛反馈。
  • 增加成本和延迟。
  • 对事实正确性仍需外部证据。

12.4. 适用场景

  • 代码审查。
  • 文档审查。
  • 合规检查。
  • 安全检查。
  • 高质量问答。
  • 自动化工作流验收。

12.5. 示例代码

def generate_with_evaluator(task, generator, evaluator, max_rounds=3):
    candidate = generator(task)

    for _ in range(max_rounds):
        review = evaluator({
            "task": task,
            "candidate": candidate,
            "criteria": ["correctness", "completeness", "safety", "clarity"],
        })

        if review["passed"]:
            return candidate

        candidate = generator({
            "task": task,
            "previous_answer": candidate,
            "issues": review["issues"],
            "instruction": "Revise the answer.",
        })

    return candidate

12.6. 开发注意事项

  • 评估标准要具体、可判定。
  • 能用测试、schema、规则验证的，不要只靠 LLM。
  • 生成器和评估器使用不同 prompt。
  • 高风险任务可使用多个评估器投票。
  • 保留评估日志和失败样本，形成回归测试集。

12.7. 是否可以组合使用

可以。Evaluator 几乎能加入所有架构，尤其适合和 Reflexion、RAG、Code Agent、Multi-Agent 组合。

13. Multi-Agent 模式

Multi-Agent 使用多个角色分工完成复杂任务。

13.1. 核心思想

把复杂任务拆给多个专门 Agent，由 Manager 负责分配、协调和汇总。

13.2. 优点

  • 适合复杂任务和专业分工。
  • 子任务可以并行。
  • 每个 Agent 可以有专门工具和上下文。
  • 更接近真实团队协作流程。

13.3. 缺点

  • 协调成本高。
  • 信息传递容易丢失或失真。
  • 多个 Agent 可能互相强化错误。
  • 成本、延迟和调试难度显著增加。

13.4. 适用场景

  • 大型软件工程。
  • 安全审计。
  • 复杂数据分析。
  • 产品方案设计。
  • 多章节报告生成。
  • 自动化研发流程。

13.5. 示例代码

class MultiAgentSystem:
    def __init__(self, manager, agents):
        self.manager = manager
        self.agents = agents

    def run(self, goal):
        assignments = self.manager.plan(goal)
        results = []

        for assignment in assignments:
            agent = self.agents[assignment["agent"]]
            result = agent.run(assignment["task"])
            results.append({
                "agent": assignment["agent"],
                "task": assignment["task"],
                "result": result,
            })

        return self.manager.summarize(goal, results)

13.6. 开发注意事项

  • 不要过早引入 Multi-Agent。
  • 每个 Agent 的职责、工具和输出格式要明确。
  • Manager 必须能判断任务是否完成。
  • Agent 间通信要结构化，避免无限聊天。
  • 共享上下文要压缩，不能把所有历史都传给所有 Agent。
  • 最终结果需要统一审查。

13.7. 是否可以组合使用

可以。Multi-Agent 本身通常就是组合架构：Researcher 用 RAG，Coder 用 ReAct + Tool-Use，Tester 用工具执行，Reviewer 用 Evaluator。

14. Hierarchical Agent 模式

Hierarchical Agent 是多智能体的分层组织形式，类似“总负责人 - 领域负责人 - 执行者”。

14.1. 核心思想

通过层级组织降低单个 Manager 的复杂度，让不同层级处理不同粒度的问题。

14.2. 优点

  • 适合超复杂任务。
  • 上下文可以分层管理。
  • 组织结构清晰。
  • 便于映射企业流程。

14.3. 缺点

  • 实现复杂。
  • 层级过多会导致信息损耗。
  • 调度、汇总和冲突处理困难。
  • 成本较高。

14.4. 适用场景

  • 企业级自动化系统。
  • 大规模项目规划。
  • 多团队协同任务。
  • 复杂文档或代码库生成。

14.5. 示例代码

def hierarchical_run(goal, director):
    org_plan = director.create_org_plan(goal)
    department_results = []

    for department in org_plan["departments"]:
        lead_agent = department["lead_agent"]
        result = lead_agent.run(department["objective"])
        department_results.append({
            "department": department["name"],
            "result": result,
        })

    return director.finalize(goal, department_results)

14.6. 开发注意事项

  • 层级不要太深，通常两到三层即可。
  • 每层都要有明确输入、输出和完成标准。
  • 上级 Agent 不应关心过多底层细节。
  • 跨团队任务要有同步机制。
  • 汇总阶段要处理冲突和重复。

14.7. 是否可以组合使用

可以。Hierarchical Agent 本质是 Multi-Agent + Plan-and-Execute + Evaluator 的组织化版本。

15. 典型组合架构

15.1. 知识库问答助手

推荐组合：Self-Ask + RAG + Evaluator

适合企业文档、规章制度、技术手册、客服知识库。关键是答案必须可追溯到来源。

15.2. 编程助手

推荐组合：Plan-and-Execute + ReAct + Tool-Use + Tests + Reflexion

适合 IDE 编程助手、自动修 bug、重构辅助。核心是让测试、类型检查和 lint 成为客观反馈。

15.3. 研究报告 Agent

推荐组合：Self-Ask + RAG + Tree of Thoughts + Evaluator

适合市场研究、技术调研、竞品分析。先拆问题，再检索证据，对多个分析框架进行比较，最后评估结论是否充分。

15.4. 企业流程自动化 Agent

推荐组合：Plan-and-Execute + Tool-Use + Memory + Human Approval

适合工单、审批、CRM 更新、运维操作。高风险动作必须有人类确认。

15.5. 多智能体研发团队

推荐组合：Manager + Researcher + Coder + Tester + Reviewer + Writer

适合大型需求实现。Manager 拆解任务，Researcher 查背景，Coder 实现，Tester 验证，Reviewer 审查，Writer 更新文档。

16. 生产环境控制流

上线 Agent 时，真正困难的是让系统可控、可测、可恢复。

生产落地重点：

  • 权限控制：用户、Agent、工具都要有权限边界。
  • 人类确认：删除、付款、发消息、改配置等动作需要确认。
  • 审计日志：记录输入、计划、工具调用、结果和审批人。
  • 预算控制：限制 token、轮数、工具次数、运行时间和费用。
  • 上下文管理：长任务需要摘要、状态持久化和上下文压缩。
  • 安全防护：处理 prompt injection、数据泄露、越权工具调用。
  • 失败恢复：区分可重试错误、业务错误和权限错误。
  • 监控评估：跟踪成功率、工具失败率、人工接管率、用户满意度。

17. 安全设计要点

Agent 安全问题通常不是来自模型本身，而是来自模型能调用工具、读取数据、执行动作。

关键风险：

  • 工具结果中的恶意指令诱导模型越权。
  • 用户让 Agent 读取无权限数据。
  • Agent 把敏感信息写入记忆。
  • 自动执行破坏性操作。
  • RAG 检索到过期或被污染文档。
  • 多 Agent 之间传播错误结论。

建议做法：

  • 把系统指令、用户输入、工具结果分层处理。
  • 工具结果默认视为不可信数据。
  • 写操作使用 allowlist 和确认机制。
  • 对敏感字段做脱敏和访问控制。
  • 日志中避免保存密钥、密码、个人隐私。
  • 对高风险任务使用只读预演，再人工确认执行。

18. 评估与监控

Agent 评估不能只看最终回答，还要看执行过程。

离线评估指标：

  • 任务成功率。
  • 工具选择准确率。
  • 平均步骤数。
  • 平均成本。
  • 幻觉率。
  • 引用准确率。
  • 安全策略触发率。
  • 回归测试通过率。

线上监控指标：

  • 用户满意度。
  • 人工接管率。
  • 工具调用失败率。
  • 平均响应时间。
  • 超预算终止率。
  • 高风险操作审批通过率。
  • 失败任务聚类。

19. 模式选择速查

需求 推荐模式
简单问答 普通 LLM 或 CoT
复杂分析 Self-Ask + Evaluator
查资料回答 RAG 或 RAG Agent
需要调用工具 Tool-Use + ReAct
长任务 Plan-and-Execute
容易失败的任务 Reflexion + Evaluator
需要多方案比较 Tree of Thoughts
需要个性化 Memory Agent
多角色协作 Multi-Agent
企业级复杂流程 Hierarchical Agent + Human Approval

20. 推荐学习路径

建议按以下顺序学习和实践：

  1. 学习 Prompt、上下文窗口、采样参数和结构化输出。
  2. 实现最小 Tool-Use Agent，掌握工具 schema、参数校验和结果处理。
  3. 实现 ReAct 循环，理解思考、行动、观察的闭环。
  4. 加入 RAG，解决知识库和证据来源问题。
  5. 加入 Plan-and-Execute，支持长任务。
  6. 加入 Evaluator，把质量评估从生成逻辑中拆出来。
  7. 加入 Reflexion，让失败能驱动修正。
  8. 加入 Memory，支持长期个性化和项目上下文。
  9. 最后再尝试 Multi-Agent 和 Hierarchical Agent。

21. 最小可行 Agent 模板

下面是一个融合 Plan-and-Execute + ReAct + Tool-Use + Evaluator 的最小架构伪代码。

def production_like_agent(user_goal, planner, llm, tools, evaluator, policy):
    policy.check_user_request(user_goal)
    plan = planner.create_plan(user_goal)
    results = []

    for step in plan["steps"]:
        trace = []

        for _ in range(policy.max_agent_steps):
            decision = llm({
                "goal": user_goal,
                "step": step,
                "trace": trace,
                "tools": tools.describe(),
                "instruction": "Choose a tool call or finish this step.",
            })

            if decision["type"] == "finish_step":
                break

            policy.check_tool_call(decision["tool"], decision["arguments"])

            if policy.requires_approval(decision["tool"]):
                policy.request_human_approval(decision)

            observation = tools.call(decision["tool"], decision["arguments"])
            trace.append({
                "decision": decision,
                "observation": observation,
            })

        review = evaluator.check_step(user_goal, step, trace)
        results.append({
            "step": step,
            "trace": trace,
            "review": review,
        })

        if not review["passed"]:
            break

    return llm({
        "goal": user_goal,
        "plan": plan,
        "results": results,
        "instruction": "Summarize the final result and remaining risks.",
    })

22. 总结

大模型智能体架构可以概括为：

LLM 推理能力
+ 工具执行能力
+ 状态和记忆管理
+ 规划与反馈循环
+ 评估和安全控制

ReAct 是理解 Agent 的入口，Tool-Use 是工程基础，Plan-and-Execute 解决长任务，RAG 解决知识依据，Evaluator 和 Reflexion 提升质量与鲁棒性，Memory 支持长期体验，Multi-Agent 适合复杂协作。

多数项目不需要一开始就上多智能体。更稳妥的路线是先做一个可靠的单 Agent：

Tool-Use + ReAct + Plan-and-Execute + Evaluator + 安全控制

当单 Agent 的职责、上下文或并行需求超过边界时，再引入 Multi-Agent 或分层架构。
