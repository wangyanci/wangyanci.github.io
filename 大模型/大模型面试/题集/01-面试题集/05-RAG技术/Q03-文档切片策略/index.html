## 问题
在 RAG 系统中，文档切片（Chunking）是关键的预处理步骤。有哪些常见的切片策略？各自的优缺点是什么？如何选择合适的切片参数？

## 答案

文档切片是 RAG 系统的关键环节，不合理的切片会导致**语义丢失**或**检索精度下降**。以下是常见策略：

**1. 固定长度切片（Fixed-size Chunking）**

```python
from langchain_text_splitters import CharacterTextSplitter

splitter = CharacterTextSplitter(
    chunk_size=1000,    # 每个 chunk 1000 字符
    chunk_overlap=200   # 重叠 200 字符
)
chunks = splitter.split_documents(documents)
  • 优点：简单直接，实现容易
  • 缺点：可能切断句子或段落，破坏语义完整性

2. 递归字符切片（RecursiveCharacterTextSplitter）

from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=1000,
    chunk_overlap=200,
    separators=["\n\n", "\n", "。", "！", "？", " ", ""]
    # 按优先级尝试分隔符：段落 > 句子 > 空格 > 字符
)
chunks = splitter.split_documents(documents)
  • 优点：优先保持段落/句子完整性，语义更连贯
  • 缺点：chunk 大小可能不均匀
  • 适用场景：通用文本处理，LangChain 推荐方案

3. 语义切片（Semantic Chunking）

基于句子相似度进行切片，当相邻句子语义差异大时切分。

from langchain_experimental.text_splitter import SemanticChunker

splitter = SemanticChunker(
    embeddings,
    breakpoint_threshold_type="percentile"  # 或 "standard_deviation"
)
chunks = splitter.split_documents(documents)
  • 优点：按语义边界切分，检索质量更高
  • 缺点：计算成本高，速度较慢

4. 结构感知切片（Structure-aware）

  • 按 Markdown/HTML 标题层级切分
  • 按代码函数/类切分
  • 按文档章节切分
from langchain_text_splitters import MarkdownHeaderTextSplitter

splitter = MarkdownHeaderTextSplitter(
    headers_to_split_on=[("#", "Header 1"), ("##", "Header 2")]
)
chunks = splitter.split_text(markdown_text)

5. 父文档-子块策略（Parent-Document Retrieval）

┌──────────────────────────────────────────────────────┐
│  父文档（完整文档或大段）                              │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐             │
│  │ 子块 1    │ │ 子块 2    │ │ 子块 3    │  ...      │
│  │ (检索用)  │ │ (检索用)  │ │ (检索用)  │            │
│  └──────────┘ └──────────┘ └──────────┘             │
│  检索时：用子块向量匹配                                │
│  生成时：用父文档完整内容作为上下文                      │
└──────────────────────────────────────────────────────┘
  • 优点：检索精度高，生成时上下文完整
  • 缺点：存储成本增加（需存父子两份数据）

参数选择建议：

参数 推荐值 说明
chunk_size 256-1024 tokens 太小则信息碎片化，太大则检索精度下降
chunk_overlap 10%-20% 保持跨 chunk 的上下文连续性
最小 chunk 50+ tokens 避免过小的无意义 chunk

不同场景的推荐策略：

场景 推荐策略 理由
通用文本 递归字符切片 平衡实现难度和效果
代码文档 结构感知切片 保持函数/类完整性
法律/合同 语义切片 语义完整性要求高
超长文档 父文档-子块策略 兼顾检索精度和生成质量

延伸追问

Q: chunk_size 应该设置多大？

A: 核心原则是不超过 Embedding 模型的最大输入长度和LLM 的上下文窗口的 1/4-1/3。一般经验值：

  • 短文本问答：256-512 tokens
  • 通用知识库：512-1000 tokens
  • 长文档摘要：1000-2000 tokens

Q: 重叠(overlap)的作用是什么？

A: 重叠确保跨 chunk 的上下文不会断裂。例如一个完整的句子"张三的年龄是25岁，他是北京分部的经理"，如果不重叠，可能被切成"张三的年龄是25岁"和"他是北京分部的经理"，导致第二个 chunk 缺少主语。

常见误区

  1. 一刀切使用固定切片 — 不同类型的文档应该用不同的切片策略
  2. 完全忽略重叠 — 没有重叠会导致跨 chunk 语义断裂
  3. chunk 越大越好 — 过大的 chunk 会降低检索精度，噪声增多
  4. 不考虑下游 LLM 的上下文限制 — chunk 数量 × chunk 大小不应超过 LLM 上下文窗口
